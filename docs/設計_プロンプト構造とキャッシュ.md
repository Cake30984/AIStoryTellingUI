# 設計_プロンプト構造とキャッシュ

プロンプトの**組み立て順・注入位置（深さ）・プロンプトキャッシュ**の設計。2026-08-02 合意・**全フェーズ未着手**。

きっかけは「LLM がユーザーに甘すぎる（迎合）」「レビューが遅い」という実使用の不満で、対策を検討する過程で
**現状ほぼプロンプトキャッシュが効いていない**ことが判明した。指示の効き（＝品質）と キャッシュ（＝コスト）は
どちらも「何をどこに置くか」で決まるため、同じ設計として1本にまとめる。

---

## 0. 前提となる2つの原理

| 原理 | 内容 | 帰結 |
|---|---|---|
| **プレフィックス一致** | キャッシュはトークン0からの前方一致でのみ効く。途中が1トークン変わると**そこから後ろが全部ミス**する | 変わらないものを前、変わるものを後ろへ |
| **近接優位** | 生成点に近い指示ほど強く効く。system 冒頭の指示は長い履歴に埋もれて薄まる | 効かせたい指示は末尾へ |

この2つは**同じ方向を向いていない**。「安定していて、かつ強く効かせたい」ブロック（出力形式・執筆ルール・作者ノート）で衝突する。

> **衝突の解法**: 本体は前に置いてキャッシュに乗せ、**末尾に短い再掲を置く**。再掲は数十トークンなので毎ターン非キャッシュでも無視できる。

## 1. リクエスト種別の棚卸し

アプリが LLM に投げるリクエストは5種類。

| # | 種別 | 呼び出し箇所 | 組み立て | 頻度 | 入出力の比重 |
|---|---|---|---|---|---|
| R1 | **本編生成** | `store.ts:2067` | `buildMessages()` ＋ 末尾に任意の念押し | 毎ターン | 入力大・出力中 |
| R2 | **選択肢生成** | `store.ts:2170` | `choicesSystem()` ＋ `base.slice(1)` ＋ 末尾念押し | 毎ターン（`always`） | **入力大・出力極小** |
| R3 | **シーン終了レビュー** | `store.ts:2942` | `reviewSystem()` ＋ user 1通（文脈＋関係性＋本文） | シーンごと1回 | 入力中・**出力大** |
| R4 | **次シーン候補の再生成** | `store.ts:3487` | `nextSceneSystem()` ＋ user 1通 | 手動・稀 | 入力小・出力小 |
| R5 | **画像プロンプト起案** | `ImageGenModal.tsx:115` | `illustrationPromptSystem()` ＋ user 1通 | 手動・稀 | 入力小・出力小 |

### 現状のキャッシュ可否

**そもそも `cache_control` を送っていない**（`openrouter.ts:50` の body は model/messages/temperature/max_tokens/stream のみ）。
Anthropic 系は明示的なブレークポイントが無いとキャッシュされないため、**そのファミリでは全種別0%**。
以下は OpenAI・DeepSeek 等の**自動プレフィックスキャッシュ**が効く前提での評価。

| # | 現状 | 原因 | 改善余地 |
|---|---|---|---|
| R1 | **ほぼ効かない** | `selectLoreEntries` が **system の最初のブロック**（`prompts.ts:71`）で、`SCAN_DEPTH=6` のスライディングウィンドウ（`lorebook.ts:14`）＝項目が入ったり抜けたりして毎ターン変わる。位置ほぼ0で壊れるので以降が全滅 | **大**（並べ替えだけで解決） |
| R2 | **効かない** | 履歴は R1 と完全に同一なのに、**先頭の system を `choicesSystem` に差し替えている**（`store.ts:2158`）＝トークン0が違うので1トークンも再利用できない | **最大**（後述） |
| R3 | **効かない**（構造上） | system が `reviewSystem` で R1 と別物。さらに `reviewModel` を別モデルにするとキャッシュの名前空間ごと別 | **小**（狙う価値なし） |
| R4 | 効かない | 同上・かつ稀 | なし |
| R5 | 効かない | 独立プロンプト・稀 | なし |

### 結論：狙うべきは R1 と R2 のみ

- **R2 が最優先**。毎ターン走り、**入力支配**（出力は JSON 100トークン程度、`maxTokens: 600`）。にもかかわらず現在0%。
  system 差し替えをやめて R1 と同じ接頭辞にすれば、入力がほぼ丸ごとヒットに変わる。
- **R1 が次点**。並べ替えだけで大部分が解決する。
- **R3 は対象外**。出力支配なので入力を無料にしても総額はほぼ変わらない。概算（入力5k・出力1.5kトークン）:

  | 構成 | 入力 | 出力 | 合計 |
  |---|---|---|---|
  | 本編と同じ高性能モデル・キャッシュヒット | $0.0015 | $0.0225 | **$0.024** |
  | 安いモデル・キャッシュミス | $0.0014 | $0.0017 | **$0.003** |

  **8倍差で「安いモデルを別に充てる」が勝つ**。`reviewModel` を分離できる現在の設計が正解で、
  キャッシュのためにモデルを統一するのは損。（単価は概算・要再確認）

## 2. `buildSystemPrompt` の三層化（R1）

現在の `parts` は「毎ターン変わるもの」が先頭と末尾に散っている。変化頻度で3層に整理し、**安定 → 準安定 → 可変**の順に並べ替える。

| 層 | 変化頻度 | ブロック |
|---|---|---|
| **T1 安定** | セッション中ほぼ不変 | 文体・執筆ルール／【セリフの出力形式】／【物語設定】／【ユーザーが演じる人物】／【配役】／【世界観】description |
| **T2 準安定** | シーン境界でのみ変化 | 【登場人物】（成長で追記される）／【最初の方向付け】（最初のシーンのみ→消える）／【これまでのあらすじ】／【現在の場面】／【時間】／【状態（現在）】の**値**／【エンディング】 |
| **T3 可変** | 毎ターン変化 | キーワード選択されたロア／【今回の応答】（群像のみ） |

**要点は「ロアを `description` から切り離して T3 へ落とす」ことに尽きる**。それ以外は既に概ね正しい位置にある。
これでシーン中はプレフィックスが安定し、**シーン境界で1回だけ壊れる**形になる。

### 注意

- 【登場人物】は T1 に見えるが、レビューで `developments` が追記されるため T2。**変わるものは必ず変わらないものの後ろ**に置く。
- 【状態（現在）】は**値は T2**、そこに付いている指示文（後述）は末尾へ分離する。

## 3. 注入の深さ

### 3.1 採用する段階

| 位置 | 実体 | キャッシュ影響 | 用途 |
|---|---|---|---|
| **system** | `buildSystemPrompt` 内（T1〜T3） | なし（前提） | 全体の傾向・設定・素材 |
| **末尾（深さ0）** | messages の最後に user メッセージを1通足す | **なし**（キャッシュ対象の後ろ） | 今すぐ強く効かせたい指示 |
| **深さ3** | 末尾から3メッセージ手前に挿入 | 直近3件ぶんを無効化 | 毎ターン守らせたいが、命令的にしたくないもの |

深さ0は `CONTINUE_PROMPT` / `CONTINUATION_NUDGE` / `choicesUserNudge`（`prompts.ts:309-321`）で**既に実績がある**。
`choicesUserNudge` のコメントが「モデルは直近の user 指示に強く従うため」と原理まで書いているとおり。

深さ3を採るのは、SillyTavern の Author's Note が既定 depth 4 付近・実務値 2〜4 で運用されており、
**「毎ターン効くが命令口調にならない」帯**として実績があるため。（既定値の正確な数字は要確認）

### 3.2 割り当て表

| 設定項目 | 現在 | 変更後 | 理由 |
|---|---|---|---|
| 世界観 description | system 先頭 | **system T1** | 全体の傾向。安定 |
| ロア（キーワード選択） | **system 先頭** | **system T3（末尾側）** | 毎ターン変わる。前にあるとキャッシュを壊す |
| 【配役】 | system | system T1 | 安定 |
| 【登場人物】 | system | system T2 | 成長で変わる |
| 【物語設定】 | system | system T1 | 安定 |
| 【ユーザーが演じる人物】 | system | system T1 | 安定 |
| 【最初の方向付け】 | system | system T2 | 最初のシーンのみ＝境界で消える。傾向づけなので system が正しい |
| 【これまでのあらすじ】/【現在の場面】/【時間】/【エンディング】 | system | system T2 | 境界で変わる素材 |
| 【状態（現在）】の**値** | system | system T2 | 境界で変わる素材 |
| **状態→帰結の拘束文** | system（値と同居） | **深さ3** | 迎合対策の主役。毎ターン効かせたいが命令的にしたくない |
| **【常に踏まえる重要事項】(`authorNote`)** | **system** | **深さ3** | 名前が「常に踏まえる」なのに一番効かない場所にある。現状のねじれ |
| 文体・執筆ルール | system | **system T1 ＋ 末尾に短い再掲** | 安定なので前へ。効きの担保は再掲で |
| 【セリフの出力形式】 | system 末尾 | **system T1 ＋ 末尾に短い再掲** | 同上。遵守が要る形式指示なので再掲は必須 |
| 【シーンの収束】/【シーンの締め】 | system | **末尾（深さ0）** | 「今すぐ畳め」の指示。system では埋もれる |
| 【今回の応答】（群像の話者指定） | system | **末尾（深さ0）** | そのターン限定の指示 |
| 続き生成の念押し | 末尾 | 末尾（変更なし） | 既に正しい |

### 3.3 実装上の決定

- **深さ3が存在しない場合はクランプして system 直後へ**。履歴は現在シーンに絞られている（`prompts.ts:298`）ため、
  シーン開始直後は履歴が1〜2件しかない。結果として「シーン序盤は弱く、後半ほど強く効く」挙動になる。
  締めのナッジには好都合、`authorNote` には微妙——**意図した挙動として受け入れる**。
- **ユーザーが深さを設定できる UI は作らない**。欄ごとに意図が確定しており、選ばせる必然性がない。
  またユーザーは A/B テストできないので良し悪しを判断できない。将来出すとしても `authorNote` 1箇所のみ・上級オプション扱い。
- 深さ3は毎ターン直近3件を無効化する。**原文窓を広げる（§4）と分母が増えて割合が下がる**ので、
  実装順は「並べ替え → 原文窓 → 深さ3」が影響最小。

## 4. 原文窓と畳み方

現状は「現在シーンの原文＋それ以前は要約」（`prompts.ts:298`）で、**原文の窓が1シーンしかない**。
シーンが変わった瞬間に直前まで読んでいた内容が要約1段落に潰れ、「忘れられた」体感の主因になる。

キャッシュヒット時の入力単価が十分安いモデルでは、原文を数シーンぶん載せても現実的なコストに収まる。
ただし**要約は廃止しない**——要約が担っているのは圧縮ではなく**取捨選択（saliency の付与）**だから。
`reviewSystem` の要約は「重要な出来事・関係や心情の変化・約束や未解決事項」を選んでおり、
全文を渡すと捨て台詞と約束が等価になってモデルが重要度を判断できなくなる。

### 全文送信を採らない理由（品質面）

| 悪化する側 | 内容 |
|---|---|
| 中間の希薄化 | 長文脈では中盤の情報の参照精度が落ちる。関係性・約束が散文に埋もれる |
| **指示の希薄化** | 迎合・ナッジ不発は**指示と本文の量比**の問題。全文送信はこれを最悪化する |
| 自己模倣の固定化 | モデルは自分の過去出力を強く真似る。言い回しの癖・段落構成が増幅されて抜けない |
| 矛盾の蓄積 | 過去の綻びが原文のまま残る。要約はそれを黙って洗浄している |

### 採用する構成

- **要約層（全期間）** ＝ saliency。維持。
- **原文層（直近Nシーン・トークン予算で決定）** ＝ 具体と声。目安 1.5万〜2万トークン。
- それ以前は要約のみ。

### 畳み方の3原則

1. **階段状に畳む**（1シーンずつ滑らせない）。滑らせるとシーン境界ごとにプレフィックスが壊れる。
   予算いっぱいまで一切落とさず、超えたら数シーンぶんまとめて畳む＝無効化の頻度が数分の1になる。
2. **橋を残す**。畳んだブロックの**末尾だけ原文で残す**（最後のシーン1つ、または末尾1000トークン程度）。
   一気に畳むと「ターンNでは覚えていたことをターンN+1で覚えていない」という**記憶密度の段差**が生じ、
   読者には理由が見えないぶん不気味に映る。橋があると段差が傾斜になる。
3. **シーン境界でのみ畳む**。読者が既に断絶を受け入れている場所に変化を紛れ込ませる。シーン途中で畳むのは最悪。
4. **要約は連結優先**。畳むときに複数シーンの要約を作り直すと情報が二重に失われる。
   まず既存のシーン要約を**連結するだけ**（無料・粒度も保たれる）。連結が長くなりすぎた段階で初めて上位要約へ。

## 5. レビューの遅さ

**キャッシュでは改善しない。** ボトルネックが入力（プリフィル）ではなく**出力（トークン生成）**にあるため。
レビューの出力は `summary` + `suggestions`×3 + `characterGrowth` + `worldGrowth` + `relationUpdates` + `moods`
+ `statChanges` + `counterEvents` で 1000〜2000トークン。特に `relationUpdates` は仕様として
**差分でなく現時点の全文**（`prompts.ts:441`）を要求しており、**参加キャラ数に比例して伸びる**。おそらくこれが最大要因。

採る手:

| 手 | 内容 | 判断 |
|---|---|---|
| 軽量モデル | `reviewModel` に安いモデルを充てる（既に分離可能） | **採用**。既定を軽いモデルにする |
| **ストリーミングで段階表示** | JSON は `summary` → `suggestions` → … の順に出るので、要約が出た時点でモーダルを埋め始める | **採用**。投機ゼロで体感だけ縮む |
| 2本に分割して並列実行 | 要約＋次シーン候補 / 状態変動 に分ける。壁時計時間ほぼ半分・入力コスト約2倍 | **採用（ユーザー設定）** |
| 裏で走らせる（投機実行） | シーン終了を押す前に開始 | **却下**。ユーザーが続きを書けば丸ごと無駄になる |

### 並列/逐次の設定

「AIと出力」タブに真偽値1つ。**並列とキャッシュは両立しない**（2本同時投入は両方ミスする。逐次なら2本目はヒットするが
出力時間が2倍になり本末転倒）ため、**並列＝入力2倍を受け入れる / 逐次＝1本にまとめる**の二択として提示する。

コスト増分の概算（レビュー入力5k・出力1.5k・50シーン）:

| モデル | 1シーン増分 | 50シーン |
|---|---|---|
| 格安（入力$0.27/M級） | 約 $0.0014 | 約 $0.07 |
| Sonnet 級（入力$3/M） | 約 $0.015 | 約 $0.75 |

レビューは出力支配なので、入力を倍にしても総額は4割増し程度。**両端とも許容範囲**。

## 6. プロンプトの中身に関する決定（迎合と隠し設定）

深さの議論と対になる、**何を書くか**の決定。

### 6.1 迎合（ユーザーに甘すぎる）対策

**プロンプトで「失敗させてよい」と許可するのは却下**。モデルは「失敗を書くべき対象」を局所的に選ぶため、
指定した行動だけ失敗して他は全部成功する不自然な偏りが出る。

採るのは**状態を帰結に接続すること**。現在の `prompts.ts:138` は

> 関係性の記述と矛盾しない態度・口調・距離感で描写してください

と**態度の話しかしていない**。これを「応じるかどうかは各キャラの現在の関係性から決まる。
関係が浅い段階で本人が同意しないことは、頼まれても起きない」に変える。
迎合が*好みの問題*から*整合性の問題*になり、モデルは後者をかなり守る。**深さ3へ置く**（§3.2）。

### 6.2 システムの領分と作者の領分

線引きは「どれくらい踏み込むか」ではなく**主張の種類**で引く。

| 領分 | 内容 | 例 |
|---|---|---|
| **システム＝媒体の文法** | ジャンルによらず真。構造的 | 出力形式／ユーザーの発言を勝手に決めない／**状態を判断材料に使う** |
| **作者＝価値判断** | 世界ごとに異なる | どれくらい厳しいか／何が失敗しうるか／拒まれることが普通か |

6.1 の拘束文は「厳しくしろ」ではなく「用意されている状態を使え」なので**構造側＝システムの領分**。
自己中和的で、全員が好意的な世界なら数値が高いのでモデルも好意的に振る舞う。過干渉にならない。

「拒む・失敗する」は価値側＝**作者の領分**で、置き場所は既にある（`World.startPreset.authorNote`）。
**境界線はデータモデル上に既に引かれており、問題は `authorNote` が弱すぎる場所に注入されていて機能していなかったこと**。
深さを直せば作者の領分が実際に使えるようになり、だからこそシステムが肩代わりする必要がなくなる。

**既定文の扱い**: 新規世界観の `startPreset.authorNote` に**書かれた状態で置き、消せるようにする**。
変更不能な既定＝押し付け、空欄＝誰も書かず迎合したまま、の中間を採る。

### 6.3 隠し設定（作家の仕込み）

- **本体は `Clause` への `eventFired` 節の追加**。現在 `stat`/`counter`/`achievement`/`group` の4種しかなく、
  「あのイベントが起きた後」を条件に書けない。`Session.usedEventIds` は既に永続化済みなので、
  節1つ＋`evalCondition` 1分岐＋`ClauseRow` 1行で、**実績・エンディング・イベントの全部で同時に使えるようになる**。
- **ロアの解禁条件はその応用**。`LoreEntry` に `Condition` を持たせ、未達なら system に注入しない・達したら注入＋発見ログへ。
- **「知っているが明かすな」型は作らない**（却下）。LLM は漏らすか、逆に禁止語へ引き寄せられて不自然にほのめかす。
  調整コストが青天井。**注入しなければ漏れない**。

## 8. 却下・保留

| 案 | 判断 | 理由 |
|---|---|---|
| 本文全体を毎ターン送る（要約廃止） | **却下** | コストは現実的だが、指示の希薄化・自己模倣・中間の希薄化で品質が落ちる。要約は圧縮でなく取捨選択 |
| レビューを本編と同じ接頭辞にしてキャッシュ共有 | **却下** | 出力支配なので割に合わない（8倍差で安いモデルの勝ち）。別モデルなら名前空間ごと別 |
| レビューの投機実行 | **却下** | ユーザーが続きを書けば無駄になる |
| 深さをユーザーが設定できる UI | **保留** | 欄ごとに設計で決まる。将来 `authorNote` のみ上級オプション |
| 深さ1・2・4 の使い分け | **保留** | v1 は system／末尾／深さ3 の3段階。末尾が命令的すぎると感じたら調整代として使う |
| ダイス判定（選択肢に `check`） | **却下** | 選択肢は AI 生成なので難易度も AI が決めることになり「作家の仕込み」にならない。`Choice.effects` を廃した FB7-C とも逆行 |
| プロンプトで失敗を許可する | **却下** | 指定した行動だけ失敗する不自然な偏りが出る（§6.1） |
| ステータスの自然減衰 `decayPerScene` | **保留** | `World.reviewGuidance` でほぼ同じことが書ける。差分は決定性と可視性のみ。導入するなら理由は「緊張感」より**迎合の固定化ループを断つこと** |
