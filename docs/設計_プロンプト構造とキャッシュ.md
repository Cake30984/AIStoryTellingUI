# 設計_プロンプト構造とキャッシュ

プロンプトの**組み立て順・注入位置（深さ）・プロンプトキャッシュ**の設計。2026-08-02 合意・**全フェーズ未着手**。

> **⚠ 2026-08-02、実測により本書の判断が3点変更されている。実装前に必ず
> [`詳細設計_プロンプト構造とキャッシュ.md`](./詳細設計_プロンプト構造とキャッシュ.md) を読むこと。**
> ①**PC1 の三層化（並べ替え）はキャッシュに無価値**——粒度がメッセージ単位で、system を1文字でも変えると
> system 全体が無効になるため（§2 の並べ替え自体は品質目的でのみ有効）
> ②**PC2（R2 の接頭辞共有）は却下**——本書 §1 の「R2 は1トークンも再利用できない」が誤りで、
> 実測では R2 は自分自身の前ターンの系列に乗っている（46%）。接頭辞共有は期待値で負けるため、
> §7 の「対案（文脈を削る）」を採る
> ③**PC-B の測定手順は2ターン制へ修正**——小説形式の1応答では帰結が描かれず判定不能になるため。
> なお **§2 の「可変ロアを system 末尾に置く」却下と、§7 の「PC-C を PC3 の前に」は実測で裏づけられた**。

> **2026-08-02 レビュー反映済み。** 主な修正: ①可変ロアの置き場所を「system 末尾」から**深さ注入**へ
> （system 末尾では後続の履歴が丸ごとミスするため・§2）②R3 のキャッシュ対象外の理由を訂正（§1）
> ③深さクランプ時の効きの向きを訂正（§3.3）④逐次実行の時間見積りを訂正（§5）
> ⑤フェーズ順を依存順から**確実性 × 価値**順へ（§7）⑥迎合対策の文面を**実測で決める** 5案に展開（§6.1）
> ⑦プロンプトの言語方針を明文化（§6.3）。

きっかけは「LLM がユーザーに甘すぎる（迎合）」「レビューが遅い」という実使用の不満で、対策を検討する過程で
**現状ほぼプロンプトキャッシュが効いていない**ことが判明した。指示の効き（＝品質）と キャッシュ（＝コスト）は
どちらも「何をどこに置くか」で決まるため、同じ設計として1本にまとめる。

## 0. 前提となる2つの原理

| 原理 | 内容 | 帰結 |
|---|---|---|
| **プレフィックス一致** | キャッシュはトークン0からの前方一致でのみ効く。途中が1トークン変わると**そこから後ろが全部ミス**する。**単位は system 文字列ではなく messages 配列全体**（`[system][履歴…]`）＝ system の末尾が変われば履歴も丸ごと巻き添えになる | 変わらないものを前、変わるものを後ろへ。**「後ろ」は system の末尾ではなく messages の末尾** |
| **近接優位** | 生成点に近い指示ほど強く効く。system 冒頭の指示は長い履歴に埋もれて薄まる | 効かせたい指示は末尾へ |

この2つは**同じ方向を向いていない**。「安定していて、かつ強く効かせたい」ブロック（出力形式・執筆ルール・作者ノート）で衝突する。

> **衝突の解法**: 本体は前に置いてキャッシュに乗せ、**末尾に短い再掲を置く**。再掲は数十トークンなので毎ターン非キャッシュでも無視できる。

## 1. リクエスト種別の棚卸し

アプリが LLM に投げるリクエストは5種類。

| # | 種別 | 呼び出し箇所 | 組み立て | 頻度 | 入出力の比重 |
|---|---|---|---|---|---|
| R1 | **本編生成** | `store.ts:2067` | `buildMessages()` ＋ 末尾に任意の念押し | 毎ターン | 入力大・出力中 |
| R2 | **選択肢生成** | `store.ts:2170` | `choicesSystem()` ＋ `base.slice(1)` ＋ 末尾念押し | 毎ターン（`always`） | **入力大・出力極小** |
| R3 | **シーン終了レビュー** | `store.ts:2942` | `reviewSystem()` ＋ user 1通（文脈＋関係性＋本文） | シーンごと1回 | 入力中・**出力大** |
| R4 | **次シーン候補の再生成** | `store.ts:3487` | `nextSceneSystem()` ＋ user 1通 | 手動・稀 | 入力小・出力小 |
| R5 | **画像プロンプト起案** | `ImageGenModal.tsx:115` | `illustrationPromptSystem()` ＋ user 1通 | 手動・稀 | 入力小・出力小 |

### 現状のキャッシュ可否

**そもそも `cache_control` を送っていない**（`openrouter.ts:50` の body は model/messages/temperature/max_tokens/stream のみ）。
Anthropic 系は明示的なブレークポイントが無いとキャッシュされないため、**そのファミリでは全種別0%**。
以下は OpenAI・DeepSeek 等の**自動プレフィックスキャッシュ**が効く前提での評価。

| # | 現状 | 原因 | 改善余地 |
|---|---|---|---|
| R1 | **ほぼ効かない** | `selectLoreEntries` が **system の最初のブロック**（`prompts.ts:71`）で、`SCAN_DEPTH=6` のスライディングウィンドウ（`lorebook.ts:4`）＝項目が入ったり抜けたりして毎ターン変わる。位置ほぼ0で壊れるので以降が全滅 | **大**（ただし system 内の並べ替えでは不十分。可変ロアは messages 側へ出す＝§2） |
| R2 | **効かない** | 履歴は R1 と完全に同一なのに、**先頭の system を `choicesSystem` に差し替えている**（`store.ts:2159`）＝トークン0が違うので1トークンも再利用できない | **最大**（後述。ただし選択肢用モデル＝本編モデルのときに限る） |
| R3 | **効かない**（構造上） | system が `reviewSystem` で R1 と別物。さらに `reviewModel` を別モデルにするとキャッシュの名前空間ごと別 | **小**（狙う価値なし） |
| R4 | 効かない | 同上・かつ稀 | なし |
| R5 | 効かない | 独立プロンプト・稀 | なし |

### 結論：狙うべきは R1 と R2 のみ

- **R2 が最優先**。毎ターン走り、**入力支配**（出力は JSON 100トークン程度、`maxTokens: 600`）。にもかかわらず現在0%。
  system 差し替えをやめて R1 と同じ接頭辞にすれば、入力がほぼ丸ごとヒットに変わる。
  **前提条件**: `choicesModelOf` は `s.choicesModel` を優先し未指定時のみ本編モデルを使う（`store.ts:751`）。
  ユーザーが選択肢用に別モデルを指定していると、R3 と同じ理由（名前空間が別）で**接頭辞を揃えても1トークンもヒットしない**。
  PC2 の効果は「選択肢用モデル未指定 or 本編と同一」のときに限られる。既定は同一なので大半のユーザーには効くが、
  「別モデル指定時はキャッシュ利得が消える」ことを設定 UI の説明に書く。
- **R1 が次点**。可変ロアを system から追い出せば大部分が解決する（**system 内の並べ替えだけでは足りない**・§2）。
- **R3 は対象外**。理由は「入力が無視できるから」では**ない**（入力は総額の約4割を占める。§5 参照）。
  ①構造上ヒットしない（system が `reviewSystem` で R1 と別物・`reviewModel` を分ければ名前空間ごと別）
  ②仮にヒットさせられても、**モデルを差し替えるほうが桁違いに効く**——の2点による。
  概算（入力5k・出力1.5kトークン）:

  | 構成 | 入力 | 出力 | 合計 |
  |---|---|---|---|
  | 本編と同じ高性能モデル・キャッシュヒット | $0.0015 | $0.0225 | **$0.024** |
  | 本編と同じ高性能モデル・キャッシュミス | $0.015 | $0.0225 | $0.0375 |
  | 安いモデル・キャッシュミス | $0.0014 | $0.0017 | **$0.003** |

  高性能モデル内でのキャッシュ効果は約36%減にとどまるのに対し、モデル差し替えは**8倍差**。
  **「安いモデルを別に充てる」が圧勝する**ので、`reviewModel` を分離できる現在の設計が正解で、
  キャッシュのためにモデルを統一するのは損。（単価は概算・要再確認）

## 2. `buildSystemPrompt` の三層化（R1）

現在の `parts` は「毎ターン変わるもの」が先頭と末尾に散っている。変化頻度で3層に整理し、**安定 → 準安定 → 可変**の順に並べ替える。

| 層 | 変化頻度 | ブロック | 置き場所 |
|---|---|---|---|
| **T1 安定** | セッション中ほぼ不変 | 文体・執筆ルール／【セリフの出力形式】／【物語設定】／【ユーザーが演じる人物】／【配役】／【世界観】description／**`alwaysOn` のロア** | system 前半 |
| **T2 準安定** | シーン境界でのみ変化 | 【登場人物】（成長で追記される）／【最初の方向付け】（最初のシーンのみ→消える）／【これまでのあらすじ】／【現在の場面】／【時間】／【状態（現在）】の**値**／【エンディング】 | system 後半 |
| **T3 可変** | 毎ターン変化 | **キーワード選択されたロア**／【今回の応答】（会話劇の群像で話者指定がある場合） | **system ではなく messages 末尾側**（§3） |

**要点は「ロアを `description` から切り離す」ことに尽きる**。それ以外は既に概ね正しい位置にある。
T1+T2 だけになった system は**シーン境界で1回だけ壊れる**形になる。

### 注意

- 【登場人物】は T1 に見えるが、レビューで `developments` が追記されるため T2。**変わるものは必ず変わらないものの後ろ**に置く。
  （**CS1 でシーン単位のキャスト絞り込みを廃止**したので、シーンが変わってもキャラの顔ぶれ自体は動かなくなった。
  残る T2 要因は `developments` の追記だけ＝`設計_登場制御の見直し.md`）
- 【状態（現在）】は**値は T2**、そこに付いている指示文（後述）は末尾へ分離する。

### T3 を「system の末尾」に置いてはいけない

当初この節は「ロアを system の末尾（T3）へ落とす」と書いていたが、**それではキャッシュは守れない**。
プレフィックス一致は system 文字列の中ではなく **messages 配列全体**に効き、順序は `[system][履歴…]` だからだ。
system の末尾が毎ターン変われば、**その後ろに続く履歴が丸ごとミスする**。

分量で見ると致命的になる。現在シーンの履歴は `SCENE_WRAP_UP_TOKENS = 4500`（`tokens.ts:26`）まで伸びる＝
system と同程度で、**「並べ替えだけ」で守れるのは入力の半分程度**にとどまる。さらに §4 で原文窓を
1.5万〜2万トークンへ広げると履歴が入力の大半を占めるので、**system 末尾に可変ブロックを置く設計は
PC3 を入れた瞬間に破綻する**。

したがって T3 の置き場所は **messages 末尾側（§3 の深さ注入）** とする。無効化されるのが
「深さ N 以降の数メッセージ」に限定され、履歴の大部分がキャッシュに残る。
§3 の深さ機構をすでに作るので、追加の仕組みは要らない。

- **`alwaysOn` のロアは T3 に落とさない。** `selectLoreEntries` はキーワードに関係なく常に返す（`lorebook.ts:20`）＝
  変化しないので T1 に残す。毎ターン変わるのは**キーワード一致ぶんだけ**で、そこだけを深さへ送れば churn は最小になる。
- 【今回の応答】も同様に、話者を自動選択する分岐（`prompts.ts:257`）では文面が固定＝実質 T1。
  可変なのは `activeCharacter` を指定した場合だけ。

## 3. 注入の深さ

### 3.1 採用する段階

| 位置 | 実体 | キャッシュ影響 | 用途 |
|---|---|---|---|
| **system** | `buildSystemPrompt` 内（T1〜T2） | なし（前提） | 全体の傾向・設定・素材 |
| **末尾（深さ0）** | messages の最後に user メッセージを1通足す | **なし**（キャッシュ対象の後ろ） | 今すぐ強く効かせたい指示 |
| **深さ3** | 末尾から3メッセージ手前に挿入 | 直近3件ぶんを無効化 | 毎ターン守らせたいが、命令的にしたくないもの |

深さ0は `CONTINUE_PROMPT` / `CONTINUATION_NUDGE`（`prompts.ts:309-321`）／`choicesUserNudge`（`prompts.ts:345`）で**既に実績がある**。
`choicesUserNudge` のコメントが「モデルは直近の user 指示に強く従うため」と原理まで書いているとおり。

深さ3を採るのは、SillyTavern の Author's Note が既定 depth 4 付近・実務値 2〜4 で運用されており、
**「毎ターン効くが命令口調にならない」帯**として実績があるため。（既定値の正確な数字は要確認）

### 3.2 割り当て表

| 設定項目 | 現在 | 変更後 | 理由 |
|---|---|---|---|
| 世界観 description | system 先頭 | **system T1** | 全体の傾向。安定 |
| ロア（`alwaysOn`） | system 先頭 | **system T1** | キーワードに関係なく常に入る＝不変 |
| ロア（キーワード選択） | **system 先頭** | **深さ3（T3）** | 毎ターン変わる。system 内のどこに置いても後続の履歴を壊す（§2） |
| 【配役】 | system | system T1 | 安定 |
| 【登場人物】 | system | system T2 | 成長で変わる |
| 【物語設定】 | system | system T1 | 安定 |
| 【ユーザーが演じる人物】 | system | system T1 | 安定 |
| 【最初の方向付け】 | system | system T2 | 最初のシーンのみ＝境界で消える。傾向づけなので system が正しい |
| 【これまでのあらすじ】/【現在の場面】/【時間】/【エンディング】 | system | system T2 | 境界で変わる素材 |
| 【状態（現在）】の**値** | system | system T2 | 境界で変わる素材 |
| **状態→帰結の拘束文** | system（値と同居） | **深さ3** | 迎合対策の主役。毎ターン効かせたいが命令的にしたくない |
| **【常に踏まえる重要事項】(`authorNote`)** | **system** | **深さ3** | 名前が「常に踏まえる」なのに一番効かない場所にある。現状のねじれ |
| 文体・執筆ルール | system | **system T1 ＋ 末尾に短い再掲** | 安定なので前へ。効きの担保は再掲で |
| 【セリフの出力形式】 | system 末尾 | **system T1 ＋ 末尾に短い再掲** | 同上。遵守が要る形式指示なので再掲は必須 |
| 【シーンの収束】/【シーンの締め】 | system | **末尾（深さ0）** | 「今すぐ畳め」の指示。system では埋もれる |
| 【今回の応答】（会話劇の話者指定） | system | **末尾（深さ0）** | そのターン限定の指示 |
| 続き生成の念押し | 末尾 | 末尾（変更なし） | 既に正しい |

### 3.3 実装上の決定

- **深さ3が存在しない場合はクランプして system 直後へ**。履歴は現在シーンに絞られている（`prompts.ts:298`）ため、
  シーン開始直後は履歴が1〜2件しかない。
  このとき効きは**弱くならず、むしろ強くなる**。`[system, m1]` に挿入すると `[system, X, m1]` ＝
  X の後ろは1件だけ＝**実質深さ1**で、定常時の深さ3より生成点に近いからだ（§0 の近接優位）。
  つまり挙動は「**シーン序盤は深さ1〜2相当で強く、履歴が伸びると深さ3に落ち着く**」。
  深さ3に載るのは状態拘束文と `authorNote` だけ（締めのナッジは末尾＝深さ0）なので、
  序盤に拘束文が強めに効くのは害が無い——**そのまま受け入れる**。
  なお §4 で原文窓を複数シーンへ広げると「シーン開始直後は履歴1〜2件」という前提自体が消えるため、
  §7 の実装順（PC3 → PC4）ではクランプはほぼ発生しない。規則としては必要だが、実挙動への影響は小さい。
- **深さ3の中身は1通の user メッセージにまとめる**（可変ロア／状態→帰結の拘束文／`authorNote`）。
  分けると挿入点が増えて無効化の起点が前倒しになるだけで、得るものが無い。順序は
  **素材（ロア）→ 拘束（拘束文・`authorNote`）**。指示を生成点側に寄せる。
- **可変ロアを深さ3に載せる追加コストはゼロ**。深さ3はもともと毎ターン直近3件を無効化するので、
  そこへ毎ターン変わるものを同居させても無効化範囲は1トークンも広がらない。
  「可変ロアの置き場所」と「拘束文の置き場所」が同じ1つの機構で片づく。
- **ユーザーが深さを設定できる UI は作らない**。欄ごとに意図が確定しており、選ばせる必然性がない。
  またユーザーは A/B テストできないので良し悪しを判断できない。将来出すとしても `authorNote` 1箇所のみ・上級オプション扱い。
- 深さ3は毎ターン直近3件を無効化する。**原文窓を広げる（§4）と分母が増えて割合が下がる**ので、
  実装順は「並べ替え → 原文窓 → 深さ3」が影響最小。

## 4. 原文窓と畳み方

現状は「現在シーンの原文＋それ以前は要約」（`prompts.ts:298`）で、**原文の窓が1シーンしかない**。
シーンが変わった瞬間に直前まで読んでいた内容が要約1段落に潰れ、「忘れられた」体感の主因になる。

キャッシュヒット時の入力単価が十分安いモデルでは、原文を数シーンぶん載せても現実的なコストに収まる。
ただし**要約は廃止しない**——要約が担っているのは圧縮ではなく**取捨選択（saliency の付与）**だから。
`reviewSystem` の要約は「重要な出来事・関係や心情の変化・約束や未解決事項」を選んでおり、
全文を渡すと捨て台詞と約束が等価になってモデルが重要度を判断できなくなる。

### 全文送信を採らない理由（品質面）

| 悪化する側 | 内容 |
|---|---|
| 中間の希薄化 | 長文脈では中盤の情報の参照精度が落ちる。関係性・約束が散文に埋もれる |
| **指示の希薄化** | 迎合・ナッジ不発は**指示と本文の量比**の問題。全文送信はこれを最悪化する |
| 自己模倣の固定化 | モデルは自分の過去出力を強く真似る。言い回しの癖・段落構成が増幅されて抜けない |
| 矛盾の蓄積 | 過去の綻びが原文のまま残る。要約はそれを黙って洗浄している |

### 採用する構成

- **要約層（全期間）** ＝ saliency。維持。
- **原文層（直近Nシーン・トークン予算で決定）** ＝ 具体と声。目安 1.5万〜2万トークン。
- それ以前は要約のみ。

### 畳み方の4原則

1. **階段状に畳む**（1シーンずつ滑らせない）。滑らせるとシーン境界ごとにプレフィックスが壊れる。
   予算いっぱいまで一切落とさず、超えたら数シーンぶんまとめて畳む＝無効化の頻度が数分の1になる。
2. **橋を残す**。畳んだブロックの**末尾だけ原文で残す**（最後のシーン1つ、または末尾1000トークン程度）。
   一気に畳むと「ターンNでは覚えていたことをターンN+1で覚えていない」という**記憶密度の段差**が生じ、
   読者には理由が見えないぶん不気味に映る。橋があると段差が傾斜になる。
3. **シーン境界でのみ畳む**。読者が既に断絶を受け入れている場所に変化を紛れ込ませる。シーン途中で畳むのは最悪。
4. **要約は連結優先**。畳むときに複数シーンの要約を作り直すと情報が二重に失われる。
   まず既存のシーン要約を**連結するだけ**（無料・粒度も保たれる）。連結が長くなりすぎた段階で初めて上位要約へ。

## 5. レビューの遅さ

**キャッシュでは改善しない。** ボトルネックが入力（プリフィル）ではなく**出力（トークン生成）**にあるため。
レビューの出力は `summary` + `suggestions`×3 + `characterGrowth` + `worldGrowth` + `relationUpdates` + `moods`
+ `statChanges` + `counterEvents` で 1000〜2000トークン。特に `relationUpdates` は仕様として
**差分でなく現時点の全文**（`prompts.ts:441`）を要求しており、**参加キャラ数に比例して伸びる**。おそらくこれが最大要因。

採る手:

| 手 | 内容 | 判断 |
|---|---|---|
| 軽量モデル | `reviewModel` に安いモデルを充てる（既に分離可能） | **機構としては維持のみ**。「既定を軽いモデルに変える」は不採用＝ユーザーがどの接続先・どのモデルを使うか分からない段階でアプリ側が特定モデルを既定にはできない（BYOK 前提）。使うかどうかは各ユーザーの選択に委ねる |
| **ストリーミングで段階表示** | JSON は `summary` → `suggestions` → … の順に出るので、要約が出た時点でモーダルを埋め始める | **採用**。投機ゼロで体感だけ縮む |
| **2本に分割して並列実行** | 要約＋次シーン候補 / 状態変動 に分ける。壁時計時間ほぼ半分・入力コスト約2倍 | **採用・既定 ON** |
| `relationUpdates` を差分化する | 全文書き直しをやめ、変化した箇所だけ返させる | **却下**（下記） |
| 裏で走らせる（投機実行） | シーン終了を押す前に開始 | **却下**。ユーザーが続きを書けば丸ごと無駄になる |

### 最大要因に手を付けない理由

上で `relationUpdates` を「おそらく最大要因」と特定しておきながら、対策はそれ以外に置いている。
これは見落としではなく**意図した取捨**なので明記しておく。

全文書き直しは冗長性ではなく**忘却対策**として設計されている。プロンプトは
「今シーンで変化していない機微（好悪・約束）は失わず維持して書く」（`prompts.ts:441`）と指示しており、
差分方式にすると「触れられなかった機微」が回を追うごとに脱落する——**関係性 prose はこのアプリの状態エンジンの中核**で、
そこが痩せるのはレイテンシ数秒と引き換えにしてよい損失ではない。

したがって**レイテンシと状態の忠実性のトレードオフを、忠実性側に倒す**。
出力量そのものは減らさず、体感（ストリーミング）と壁時計時間（並列）で殴る。
既に効いている軽い手として「変化が無いキャラは省略可」（同 441）があるので、
実測で省略が守られていないと分かった場合はそこを強めるのが先。

### 並列/逐次の設定

取りうるのは3通りで、真ん中は消える。

| 構成 | 壁時計時間 | 入力コスト |
|---|---|---|
| ①**1本のまま**（分割しない） | 基準 | 基準 |
| ②**2本を並列** | **約半分** | 約2倍（同じ文脈を2回投入・同時なので両方ミスする） |
| ③2本を逐次 | ①とほぼ同じ | ①より増える |

③が無意味なのは「出力時間が2倍になる」からではない——**分割しても出力トークン総量は変わらない**
（1.5k が 0.75k×2 になるだけ）ので逐次の総時間は①とほぼ同じ。無意味なのは、
**時間短縮という分割の唯一の目的が消える**からで、往復が1回増えるぶんむしろ悪い
（2本目が接頭辞ヒットしても、入力が①より安くなることはない）。

よって②と①の二択。**既定は②の並列（ON）**とする。

「AIと出力」タブに真偽値1つを置き、OFF で①に戻せるようにする。

**なぜトグルを残すか（§3.3 の「深さ設定 UI は作らない」と矛盾しないか）**:
深さを却下した理由は「**ユーザーが良し悪しを判断できない**（A/B テストできない）」だった。
コストは違う——**請求書に出る＝ユーザーが直接観測でき、本人の許容額は本人にしか分からない**。
判断材料が本人の側にある設定は出してよい。線引きは「設定の多さ」ではなく
**その量をユーザーが評価できるか**にある。

コスト増分の概算（レビュー入力5k・出力1.5k・50シーン）:

| モデル | 1シーン増分 | 50シーン |
|---|---|---|
| 格安（入力$0.27/M級） | 約 $0.0014 | 約 $0.07 |
| Sonnet 級（入力$3/M） | 約 $0.015 | 約 $0.75 |

レビューは出力支配なので、入力を倍にしても総額は4割増し程度。**両端とも許容範囲**なので既定 ON で問題ない。

### 分割時の注意: 2本の推論が食い違う

現在は1回の推論が `summary` と `statChanges.reason` の両方を書くので、要約と数値の理由づけが自動的に噛み合う。
2本に割ると**別々の推論**になり、「要約では和解したことになっているのに好感度が下がっている」類のねじれが起こりうる。

対策: **分割線を「同じ事実の別表現」ではなく「独立した仕事」で引く**。

| 呼び出し | 担当 |
|---|---|
| A | `summary` / `suggestions` / `characterGrowth` / `worldGrowth` |
| B | `relationUpdates` / `moods` / `statChanges` / `counterEvents` |

A は「何が起きたか」、B は「状態がどう動いたか」。両者は**同じ本文**を読むので事実の齟齬は出にくく、
ねじれが出るとしたら解釈のレベルに限られる。`summary` と `statChanges` を別々の呼び出しに割るこの形が、
2分割としては最も干渉が小さい。実測でねじれが目立つようなら分割を諦めて①へ戻す（既定 ON を降ろす）。

## 6. プロンプトの中身に関する決定（迎合と領分）

深さの議論と対になる、**何を書くか**の決定。ゲーム性そのものに関わる別トピック（隠し設定・失敗演出・
ダイス・ステータス減衰・`WORLD_PRESETS`）は範囲が異なるため
[`設計_ゲーム性向上バックログ.md`](./設計_ゲーム性向上バックログ.md) に分けた。

### 6.1 迎合（ユーザーに甘すぎる）対策

**プロンプトで「失敗させてよい」と許可するのは却下**。モデルは「失敗を書くべき対象」を局所的に選ぶため、
指定した行動だけ失敗して他は全部成功する不自然な偏りが出る。

採るのは**状態を帰結に接続すること**。現在の `prompts.ts:138` は

> 関係性の記述と矛盾しない態度・口調・距離感で描写してください

と**態度の話しかしていない**。応じるか拒むかという*帰結*には触れていないので、
モデルは「口調は素っ気ないが要求は全部通す」という書き方ができてしまう。ここを塞ぐ。

迎合を*好みの問題*から*整合性の問題*に変えるのが狙い。モデルは後者をかなり守る。**深さ3へ置く**（§3.2）。

ただし**文面は一意に決まらない**。強く縛れば序盤が硬直し、緩めれば効かない。
一発で当てにいかず、下の5案を実測して決める。

#### コールドスタート問題（初期案の欠陥）

当初案は「関係が浅い段階で本人が同意しないことは、頼まれても起きない」だったが、これは**そのままでは採れない**。

セッション冒頭は関係値が初期値・関係性 prose も空で、**あらゆる関係が「浅い」判定になる**。
そこへ禁止形の拘束を毎ターン深さ3で打ち込むと、1シーン目が「何を持ちかけても断られる」状態になる。
しかも §2.3 のとおり数値が動くのはレビュー＝シーン境界だけなので、**緩むまで数シーンかかる**。
「自己中和的だから過干渉にならない」（§6.2）は定常状態の話で、初期状態には効いていない。

対策は文面側で吸収する。**拒否の二値ではなく「応じる／ためらう／条件をつける／拒む」の連続**として書き、
初対面に相当する既定の距離感を含意させる。下の V2 以降はすべてこれを満たす。

#### 検証する5案

| # | 型 | 文面 | 狙い / 懸念 |
|---|---|---|---|
| **V0** | 現行（対照） | 関係性の記述と矛盾しない態度・口調・距離感で各キャラを描写してください（記述やステータスの数値はセリフに出さない）。 | 対照群。これを外すと比較にならないので必ず一緒に回す |
| **V1** | 禁止・非対称 | 応じるかどうかは各キャラの現在の関係性から決まります。関係が浅い段階で本人が同意しないことは、頼まれても起きません。 | 当初案。**効きの上限を測る用**。拒否側しか言っていないので序盤硬直・拒否ループが出るはず |
| **V2** | **帰属・対称（本命）** | 求めに応じるか、ためらうか、条件をつけるか、拒むかは、そのキャラの現在の関係性と気分から決まります。関係が育っていれば自然に応じ、まだ浅ければためらいや条件がつきます。**ユーザーがそう望んだから、という理由だけで態度を決めないでください。** | 「誰が決めるか」だけを縛り、結果は縛らない＝§6.2 の領分に正確に収まる。応諾も拒否も同じ規則から出るので自己中和が文面に内蔵される。最終文が迎合そのものを名指しする |
| **V3** | 反応描写・分離型 | ユーザーの働きかけには、まずそれを受け取った各キャラの反応を描いてください。求められた結果がそのまま起きたことにはせず、その人物が現在の関係性のもとで実際にどう応じるかを書きます。 | 海外実践の「行為と帰結の分離」の日本語版（§6 の表・ゲーム性文書 §6）。命令口調にならず文体が荒れにくい反面、**拘束は最も弱い**と予想 |
| **V4** | 段階列挙 | 応じるかどうかは関係性から決まります。ほとんど知らない相手には警戒と社交辞令、打ち解けた相手には気を許した態度、深い関係の相手には迷いのない受容——という段階があり、段階を飛び越えた反応は書かないでください。 | **上限の測定用**。最も強いが「どの段階で何が起きるか」を決めており、**§6.2 の線を越えて作者の領分に入っている**。効きが V2 と大差ないなら採らない |
| **V5** | 義務否定・一人称 | 各キャラは、ユーザーの求めに応じる義務を負っていません。応じるかどうかはその人物自身が、現在の関係性・気分・立場から判断します。 | SillyTavern の `{{char}} is not obligated to comply.` に状態接続を足した形。assistant としての癖を役割で上書きするので効きやすいが、**全体に冷たくなる**懸念 |

**事前の見立て**: V2 を本命に、V1（上限・強すぎ側）と V3（下限・弱すぎ側）を両端に置いて挟む。
V4 は領分を越えているので、効きが V2 を明確に上回った場合にのみ「作者の領分へ（`authorNote` の既定文の一部として）」移して採用する。
V5 は V2 と組み合わせられる（義務否定＋帰属）ので、単独で負けても部分採用の余地がある。

#### 検証手順

**セーブロードのチェックポイント機構をそのまま A/B に使う**
（[`設計_セーブロードと分岐.md`](./設計_セーブロードと分岐.md)）。同一の復元地点から同一入力を投げれば、
文面以外の条件が揃う。

1. 検証用セッションを2つ用意する。
   - **S-cold**: 1シーン目・関係値すべて初期値（コールドスタート測定用）
   - **S-warm**: 数シーン進んで関係性 prose と数値が育った地点
   さらに**全員が好意的な世界観**を1つ用意する（自己中和の確認用。ここで拒否が増えるなら文面が過干渉）。
2. 各案 × 各地点で、**同一の入力3種**を投げる。
   - ①**浅い関係で踏み込んだ求め**（下げたいのはここだけ）
   - ②**関係相応の妥当な求め**（通らなければ過剰拒否）
   - ③**関係が深い相手への求め**（拒まれたら明確な失敗）
3. 各セル N=5。温度は既定のまま（本番条件で測る）。

**指標**（①〜③の別に記録）:

| 指標 | 望ましい方向 | 失敗の見え方 |
|---|---|---|
| 無理筋の即時受容率（入力①） | **下げる** | V0 が高いはず。ここが下がらない案は不採用 |
| 過剰拒否率（入力②③） | 上げない | V1/V4 で上がると予想 |
| 序盤の会話進行（S-cold） | 止めない | 「断られて話が進まない」＝コールドスタート失敗 |
| 文体の劣化 | 出さない | 「関係性が浅いため」等、**仕組みが地の文に漏れる**のが典型。数値の露出も含む |
| 好意的世界での余計な拒否 | 出さない | 出たら自己中和が成立していない＝領分を越えている |

4. **PC4（深さ注入）を待たずに測れる。** V0 の位置（`prompts.ts:138`・system 内）で文面だけ差し替えれば
   文面どうしの比較は成立する。深さの効果は文面が決まった後に**別の1変数として**測る。
   同時に2つ動かすと、負けたのが文面なのか位置なのか分からなくなる。

**採用条件**: 入力①の受容率が V0 より明確に下がり、かつ入力②③の過剰拒否と S-cold の進行が
V0 と同等——を満たす案のうち、**最も文面が短いもの**を採る（深さ3は毎ターン再送されるため）。
どれも満たさない場合は §6.2 のとおり**システム側は V0 のままにして `authorNote` の既定文（作者の領分）に寄せる**。
システムが肩代わりしないことは敗北ではない。

### 6.2 システムの領分と作者の領分

線引きは「どれくらい踏み込むか」ではなく**主張の種類**で引く。

| 領分 | 内容 | 例 |
|---|---|---|
| **システム＝媒体の文法** | ジャンルによらず真。構造的 | 出力形式／ユーザーの発言を勝手に決めない／**状態を判断材料に使う** |
| **作者＝価値判断** | 世界ごとに異なる | どれくらい厳しいか／何が失敗しうるか／拒まれることが普通か |

6.1 の拘束文は「厳しくしろ」ではなく「用意されている状態を使え」なので**構造側＝システムの領分**。
自己中和的で、全員が好意的な世界なら数値が高いのでモデルも好意的に振る舞う。過干渉にならない。

「拒む・失敗する」は価値側＝**作者の領分**で、置き場所は既にある（`World.startPreset.authorNote`）。
**境界線はデータモデル上に既に引かれており、問題は `authorNote` が弱すぎる場所に注入されていて機能していなかったこと**。
深さを直せば作者の領分が実際に使えるようになり、だからこそシステムが肩代わりする必要がなくなる。

**既定文の扱い**: 新規世界観の `startPreset.authorNote` に**書かれた状態で置き、消せるようにする**。
変更不能な既定＝押し付け、空欄＝誰も書かず迎合したまま、の中間を採る。

### 6.3 プロンプトの言語 — 日本語で統一する

内部プロンプト（`prompts.ts` の全 system / nudge / 拘束文）は**日本語のまま維持する**。英語化しない。
現状すでに全文日本語なので、これは**現状の追認と、今後ぶれさせないための明文化**。

根拠を強い順に:

1. **出力言語と一致させる。** 生成物は日本語の小説文。指示を英語で書くと、モデルが指示側の言語に
   引きずられて英語混じりの応答や英語の思考漏れを出す事故が起きる。特に本アプリは
   `narrativeStyle` や `structuredOutput` で**出力の形を細かく縛っている**ので、言語の揺れは形式崩れに直結する。
2. **プロンプトの半分は作者が書いた日本語。** `description` / ロア / キャラ定義 / `authorNote` / `reviewGuidance` は
   すべて日本語で入ってくる。骨組みだけ英語にすると**恒久的に混在**し、どちらの言語で答えるべきかの手がかりが濁る。
   骨組みが少数派の言語になる構成にメリットが無い。
3. **形式指示が日本語の組版そのもの。** 「セリフは鉤括弧「」で示す」「行頭を @名前 にする」「地の文」——
   これらは英語に置き換えると指示対象を言い換える手間が増え、かえって曖昧になる（`prompts.ts:268-276`）。
4. **トークン数の不利は、この文書の施策で消える。** 日本語は同じ内容でも英語よりトークンを食うが、
   骨組みは T1＝**キャッシュに最も乗りやすい層**（§2）。PC1 が効けば、まさにこの部分が繰り返し課金されなくなる。
   キャッシュを整えると決めた以上、骨組みの言語をコストで選ぶ理由は無い。
5. **BYOK なのでモデルを特定できない。** 「英語のほうが指示に従う」はモデル依存の主張で、
   ユーザーがどのモデルを挿すか分からない本アプリでは**検証も保証もできない賭け**になる。
6. **作者がプロンプトを読める。** 本アプリは作者にプロンプトを見せる方向（画像起案の `draftContext` 等）にある。
   日本語なら作者が自分の `authorNote` と地続きに読める。

**例外（英語のまま維持するもの）**: **JSON のキー名・スキーマ**（`summary` / `relationUpdates` / `statChanges` …）。
これらは自然言語ではなく識別子で、コード側の型と1対1に対応する。日本語キーにすると
JSON 生成が不安定になりやすく、型との二重管理も生む。**自然言語＝日本語 / スキーマ＝英語**の線で固定する。

なお §3 で決めた「海外実践の用語（Author's Note・depth 等）はプロンプトに出さない」も同じ方針の一部。
**参考にするのは構造であって語彙ではない。**

> 隠し設定（`eventFired` 節・ロアの解禁条件）は本書の範囲外。
> [`設計_ゲーム性向上バックログ.md`](./設計_ゲーム性向上バックログ.md) §1 を参照。

## 7. 実装フェーズ

**依存順ではなく「確実性 × 価値」順**に並べる。当初は依存順（三層化 → … → レビュー高速化）だったが、
それだと**唯一「やれば必ず良くなる」と言い切れる項目（レビューの体感速度）が最後**に来て、
その前に推測ベースの基盤工事が5つ並ぶ。発端の不満2つ（迎合・レビューが遅い）への着手も最後になる。逆にする。

| フェーズ | 内容 | 対象 | 備考 |
|---|---|---|---|
| **PC0** | **実測**: `usage`（prompt/completion/cached トークン）をログし、R1〜R5 の実コストと現在のキャッシュヒット率を1セッションぶん記録 | `openrouter.ts` / デバッグ表示 | **本書の金額はすべて概算**（§9）。PC1・PC2 に着手する価値があるかはこれで決まる。半日 |
| **PC-A** | レビューのストリーミング段階表示＋並列（既定 ON）＋ OFF トグル | `store.ts` / `SceneReviewModal.tsx` / `SessionEditor.tsx` | §5。**依存ゼロ・リスクゼロ**で発端の不満の片方に直接効く。最優先 |
| **PC-B** | 迎合対策の文面（§6.1）— **V0〜V5 を実測して決定**。`startPreset.authorNote` の既定文（§6.2） | `prompts.ts` / `store.ts` | **PC4 を待たない**。V0 の位置（`prompts.ts:138`・system 内）で文面だけ差し替えれば効果の大半は取れる。位置の最適化は PC4 で別途 |
| **PC1** | `buildSystemPrompt` の三層化（T1/T2 の並べ替え・`alwaysOn` 以外のロアを外に出す口を用意） | `prompts.ts` | 1ファイル・型変更なし。**キャッシュ抜きでも品質に効く**（近接優位・§0）ので PC0 の結果が芳しくなくても価値は残る |
| **PC4** | 深さ注入の口を作る（末尾／深さ3）＋割り当て表どおりに移設（可変ロアを含む） | `prompts.ts` | §3.2。クランプ規則を実装。PC-B の文面をここへ移す |
| **PC-C** | `cache_control` の明示送信 | `openrouter.ts` | `ChatMessage.content` を content ブロック配列へ拡張＋`provider.kind` 分岐。**`openrouter.ts` 内に閉じ込める**。下の注記のとおり**PC3 より前に必要** |
| **PC2** | R2（選択肢）の system 差し替えを廃止し R1 と接頭辞を共有 | `store.ts:2156-2160` | 下の注記のとおり**単純な削除では済まない**。先に「削る案」と比較する。**要実測** |
| **PC3** | 原文窓をトークン予算制へ拡張＋畳み方4原則 | `prompts.ts` / `store.ts` | §4。**PC-C（と PC0 の実測）が前提**。最も体感品質を上げるが、最もコストが跳ねる |

### PC-C を「後日」から前倒しした理由

当初 `cache_control` は全フェーズの後ろ（「後日」）に置いていたが、**PC3 のコスト前提がこれに依存している**。

§4 は原文窓の拡張を「**キャッシュヒット時の**入力単価が十分安いモデルでは現実的なコストに収まる」と正当化している。
一方 §1 が書いたとおり、**Anthropic 系は明示的なブレークポイントが無いとキャッシュされない**。
つまり Claude 系を挿しているユーザーには、PC3 は「毎ターン1.5〜2万トークンを全額」として降ってくる。
物語生成でこのファミリを選ぶユーザーは少なくないはずで、しかも BYOK ＝**請求はそのユーザーに直撃する**。

したがって **PC-C なしで PC3 を出さない**。順序を入れ替えられない事情があるなら、
PC3 のトークン予算を保守的な値（現状＋1シーンぶん程度）から始めて段階的に上げる。

### PC2 の注記: 「`base.slice(1)` をやめるだけ」ではない

`choicesSystem` を落とすと、次の3つが同時に壊れる。**先に移設してから外す**。

1. **`choicesUserNudge` が system を参照している。** 文面が「**指示どおりの** JSON 配列」「**上で指定した**形式・個数を厳守」
   （`prompts.ts:347-351`）＝参照先が消えると宙に浮く。出力形式（JSON 配列のみ・10〜30字・2〜4個）と
   auto の空配列規約（`prompts.ts:329-337`）を**すべて nudge 側へ移す**必要がある。実質、
   `choicesSystem` の中身が `choicesUserNudge` に移動するだけで、総量は減らない。
2. **`auto` にはリトライが無い。** `maxAttempts = mode === 'always' ? 2 : 1`（`store.ts:2166`）。
   「本編を書き続けるリスクは既存の `maxAttempts` で吸収」は `always` にしか当てはまらない。
   auto も2回にするか、auto は現状維持（system 差し替えのまま）にするかを決める。
3. **R1 の system が JSON 出力と衝突する。** 残る system には【セリフの出力形式（厳守）】（`prompts.ts:268`）や
   執筆ルール「1回の応答で1〜3段落」（`prompts.ts:211`）が入ったままになる。「厳守」と書かれた
   散文形式の指示を抱えたまま JSON 配列を出させる形なので、**リスクは現状より上がる**。
   実測（`always` で N ターン回して抽出失敗率を比較）を通してから採用を確定する。

### PC2 の前に比較すべき対案: 「タダにする」ではなく「送らない」

本書は R2 を「キャッシュが効かない」問題として立てたが、素直に見ると
**「10〜30字の文字列を3個作るために 5〜7k トークン送っている」**問題でもある。
毎ターン走るぶん、金額では本編 R1 に匹敵し、レビューの10倍近い**最大の支出**のはず（PC0 で確認する）。

| 案 | 入力 | キャッシュ依存 | JSON 遵守 |
|---|---|---|---|
| **PC2（接頭辞共有）** | そのまま（5〜7k）。ヒット時のみ安い | **する**（プロバイダ・モデル一致が前提） | **下がる**（上記3） |
| **対案（文脈を削る）** | 1〜1.5k に固定（登場人物＋【状態（現在）】＋直近2〜4メッセージ） | **しない** | **上がる**（短く焦点の合った専用プロンプト） |

対案は**プロバイダのキャッシュ実装に一切依存せず**約8割減り、しかも PC2 が抱えるリスク3を最初から持たない。
一方 PC2 が上回るのは**キャッシュが効く場合**——そのときは選択肢が
あらすじ・ロア・関係性の全文脈をほぼ無料で読めるので、選択肢の質そのものが上がる。

つまり**どちらが勝つかは PC0 の実測次第**で、今どちらかに決めるべきではない。
キャッシュが実際に効いていれば PC2、効いていない／モデルが分かれているなら対案。
（両取りも可能: 対案で削ったうえで接頭辞も揃える。ただし削ると R1 と接頭辞が違うものになるので、
どちらか一方しか選べない。）

> `Clause` への `eventFired` 節追加は本書と独立に着手可。**むしろ本書のどのフェーズよりも先でよい**
> （小・確実・作者が組める表現力が直接増える）。
> [`設計_ゲーム性向上バックログ.md`](./設計_ゲーム性向上バックログ.md) §1 参照。

## 8. 却下・保留

| 案 | 判断 | 理由 |
|---|---|---|
| 本文全体を毎ターン送る（要約廃止） | **却下** | コストは現実的だが、指示の希薄化・自己模倣・中間の希薄化で品質が落ちる。要約は圧縮でなく取捨選択 |
| レビューを本編と同じ接頭辞にしてキャッシュ共有 | **却下** | ①`reviewSystem` が別物・別モデルなら名前空間ごと別＝構造上ヒットしない ②仮に揃えても、モデル差し替えの8倍差のほうが支配的（§1） |
| 可変ロアを system の末尾（T3）に置く | **却下** | プレフィックス一致は messages 配列全体に効くので、system 末尾が変われば**後続の履歴が丸ごとミス**する。PC3 で原文窓を広げるほど損失が増える（§2）。深さ注入へ回す |
| 2本に分割したレビューを逐次実行 | **却下** | 出力トークン総量は変わらないので時間は1本と同等＝**分割の目的が消える**。往復が1回増えるぶん悪い（§5） |
| レビューの投機実行 | **却下** | ユーザーが続きを書けば無駄になる |
| 深さをユーザーが設定できる UI | **保留** | 欄ごとに設計で決まる。将来 `authorNote` のみ上級オプション |
| 深さ1・2・4 の使い分け | **保留** | v1 は system／末尾／深さ3 の3段階。末尾が命令的すぎると感じたら調整代として使う |
| プロンプトで失敗を許可する | **却下** | 指定した行動だけ失敗する不自然な偏りが出る（§6.1）。詳細は `設計_ゲーム性向上バックログ.md` §2.2 |
| `relationUpdates` の差分化 | **却下** | 全文書き直しは冗長性ではなく忘却対策。差分にすると触れられなかった機微が回ごとに脱落する（§5） |
| 内部プロンプトの英語化 | **却下** | 出力が日本語・作者入力も日本語・形式指示が日本語の組版そのもの。トークン数の不利は T1 がキャッシュに乗れば消える（§6.3） |
| 迎合対策の文面を一発で決める | **却下** | 強すぎれば序盤硬直・弱すぎれば効かない。V0〜V5 を実測して決める（§6.1） |

> ダイス判定・ステータスの自然減衰（`decayPerScene`）・`WORLD_PRESETS` の扱いも同じ検討で結論が出ているが、
> ゲーム性の話なので [`設計_ゲーム性向上バックログ.md`](./設計_ゲーム性向上バックログ.md) §3 / §2.4 / §4 に置いた。
