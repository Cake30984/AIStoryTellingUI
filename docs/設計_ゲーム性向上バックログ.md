# 設計_ゲーム性向上バックログ

「同人ゲー・エロゲと比べて何が足りないか」の検討から出た**ゲーム性の候補**と、その採否。2026-08-02 合意・**全項目未着手**。

本書は確定した実装計画ではなく、**優先度つきの候補と却下理由の台帳**。
プロンプトの注入位置・キャッシュ・迎合対策そのものは範囲が異なるため
[`設計_プロンプト構造とキャッシュ.md`](./設計_プロンプト構造とキャッシュ.md) に分けてある。

検討の発端は3つの指摘だった。

1. **作家が仕込んだ驚きの不足** — LLM 即興はプレイヤーに迎合しがちで、プレイヤーが知らない秘密を保持できない
2. **難易度・失敗の不在** — リソースが尽きる／選択を誤ると悪化する、という緊張がコード側で担保されていない
3. **判定（ダイス）の不在** — 不確実な行為判定が無い

結論を先に書くと、**1は採用（ただし提案とは別の形）・2は保留・3は却下**。

## 1. 作家の仕込み

### 1.1 `eventFired` 節（最優先・本書で最も価値が高い）

現在 `Clause` は4種しかない（`types.ts:165`）。

```
stat / counter / achievement / group
```

このため **「あのイベントが起きた後」を条件に書けない**。実績は「達成した」という結果しか表せないので、
作者が組みたい「A を見た後に B が解禁される」という**連鎖＝シナリオグラフ**が表現できない。

`Session.usedEventIds` は既に永続化されている（`types.ts:634`）ので、追加はごく小さい。

```ts
| { kind: 'eventFired'; eventId: string; have: boolean }
```

- 実装量: 節1つ＋`evalCondition` に1分岐＋`ClauseRow` に1行。
- **条件エンジンは実績・エンディング・特別イベントで共有されている**ため、1箇所の追加で3機能すべてが同時にグラフを組めるようになる。
- ADR-1 の「発火はコード判定」の直系。LLM に何も頼まないので壊れない。
- 作者体験のハードルはほぼ上がらない。条件エディタの選択肢が1つ増えるだけで、既存の文章形 UI（`OP_LABELS`／`.clause-joint`）でそのまま書ける。

### 1.2 ロアの解禁条件（1.1 の応用）

`LoreEntry` に `Condition` を持たせ、**未達なら system に注入しない・達したら注入＋発見ログへ**。

現状 `selectLoreEntries`（`lorebook.ts`）はキーワード一致だけで注入可否を決めており、
作者が「まだ明かしたくない設定」を書く場所が無い。ここを塞ぐ。

**ハードルへの配慮**: 「秘密ロア」という第二の概念を新設しない。**既存のロア1行にオプション欄が1つ増えるだけ**にする。
概念が増えないので、使わない人には何も見えない。

### 1.3 却下: 「知っているが明かすな」型のシークレットロア

秘密を system に入れたうえで「まだ明かすな」と指示する方式は**採らない**。

- LLM は漏らす。あるいは逆に禁止語へ引き寄せられて不自然にほのめかす。どちらも頻発する。
- プロンプト調整で潰そうとすると工数が青天井。
- **注入しなければ漏れない**。1.2 の方式なら LLM に秘密保持を要求しないので、事故が原理的に起きない。

失うのは「秘密を知ったうえでの巧妙な伏線」だが、**「作家が仕込んだ驚き」の実体は
"明かすタイミングを作者が握っていること"** であって、モデルの繊細なほのめかしではない。1.2 で目的は達せられる。

## 2. 失敗と難易度

### 2.1 前提: 2つの別々の軸を混同しない

| 軸 | 扱う問題 | 例 |
|---|---|---|
| **局所的な帰結の妥当性** | 1ターン内。「ユーザーがやったことは、だいたい狙いどおりになる」 | 迎合 |
| **大域的な資源圧** | セッション全体。「締め切り・枯渇が無い」 | 緊張感の不足 |

どちらも「緊張」と呼ばれるが、前者は*一手一手の手応え*、後者は*締め切り*で、**片方を直しても他方は埋まらない**。

前者（迎合）への対策は**プロンプト構造の問題**なので
[`設計_プロンプト構造とキャッシュ.md`](./設計_プロンプト構造とキャッシュ.md) §6 に置いた。本書は後者を扱う。

### 2.2 却下: プロンプトで「失敗させてよい」と許可する

- モデルは「失敗を書くべき対象」を**局所的に選ぶ**。結果、指定した行動だけ失敗して他は全部成功する不自然な偏りが出る。
- 効かないか、暴れるかの二択になりやすく、うまい文面を探すコストが高い。
- そもそも**「厳しさ」は世界ごとの価値判断＝作者の領分**であり、システム既定に入れるのは過干渉
  （領分の線引きは `設計_プロンプト構造とキャッシュ.md` §6.2）。

### 2.3 迎合が固定化する構造（本書で新しく特定した問題）

単発の迎合よりも、**それが状態に焼き付く経路が閉じていない**ほうが深刻。

```
本編が甘い
  → レビューは「実際に起きた結果」を読むので甘く採点
  → ステータス・関係性が上がる
  → 【状態（現在）】が「好意的」になる
  → 本編がさらに甘い
```

数値が**単調増加しかしない**ため、このループを断ち切る機構がコード側に無い。

### 2.4 保留: ステータスの自然減衰（`decayPerScene`）

`StatDef` に「シーン/日ごとに N 減る」を持たせ、資源が枯渇したら既存の条件エンジンでバッドイベント・
バッドエンドを撃つ、という案。

| 観点 | 評価 |
|---|---|
| 偏りが出ないか | 出ない。**コードが全域に一律で**適用するので、2.2 のような局所的な偏りは原理的に起きない |
| プロンプト工数 | ゼロ。本編プロンプトへの追加が要らない |
| **新規性** | **低い**。`World.reviewGuidance` は毎回そのままレビュー system へ注入され、「条件つきの方針は現在のステータス・日付・本文から判断する」と明記済み。**作者が「毎シーン体力を減らす」と書けば近いことは今でもできる** |
| 差分 | ①決定性（LLM 任せでなく必ず減る）②可視性（プレイヤーが読める時計になる） |

**判断: 保留。** 新しい表現力ではないので単独の目玉にはならない。
導入するなら理由は「緊張感を出す」ではなく **2.3 のループを機械的に断つこと**に置く。

## 3. 判定（ダイス）— 却下

「選択肢に `check:{stat, difficulty}` を付け、コードが乱数で成否を決めてから結果を本編プロンプトへ注入する」案。

### 3.1 却下理由

| 理由 | 内容 |
|---|---|
| **仕込みにならない（決定的）** | **選択肢は AI が生成している**（`choicesSystem`）。作者が書いたものではないので、`difficulty` を決めるのも AI になる。「作家が仕込んだ難所」ではなく**ただの AI 由来の乱数**にしかならず、1章の目的をまったく満たさない |
| 既存の決定と逆行 | `Choice.effects` は FB7-C で廃止済み（評価はシーン終了レビューに一本化）。選択肢へメタデータを戻すのは逆方向 |
| 可視ダイスの妥当性 | デジタルで乱数を見せる表現は、アナログゲームの移植以外ではほぼ廃れている。プレイヤーは「運が悪かった」より「準備が足りなかった」で負けたい |
| モデルに振らせる方式 | 出目が偏り、結果を都合よく解釈する。海外コミュニティでも評判が悪い |

### 3.2 ただし救うべき部分

ダイス案の中で価値があるのは乱数ではなく、**「結果をコードが先に決めて、本編プロンプトへ成否を注入する」機構**のほう。
LLM の忖度を排するという指摘自体は正しい。

将来やるなら**乱数ではなく状態で決める**形にする。作者が世界観側に難所を仕込み（例: 信頼60以上）、
コードが判定して結果を本文へ注入する。これは実質「条件エンジンの判定結果を本編プロンプトへ流す」ことなので、
**§1 の `eventFired` と同じ土台に乗る**。ダイスとして単独で作る理由は無い。

## 4. 初期素材の入口（`WORLD_PRESETS`）

### 4.1 実体の確認

`WORLD_PRESETS`（`store.ts:916`）の中身は次だけ。

```
{ id, label, aspects: string[], stats: [...], counters: [...] }
```

例: 恋愛 = `aspects:['信頼','恋愛']` / `stats:[好感度]` / `counters:[デート回数]`。
**description もロアもエンディングも登場人物も入っていない。**

つまりこれは**サンプル世界観ではなく、関係次元とステータスの初期スキーマ**。
「手本はカセットが担う」という認識は正しいが、`WORLD_PRESETS` はそもそも手本として競合していない。

### 4.2 何を防いでいるか

`relationAspects` が空のまま遊ぶと**レビューが劣化する**。`prompts.ts:396`:

> 次元未定義のため relationUpdates.aspects は空配列にし、stance のみ更新する

関係性の機微が `stance` の1〜2文だけになり、このアプリの中核である状態エンジンが半分死ぬ。
プリセットが実際に防いでいるのは手本の不在ではなく、**空設定のまま遊び始めてしまうこと**。

### 4.3 判断

- **3ジャンル（恋愛/RPG/経営）に分ける必要は無い。** 恋愛でも RPG でも「信頼」は要るし、好感度は汎用。
- **中立な既定1つ**（信頼＋好感度あたり）を新規世界観に入れておけば、**プリセット選択という UI ごと消せる**。
  選ばせないほうが簡単で、作成のハードルも下がる。
- 維持コスト自体は小さい（コード20行程度）ので、急いで消す理由は無い。

### 4.4 前提条件: 複製の導線が無い

「たいていの人は既存を編集することから始める」という前提を採るなら、**それを可能にする経路が現状無い**。

- `importCassette` は棚に積むだけ
- `playCassette` はセッションへ複製するだけ
- **カセットの中の世界観・キャラをライブラリへ取り出す経路が無い**

`WORLD_PRESETS` の廃止は、**「中立な既定1つ」＋「カセット/既存世界観から複製して編集する導線」とセット**で初めて意味を持つ。
単体で消すと、初回起動時に空の10セクションを前にした新規ユーザーが取り残される。

## 5. 事業判断: 難易度でカセット購入を動機づけるか — 却下

「作成が難しければ、作れない人が完成品カセットを買う動機になるのでは」という案。
（マネタイズ本体は [`公開計画_マネタイズと配布.md`](./公開計画_マネタイズと配布.md)）

| 理由 | 内容 |
|---|---|
| **作り手が集客導線そのもの** | 「カセットが唯一の集客導線＝ツクール構造」と整理済み。作れる人が減れば宣伝してくれる人が減る。買い手を増やすために作り手へ課税する形になり、成長方向と逆 |
| リピートしない | 人がツクール製ゲームを買うのはエディタが難しいからではなく、*エディタが簡単でも面白いゲームを作るのは難しい*から。難解さで買わせると、買った後に改造できず2本目の動機が生まれない |
| 線引きが増える | 既に無料/有料の線引きと抜け道7件を抱えている。そこへ「難易度による差別化」という別軸を足すと設計も説明も破綻しやすい |

### 正しい形: 下限ではなく上限を上げる

- **下限を上げる**（作りにくくする）＝却下
- **上限を上げる**（上手い人がはっきり良いものを作れる）＝採用してよい

既定は自動で誰も意識せず、こだわる作り手だけが手を入れられる余地がある——結果として
市販カセットが「自作より明らかに良い」状態になれば、購入動機は自然に立つ。
`設計_プロンプト構造とキャッシュ.md` の深さ注入を**ユーザー設定にしない**判断は、この原則と整合している。

## 6. 参考: 海外コミュニティ（SillyTavern / AI執筆界隈）の迎合対策

§2.2 の判断根拠。**効果が確認されているものはほぼ「文面」ではなく「注入位置と役割分担」の話**だった。
（各項目の細部は伝聞ベース・要検証）

| 手法 | 内容 | 本アプリでの扱い |
|---|---|---|
| **深さ指定の注入** | Author's Note を末尾から N メッセージ目に差す（実務値 2〜4）。World Info も position/depth/role を項目ごとに選べる | **採用**（`設計_プロンプト構造とキャッシュ.md` §3）。ただし用語は出さない |
| 行為と帰結の分離 | `Describe the attempt and the world's reaction, not the outcome the user intended.` 許可を与えるのでなく短絡を禁じる | 採用（従）。単独では根拠が無く薄まる |
| NPC の自律性 | `{{char}} is not obligated to comply.` 等。assistant としての癖を役割で上書き | 本アプリは**関係性 prose と数値で根拠を与えられる**ので、一般論より強い形が採れる（同 §6.1） |
| Prefill | 応答の書き出しを先に固定し、モデルに整合を取らせる | 未検討。`streamChat` は assistant prefix を送れないので要改修 |
| adjudicator パス | 本編とは別に「成功したか」だけ答えさせる呼び出しを挟む | §3.2 の将来案と同じ発想 |
| アンチ slop | 禁止フレーズ・logit bias | 迎合ではなく文体の話。未検討 |
| モデルにダイスを振らせる | あちらでも評判が悪い | §3.1 と同じ結論 |
