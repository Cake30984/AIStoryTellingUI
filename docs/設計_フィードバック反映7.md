### 選択式質問の結果（2026-07-19 合意）

- **Q1 ポイントの確定タイミング = レビュー時評価に一本化**（推奨案どおり）。選択肢の事前 effects（P5）を廃止し、選択肢経由・自由入力の独自行動を問わず「実際に起きた結果」をレビューが評価して加点。却下: 生成時決定＋選択後開示（評価経路の二重化・展開を無視した固定点）
- **Q2 変動幅 = 定義ごとの数値**。ただし**最小〜最大の範囲指定**とし、その間で柔軟に配分させる（ユーザー回答による拡張）。加えて**世界観のレビュー指針欄**（自由記述）を新設——「毎シーン必ず体力を消耗」「呪い中は大きく・弱まったら小さく」等の方針をレビューへ毎回注入する。指針の条件分岐は「レビューが観測できる事実（日付・フラグ・現在値・本文）」に紐づけて書けば機能する。LLM 判断なので厳密保証はなく、機械的保証が要る場合の**条件付き自動変動ルール**（コード実行）は発展案として記録（今回は見送り）
- **Q3 ツリー行クリック = 移動**（推奨案どおり）。「↩ 戻る」ボタン廃止・⋯「この時点に戻す」へ
- **Q4 同一キャラ束縛 = 全条件で統一し、さらに拡張**（ユーザー回答による拡張）: 単なる束縛でなく、**条件を満たしたキャラの組ごとにイベント・実績・エンディングが独立に存在する**モデルへ。「A と3回デート→A のイベント、後日 B と3回デート→B でも同じイベント」。複数人条件は「相手1・相手2」のキャラ変数で区別。名前は `@相手1` 置換で表示

## FB7-A: 即効修正（画像ズーム・表記統一・方向付けテンプレート）

### ②-1 バグ修正: 拡大画像がサムネイル CSS に潰される

原因: `ZoomOverlay` は呼び出し元（`GalleryThumb`/`RecordThumb`/`BackgroundThumb`/`IllustrationView` 等）の JSX 内に描画されるため、`.job-thumb img { width:160px; height:160px; object-fit:cover }`（panels.css）などの**祖先由来の img セレクタが拡大画像にマッチ**する。インライン指定は max-width/max-height のみなので width/height 160px が勝ち、「小さい正方形クロップ」になる。

修正:

- `ZoomOverlay` を `createPortal(document.body)` で描画（コンテナ CSS・stacking context から独立。`useModalEscape` は据え置き）
- 専用クラスを与える: `.zoom-overlay`（overlay 全画面・中央寄せ）/`.zoom-overlay-img { max-width:92vw; max-height:88vh; width:auto; height:auto; object-fit:contain }`。キャプション版も同構造（画像の下に `.zoom-caption`）
- 防御として `.job-thumb img` → `.job-thumb > img` に絞る（同種の内包事故の再発防止）

### ②-2 機能追加: 等倍ズームトグル

- 既定=フィット表示（画像全体が見える）。**画像クリックで等倍（natural size）⇔フィットをトグル**。等倍時は overlay を `overflow:auto` にしてスクロールで見る（カーソルは `zoom-in`/`zoom-out`）
- フィット時に画像クリックで閉じる現仕様は「背景クリック・Escape で閉じる」に統一（キャプション版と挙動を揃える）
- ホイール倍率・ドラッグパンまでは作らない（過剰。等倍＋スクロールで用は足りる）

### ④ 表記統一「スタット」→「ステータス」

- `WorldEditor.tsx:90` ClauseRow の `<option value="stat">スタット</option>` → 「ステータス」
- `WorldEditor.tsx:1090` 実績の説明文「スタット・カウンター・…」→「ステータス・カウンター・…」
- UI 文言はこの2箇所のみ（grep 済み。コード内コメントは対象外）

### ⑦ 最初の方向付けを開始テンプレートへ

- `WorldStartPreset.initialDirective?: string` を追加（optional・persist キー据え置き）
- `startPresetPatch`（store.ts）: story モードの他項目と同じ規則でコピー（空欄のみ／overwrite 時は全上書き）
- WorldEditor「開始テンプレート」節: 導入欄の直後に「最初の方向付け」textarea（説明は SessionEditor と同文: 最初のシーンに滞在している間だけ AI に渡す非表示の指示）
- カセットは `session.story.initialDirective` を直接持つため既対応。世界カード PNG（`aist_world`）は World を丸ごと焼いていれば自動追従——`cards.ts` がフィールドを白リストしていないか実装時に確認する

### 検証

- `npx tsc --noEmit` → `npm run build`
- preview_eval: `startPresetPatch` が initialDirective を空欄時コピー／入力済み保持／overwrite 上書きすること
- ユーザー確認: ①ギャラリー・ジョブ・挿絵のクリック拡大が全体表示＋クリック等倍になる ②非正方形画像が切れない ③条件エディタの表記 ④世界観の開始テンプレートに方向付けを書く→新規セッションで世界を選ぶとコピーされる

## FB7-B: 分岐ツリーの履歴リンク化（①）

### 挙動（合意仕様）

1. **行クリック＝その地点を本文で開く**（ナビゲーション。何も消さない・確認なし）
   - ノードが現在パス上（currentId の祖先 or 自身）: 復元せず、本文の該当メッセージへスクロール＋数秒ハイライト。属するシーンが畳まれていれば展開してから
   - ノードが現在パス外: **そのノードが乗る線の先端**（後述 `lineTipOf`）を `restoreCheckpoint` で読み込み → 該当メッセージへスクロール。復元は FB6-C 以降「読みに行くだけの移動」で安全（上書きの確認・削除は次の物語操作時に `ensureLineTip` が行う）
2. 分岐を作る操作は**本文の操作行**（⑂ 分岐・ここから・編集・削除）に集約（FB6-C のまま）。ツリーは「読む・移動する」装置
3. hover の「↩ 戻る」ボタンは廃止し、行 hover は「→ 開く」表示（行クリックと同じ）。⋯ メニューに「**↩ この時点に戻す**」（従来の `restoreCheckpoint`＝その時点より先を読み込まない。確認文は現行のまま）を追加。「⑂ ここから分岐して再開」「このシーンの開始前に戻る」「この分岐を削除」は従来どおり
4. しおりタブの「ここに戻る」は従来どおり復元（セーブポイントに戻る明示動線）
5. 生成中（streaming/choices/review）は復元を伴う移動は不可（現行 restore と同条件）。現在パス上のスクロールのみは常時可

### 実装

**線の先端の決定** — 純関数 `lineTipOf(tree, nodeId): string`（BranchTreeModal か store。export・検証用）: `nodes` 配列順で「最初の子」を辿り続けて到達する葉。`buildGraph` のレーン継承（最初の子が親レーンを継ぐ）と同じ規則なので、**クリックした行が乗っているレーンの末端**と視覚的に一致する。別の枝に行きたければその枝の行をクリックすればよい（枝の行は別レーンにある）

**アンカーの解決**: `node.anchorMessageId`（FB3-B1 以降の全ノードにある）→ 無い旧ノードは対象ノード自身のスナップショットを読んで末尾メッセージ id（クリック時1回の追加読込）→ それも無ければスクロールなしで末尾へ。編集・削除で先端側から消えたメッセージ id は「見つからなければ末尾へ」で吸収

**store**: 非永続 state `scrollTarget: { sessionId: string; messageId: string; seq: number } | null` ＋ アクション `navigateToNode(sessionId, nodeId)`（現在パス判定 → 必要なら `restoreCheckpoint(lineTipOf(...))` → `scrollTarget` セット）。`partialize` から除外

**ChatPanel**: `renderMessage`/`renderNovelMessage` の各ルート要素に `data-msg-id={m.id}` を付与。`scrollTarget` を購読する useEffect で ①メッセージの属するシーンが畳まれていれば `expanded` に追加 ② rAF 1〜2フレーム後に `querySelector([data-msg-id])` → `scrollIntoView({ block:'center' })`＋`.msg-flash` クラスを約2秒 ③ `scrollTarget` をクリア。復元直後の「末尾 user メッセージへの自動スクロール」より**後に**消化して勝たせる。マーカー等で DOM に無い id は直前の描画メッセージへフォールバック

**BranchTreeBody**: 行本体（`.bg-body`。ボタン類を除く）のクリックで `navigateToNode`。`doRestore` の確認ダイアログは ⋯「この時点に戻す」専用に残す

### 検証

- tsc → build。preview_eval: `lineTipOf` を合成ツリー（直列・分岐あり・クリック行がレーン途中/先端/ルート）で直叩き。`navigateToNode` の「パス上=復元なし／パス外=先端へ復元」を state 遷移で確認
- ユーザー確認: ①現在分岐の過去ノードをクリック→ページがその場面へスクロール（分岐は増えない） ②別の線の行をクリック→その分岐の本文全体が読め、クリック地点にスクロール ③そこから⑂・ここから等で初めて上書き/分岐の確認が出る ④⋯「この時点に戻す」が従来挙動

## FB7-C: ポイントのレビュー確定一本化＋変動幅＋レビュー指針（③）

### 決定

- 加点・変動は**シーン終了レビューの statChanges/counterEvents に一本化**。選択肢の事前 effects（P5）は廃止
- 定義ごとに**1回のレビューあたりの変動幅（最小〜最大）**を指定でき、プロンプトの目安＋コードのクランプ両方に使う
- 世界観に**レビュー指針**（自由記述）を新設し、状態変動の方針をレビューへ毎回注入する

### データ・プロンプト

- `StatDef.deltaMin?: number` / `StatDef.deltaMax?: number` — 変動させる場合の1回あたりの絶対値の下限/上限。未設定側は拘束なし（従来の ±1,000,000 安全クランプのみ）。「変動しない（delta 0＝項目を出さない）」は常に許される＝deltaMin は「動かすなら最低これだけ動く」の意味
- `CounterDef.amountMin?: number` / `CounterDef.amountMax?: number` — 同様（1..1000 の既定範囲内でさらに絞る）
- `World.reviewGuidance?: string` — **レビュー指針**。シーン終了レビューの system に【世界のレビュー指針】として毎回そのまま注入する世界固定の方針文（例: 「体力は毎シーン必ず消耗させる。関係フラグ『呪い』が立っている間は10〜20、外れていれば1〜5」）。条件分岐は「レビューが観測できる事実」（現在のステータス/カウンター値・関係フラグ・日付・本文の描写）に紐づけて書けば機能する。**LLM 判断なので厳密保証はない**（min/max クランプで暴走は抑制）。厳密な機械的保証が必要になったら「条件付き自動変動ルール」（`{condition, statId, delta}` をコードが毎レビュー適用）を次弾で検討（発展案・今回は見送り）
- WorldEditor: ステータス欄に「変動幅/回（最小〜最大）」・カウンター欄に「加算/回（最小〜最大）」の number 入力2つ（既存 min/max の行に並べる）。ステータス節の冒頭に「レビュー指針」textarea
- `reviewSystem`（prompts.ts）: statLine/counterLine を定義ごとの範囲付き列挙へ変更。例:「statChanges.name は既存の【好感度（動かすなら±5〜15）・所持金（±100〜3000）】のみを使う。**範囲は"そのシーンの出来事の大きさ"の物差し**であり、平凡なシーンは下限寄り、決定的な出来事では上限近くまで使ってよい」。`World.reviewGuidance` があれば指針ブロックとして注入
- **独自行動の評価を明記**: 指針に「主人公の行動は、提示された選択肢を選んだ場合も**自由入力の独自行動**も同様に、実際に起きた結果に基づいて statChanges/counterEvents に反映し、reason に行動と結果を書く」を追加
- **レビュー文脈の拡充**: レビューの user 文脈に現在のステータス/カウンター値・現在日付（タイムライン）を注入する（現状は関係性 prose のみ。指針の条件参照「呪いフラグがある間は…」「5日目以降は…」を可能にするため）
- `prepareSceneReview` の解決部（store.ts:2617-2660 付近）でクランプ: `deltaMin ≤ |delta| ≤ deltaMax`（delta≠0 のもののみ。符号維持）・`amountMin ≤ amount ≤ amountMax`。**レビュー画面での手動編集は従来どおり**（def の min/max クランプのみ。ユーザー主権）

### 選択肢 effects の撤去

- `choicesSystem` の effects 形式分岐と `statNames` 引数・`choicesUserNudge` は形式言及なしへ
- `coerceChoices` の effects 解決、`Choice.effects`/`ChoiceEffect` 型、`applyChoiceEffects` アクション、ChatPanel の加点バッジ（`choice-effects`）と `choiceLockRef`、関連 CSS を削除。旧データの `effects` は読み捨て（optional なので persist キー据え置き）
- 実績の再評価はレビュー確定（`applyReviewToState`→`unlockAchievements`）に残るため機能欠落なし
- AGENTS.md の「選択肢」「状態エンジン」記述と ADR-1（P5 の方針転換＝選択肢連動加点の廃止）を更新

### 検証

- tsc → build。preview_eval: 解決部クランプ（min 未満の引き上げ・max 超の切り下げ・0 は除外のまま・未設定時は従来上限）／`reviewSystem` 出力文字列に範囲・指針が載ること
- ユーザー確認: ①選択肢にポイントが表示されない ②レビューの 📊 で独自行動にも加点案が付く（reason に行動が書かれる） ③7日間・max100 の世界で 5〜15 を設定→1シーンの変動が実際に大きくなる ④レビュー指針（体力消耗）が毎レビュー反映される

## FB7-D: 条件エンジンのキャラ変数化（⑤⑥）

### 意味論（合意仕様）

**キャラ変数**: 条件の節のうちキャラ系の節（`stat`/`counter` の scope=character・characterId 未指定、`relationFlag` の fromId 未指定）は**キャラ変数（相手1・相手2・相手3）**のいずれかに属する（既定=相手1）。条件の評価は「参加キャラから変数ごとに**相異なる**キャラを割り当てる組み合わせ」を試し、**すべての節が成立する割り当てが存在すれば成立**。成立した割り当て（変数→キャラ）がその発火の「当事者」になる。

- 現行の「節ごとに独立していずれかのキャラ」は、A の好感度と B のフラグの合成で成立してしまうため廃止。**既存ワールドの成立タイミングが変わりうる**（厳しくなる方向）
- `any` 条件は従来どおり節単位（成立した節の割り当てを当事者に）
- global 節・characterId 明示節は変数と無関係に従来どおり
- 適用範囲は**条件エンジン全体**（エンディング・実績・特別イベント・ScheduledEvent.condition）

**キャラの組ごとの独立発火**（⑤の本体）: 「3回デート」を1つ定義すれば、A で成立→A のイベント/実績、後日 B で成立→B でも**同じ定義が再度**発火する。

- **実績**: 解除記録を `(defId, 当事者キャラの組)` 単位にする。`SessionState.achievements` に `characterIds?: string[]`（変数順）を追加し、同じ組では再解除しない。キャラ系の節を含まない定義は従来どおり defId 単位で1回
- **特別イベント**: 消化記録 `usedEventIds` のキーを「`eventId`（global 条件）／`eventId@charId1[+charId2]`（キャラ条件）」にする。`nextScheduledEvent` は「未消化の (イベント, 割り当て) 」を day 順・参加キャラ順で1つ選ぶ。旧データの素の eventId は「全組み消化済み」として扱う（安全側）
- **エンディング**: `checkEndings` が `{ def, partners: {characterId, name}[] }` を返す。複数の割り当てが同時成立した場合、レビューのプレビューで相手を選べる（既定=参加キャラ順の最初の割り当て）。`Session.ending` に `partners?: {characterId, name}[]` を追加し、エピローグ注入（prompts.ts 1.8）に「相手: X。この結末は X との関係の帰結として描く」を追記。`EndingRecord` に `characterIds?: string[]` を追加（周回記録で「誰との結末か」が残る。到達バッジ等の表示粒度は当面 defId 単位のまま＝キャラ別コンプ表示は将来の拡張余地）

**`@相手` プレースホルダ**（⑥）: 実績・イベント・エンディングの name / description / note / epilogueGuidance 内の `@相手1`・`@相手2`（変数が1つだけなら `@相手` も同義）を、発火時の当事者キャラ名に置換して表示・注入する。ヘルパ `bindPartnerNames(text, partners)` に一本化。適用箇所: 実績トースト・状態パネルの解除一覧・イベントのシーン注入 note・エンディング名（レビュープレビュー・完結バッジ・ツリー 🏁・エピローグ指針）

### UI（条件エディタの整理）

- ClauseRow: 種別ラベル「ステータス」（④）・定義選択肢にスコープ併記（「好感度（キャラ別）」「所持金（全体）」）。キャラ系の節に**対象セレクト「相手1／相手2／相手3」**（既定=相手1。1変数しか使わなければ従来と同じ見た目・挙動）
- エンディング・実績・イベント節の説明文を更新: 「キャラ別の条件は**同じ『相手』が全部満たしたとき**に成立し、そのキャラの名前が `@相手1` に入ります。相手2 を使うと『別のもう一人』の条件を書けます」
- 実績・イベントの一覧（StatusView 等）はキャラの組ごとの解除行を表示（「アリスと3回デート（相手1=アリス）」）

### 実装

- `Clause` に `charVar?: 1 | 2 | 3`（optional・既定1。persist キー据え置き）
- 純関数 `matchAssignments(cond, state, world, characterIds): {v1?: string; v2?: string; v3?: string}[]`（成立する割り当ての列挙・参加キャラ順・export）。`evalCondition` は「割り当てが1つ以上あるか」の互換窓口として残す
- `unlockAchievements`: defs × 割り当てで反復評価（連鎖依存の反復は現行のまま）。`achievement` 節から per-char 実績を参照する場合は「いずれかの組で解除済みか」で判定（変数束縛はしない＝単純さ優先）
- `checkEndings`・`nextScheduledEvent`・`confirmSceneReview`（イベント消化キー）・`SceneReviewModal`（相手セレクト）・トースト表示を順に更新

### 検証

- tsc → build。preview_eval: `matchAssignments` を合成 state で直叩き（同一キャラで全節成立／別キャラ分担では不成立／相手1+相手2 の2人条件・同一人は不可／characterId 明示・global 混在／any の節単位）。実績の組単位解除（A→B の順で2回解除・同じ組は1回）。イベント消化キーの新旧互換。`bindPartnerNames` の置換
- ユーザー確認: ①「デート3回」実績が A で解除→B でも独立に解除され、名前が「@相手1と3回デート」→各キャラ名で表示 ②「好感度≥70 かつ フラグ『告白』」を A だけが満たす→A とのエンディング予告・エピローグが A との結末として書かれる ③2人同時成立→レビューで相手を選べる ④相手1・相手2 の2人条件（修羅場イベント等）が別々の2人でのみ発火

## FB7-E: 発見キャラ（未定義人物の登場制御とキャラ化・⑧）

### 決定

- **登場ポリシー**: セッション設定（進行タブ）に「新しい登場人物」セレクト `newCharacterPolicy?: 'allow' | 'avoid'`（既定 allow=現状の挙動に近い）。system プロンプトに注入: allow=「既定キャラ以外の名前付き人物を自由に登場させてよい」／avoid=「名前付きの新キャラは登場させない（モブは無名のまま）」。`WorldStartPreset` にも同項目を追加しテンプレートコピー対象にする
- **検出**: 2経路を同じ採用フローに流す
  - (a) 構造化出力の行話者が未解決（参加キャラ・ペルソナ・`NARRATION_NAMES` のいずれにも `matchCharacterByName` で解決できない）→ その話者チップに **？バッジ** を表示（StructuredMessage）。クリックで「このキャラクターを定義しますか」
  - (b) シーン終了レビューに `newCharacters: [{name, note}]` を追加（非構造化・地の文だけの登場向け）。レビューモーダルにチェック式の「新しい登場人物」セクション
- **キャラ化フロー**: 承認 → LLM がキャラ JSON を起案（persona/speechStyle/appearance/greeting をここまでの transcript から。imagePrompt は空）→ CharacterEditor の draft として開き、ユーザーが確認・編集して保存
- **保存先 = ライブラリの通常キャラ**＋現在セッションの `characterIds`（と現在シーンの `activeCharacterIds`）へ追加。タグに「発見」を付ける
  - カセットから始めたセッションで発見しても **`Cassette.session` は開始時スナップショットなので不変**＝カセットは汚れない（要望どおり）
  - ライブラリに入るので、そのままカード PNG 書き出し・他セッションでの再利用が可能（要望どおり）
  - セッション内オーバーレイとしてキャラ本体を持つ案は却下: 立ち絵・配役・状態エンジン・カード化の全系統に「素材でないキャラ」の分岐が波及し複雑化する。ライブラリ直行なら既存機構がそのまま使える

### 実装

- `Session.newCharacterPolicy?`・`WorldStartPreset.newCharacterPolicy?` 追加。`buildSystemPrompt` に注入ブロック追加
- `structured.ts` は変更なし（未解決話者は既に narration 扱い）。`StructuredMessage`/`useSpeakers` で「未解決だが発言者名がある」行に ？バッジ→ ChatPanel のキャラ化モーダルを開くコールバック
- キャラ起案: `prompts.ts` に `characterDraftSystem()`（JSON: name/persona/speechStyle/appearance/greeting）＋ transcript 文脈。裏方モデルは reviewModel を流用
- `reviewSystem`/`prepareSceneReview`/`SceneReviewModal`/`confirmSceneReview` に newCharacters の提案→承認→（保存はキャラ化モーダル経由）を追加
- 生成された Character は `upsertCharacter` で保存 → `updateSession` で participants へ追加

### 検証

- tsc → build。preview_eval: ポリシー注入文字列・未解決話者の検出（参加キャラ名・別名・ペルソナ名では出ないこと）
- ユーザー確認: ①avoid 設定で新キャラが名前付きで出にくくなる ②構造化本文に未知の話者→？バッジ→承認でキャラ draft が開き保存できる ③保存したキャラがセッションに参加し立ち絵・状態が使える ④カセット本体が変わっていない ⑤レビューでも新登場人物が提案される
