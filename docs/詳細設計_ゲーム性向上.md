## 1. G1 — `eventFired` 節

### 1.1 決定事項（上位設計の未決を確定）

**v1 では当事者の組を問わない。** 節の意味は「**その定義がどれか1組で発火済みか**」。
判定は `usedEventIds` の**前方一致**（`eventUsedKey` が `eventId@charId1[+charId2]` を作るため・`store.ts:1671`）。

当事者の組まで問う版（「A と B の組で発火したか」）は節に当事者指定が要るので v1 では作らない。
**この決定は後から拡張できる**（`{ kind:'eventFired'; eventId; have; roleId? }` の optional 追加で済み、
既存データは `roleId` 未設定＝現行の意味のまま動く）。

### 1.2 型（`types.ts`）

```ts
export type Clause =
  | { kind: 'stat'; defId: string; characterId?: string; op: Op; value: number }
  | { kind: 'counter'; defId: string; characterId?: string; op: Op; value: number }
  | { kind: 'achievement'; defId: string; have: boolean }
  | { kind: 'eventFired'; eventId: string; have: boolean }   // ★追加
  | { kind: 'group'; roleId: string; quantifier: Quantifier; subject?: boolean; clauses: GroupSubClause[] }
```

`GroupSubClause` には**足さない**。group 節の下位条件は「ロールの各メンバーに課すキャラ限定条件」で、
イベント発火はキャラに紐づかない（v1 では組を問わないため）。混ぜると意味が壊れる。

**optional な union メンバの追加なので persist キーは据え置き**（クリーンブレイク方針の「optional 追加ならキー据え置き可」に該当）。

### 1.3 評価コンテキストのオブジェクト化（本書での設計判断）

上位設計は「`matchGroups` へ引数1つ追加と呼び出し5箇所の追従」としていた。
**本書は引数追加ではなくコンテキストオブジェクト化を採る。**

```ts
// store.ts（または後述の切り出し先）
export interface ConditionContext {
  state: SessionState
  world: World | undefined
  characterIds: string[]
  roleAssignments: RoleAssignment[] | undefined
  characters: { id: string; name: string }[]
  /** Session 直下（SessionState ではない）。前方一致で判定する */
  usedEventIds: string[]
  exactSelections?: Record<string, string[]>
}

export function matchGroups(cond: Condition | undefined, ctx: ConditionContext): {
  ok: boolean; subjects: RoleParty[]; exactCandidates: ExactGroupCandidate[]
}
```

**理由**:

1. `matchGroups` は既に**6引数**（`store.ts:359`）。7つ目を位置引数で足すのは事故の温床。
2. **G3（ロアの解禁条件）で同じコンテキストがもう一度要る。** 引数追加を選ぶと近い将来2回目の
   シグネチャ変更が確実に来る。1回で済ませる。
3. 型で全呼び出し元が落ちるので、機械的かつ安全に追従できる。

**追従が必要な箇所**（型エラーで全部落ちる）:

| 関数 | 現在地 |
|---|---|
| `evalCondition`（互換窓口） | `store.ts:405` |
| `unlockAchievements` | `store.ts:502` |
| `checkEndings` | `store.ts:536` |
| `nextScheduledEvent` | `store.ts:1709` |
| `confirmSceneReview` のエンディング再判定 | `store.ts:3279` |
| `SceneReviewModal` のプレビュー（`checkEndings` 呼び出し） | `SceneReviewModal.tsx` |

`checkEndings` / `evalCondition` / `unlockAchievements` も同じ `ctx` を受ける形へ揃える。
セッションから ctx を作るヘルパを1つ置くと呼び出し側が短くなる:

```ts
export function conditionContextOf(
  session: Session,
  world: World | undefined,
  characters: { id: string; name: string }[],
  state?: SessionState,          // 未指定なら session.state（レビュー確定後 state を渡す用）
  exactSelections?: Record<string, string[]>,
): ConditionContext
```

### 1.4 判定（`evalClause`）

```ts
case 'eventFired': {
  const fired = ctx.usedEventIds.some(
    (k) => k === clause.eventId || k.startsWith(`${clause.eventId}@`),
  )
  return fired === clause.have
}
```

前方一致ヘルパを**export して共有する**（G2 でも使う）:

```ts
/** そのイベント定義がどれか1組で発火済みか。usedEventIds は `eventId` or `eventId@charId1[+charId2]` */
export function isEventFired(usedEventIds: string[], eventId: string): boolean
```

### 1.5 ⚠ 落とし穴（上位設計に書かれていない・実装前に合意が要る）

#### (a) 同一シーン内での連鎖は起きない（仕様として明記する）

`usedEventIds` への追記は `confirmSceneReview` で行われる。一方 `nextScheduledEvent` は
**そのレビューの中で1つだけ**イベントを選ぶ。したがって「A が発火 → 同じレビューで B（条件: A 発火済み）も発火」
は**起こらない**。B は**次のシーン**で候補になる。

**実績（`unlockAchievements`）は `while` ループで連鎖を1パスで解決している**（`store.ts:498`）ので挙動が違う。
この非対称は意図的（イベントは1シーンに1つ・実績は同時に何個でも解除されてよい）。
**条件エディタのヘルプに一言書く**——「イベントの連鎖は1シーンに1段ずつ進みます」。

#### (b) エンディング条件に `eventFired` を使うと1シーン遅れる

`confirmSceneReview` の中でエンディングを判定する時点では、**今回発火するイベントはまだ `usedEventIds` に無い**。
よって「イベント X が発火したことを条件にしたエンディング」は**次のシーンのレビューで**成立する。

これは**プレビュー（`SceneReviewModal`）と確定（`confirmSceneReview`）の一致**という既存の重要な性質
（`docs/設計_エンディング.md`）を保つための当然の帰結——両方が「確定前の `usedEventIds`」を見るので**予告と発火は一致する**。
仕様として受け入れる。

#### (c) 存在しない `eventId` を参照する節は常に false

イベント定義を削除しても節は残る。**黙って発火しなくなる**（上位設計 §1.1.1 の「鎖は黙って途切れる」の典型）。
→ **WorldEditor に警告を出す**（§1.7）。

#### (d) 旧データの素の `eventId`

`nextScheduledEvent` は素の `eventId` が `usedEventIds` にあると「全組み消化済み」として扱う（`store.ts:1698`）。
`isEventFired` の前方一致は素の id も拾うので、**この規約と整合する**（発火済み＝true）。

### 1.6 ファクトリ（`store.ts:881`）

```ts
case 'eventFired':
  return { kind: 'eventFired', eventId: world.scheduledEvents?.[0]?.id ?? '', have: true }
```

### 1.7 UI（`WorldEditor.tsx` の `ClauseRow`・`WorldEditor.tsx:176`）

kind のプルダウンに1つ追加:

```tsx
<option value="eventFired">特別イベント</option>
```

行の形（既存の `achievement` 行と同じ文章形・`OP_LABELS`／`.clause-joint` の規約に従う）:

```
[特別イベント▼] [イベント名▼] が [発生済み ▼]
                                  [未発生   ]
```

- イベント名のプルダウンは `world.scheduledEvents` から。`（未選択）` を先頭に置く。
- **警告表示**: `clause.eventId` が `world.scheduledEvents` に無い場合、行の右に
  「このイベントは存在しません」を `--danger` 色で出す。実績行（`achievementId` で自己参照を除外している）と
  同様の考え方だが、こちらは**参照切れの検出**が目的。

`ClauseRow` は実績・エンディング・特別イベントの3画面で共有されているので、**1箇所の追加で3機能すべてに効く**
（上位設計 §1.1 のとおり）。

**自己参照の除外**: 特別イベントの条件編集で自分自身を参照できてしまうと、永久に発火しない鎖ができる。
`ClauseRow` は既に `achievementId` prop で実績の自己参照を除外しているので、**同じ形で `eventId` prop を足す**
（イベントの条件エディタから渡す。実績・エンディングからは未指定）。

### 1.8 受け入れ基準

1. 実績・エンディング・特別イベントの3つすべてで `eventFired` 節が書ける
2. 当事者つきイベント（`eventId@charId`）で発火したものが、素の `eventId` を指定した節で真になる
   （**前方一致の確認＝上位設計が最も強く警告していた点**）
3. A → B → C の3段の鎖が、**3シーンかけて**順に発火する（同一シーン内で連鎖しないことの確認）
4. 存在しないイベントを参照する節に警告が出る
5. `npx tsc --noEmit` → `npm run build`

## 2. G2 — 消化済みイベントの可視化

### 2.1 ⚠ 上位設計からの変更: 置き場所を「世界観エディタ」から「ステータスドック」へ

上位設計 §1.1.1 は「**イベント一覧に**消化済みマークを出す（`usedEventIds` を読むだけ）」としていた。
しかし**世界観エディタ（`WorldEditor`）は素材の編集画面で、どのセッションの話かを知らない**。
`usedEventIds` は `Session` 直下にあるので、**エディタからは原理的に読めない**。

→ 表示場所は**ステータスドック（`StatusView.tsx`）**が正しい。

### 2.2 ⚠ ネタバレの扱い（上位設計に無い論点）

`StatusView` は**プレイヤーが見る画面**でもある。未発火のイベント名を一覧すると**先の展開が割れる**。
実績・エンディングは `hidden` を持つが、`ScheduledEvent` は持たない。

**決定: 消化済みのものだけを出す。**「起きた出来事」の一覧なのでネタバレしない。
未消化は件数も出さない。作者のデバッグ用途（上位設計の目的）はこれで足りる——
「A が発火していない」ことは**一覧に A が無いこと**で分かる。

### 2.3 実装

`StatusView.tsx` に節を1つ追加:

```
【起きた出来事】
- 霧の夜の依頼
- 封蝋の紋章（藤宮 灯）      ← 当事者つきは名前を併記
```

- 対象: `world.scheduledEvents` のうち `isEventFired(session.usedEventIds, e.id)` が真のもの
- 当事者つきキー（`eventId@charId1+charId2`）から characterId を切り出し、現在の実名へ解決して併記する
  （**リネーム追従のため、名前は保存せず表示直前に解決する**＝`resolveParties` と同じ規約）
- 発火順は `usedEventIds` の配列順（追記順＝時系列）
- 1件も無ければ節ごと出さない

### 2.4 受け入れ基準

1. イベントが発火したシーンの後、ドックの状態タブに出来事が増える
2. 当事者つきイベントで当事者名が出る／キャラをリネームすると追従する
3. 未発火のイベント名がどこにも出ない

## 3. G3 — ロアの解禁条件

### 3.1 型（`types.ts`）

```ts
export interface LoreEntry {
  id: string
  keys: string[]
  content: string
  alwaysOn: boolean
  enabled: boolean
  order: number
  addedInStory?: boolean
  /** 解禁条件。未達なら注入しない。**alwaysOn より強い**（docs/設計_ゲーム性向上バックログ.md §1.2） */
  condition?: Condition        // ★追加
}
```

**optional 追加なので persist キー据え置き。**

### 3.2 ゲートの位置 — 依存の向きに注意

`lorebook.ts` は現在 `types` にしか依存しない純粋関数で、`store.ts` がそれを import している。
**条件エンジンは `store.ts` にあるので、`lorebook.ts` から呼ぶと循環依存になる。**

3つの選択肢:

| 案 | 内容 | 判断 |
|---|---|---|
| (a) 条件エンジンを `src/lib/conditions.ts` へ切り出す | 正攻法だが `store.ts` から純関数群を大量に移す大工事 | **今はやらない** |
| (b) `lorebook.ts` に ctx を引数で渡す | 判定関数も渡すことになり、結局 store から関数を注入する形で汚い | 却下 |
| **(c) `resolveRefs` の段階でゲート済みの World を作る** | `resolveRefs` は既に `effectiveWorld` を合成している。そこに1段挟むだけ | **採用** |

**(c) の実装**（`store.ts:1946`）:

```ts
const effWorld = gateLoreByCondition(
  effectiveWorld(worlds.find((w) => w.id === session.worldId), session.overlay),
  ctx,
)
```

```ts
/** 解禁条件が未達のロアを World から取り除く純関数。条件なしの項目はそのまま通す */
export function gateLoreByCondition(world: World | undefined, ctx: ConditionContext): World | undefined
```

- 条件なし（`condition` 未設定）→ 通す
- 条件あり → `matchGroups(condition, ctx).ok` が真のときだけ通す
- **`alwaysOn` でも条件が未達なら落とす**（上位設計の決定＝条件のほうが強い）
- **1件もゲートしていない World は同一参照のまま返す**（`stripLegacyFlagClauses` と同じ最適化。
  毎ターン呼ばれるので無駄なオブジェクト生成を避ける）

これで `lorebook.ts` は**無改修**、`prompts.ts` も**無改修**（既にゲート済みの World を見るだけ）になる。
レビュー文脈（`prepareSceneReview` の `refs.world`）も同じ `resolveRefs` を通るので**自動的に整合する**
——未解禁の設定がレビューに漏れることもない。

### 3.3 ⚠ 「発見ログへ」の再設計

上位設計 §1.2 は「達したら注入**＋発見ログへ**」としていた。しかし発見ログ＝`SessionOverlay.lore` は
**素材に無い発見を上乗せする層**で、本編には「素材＋オーバーレイの実効ビュー」が注入される（AGENTS.md）。
**素材側のロアが解禁されただけで overlay に足すと、同じ内容が二重に注入される。**

→ **overlay には足さない。** 代わりに「解禁された」ことを1回だけ通知する。

```ts
// types.ts / Session
/** 解禁条件つきロアのうち、既に解禁を通知したもの（重複通知の防止） */
revealedLoreIds?: string[]
```

- `confirmSceneReview` の最後（state 確定後）に、条件つきロアを再評価する
- 新たに解禁されたものがあれば `infoNotice` で「新しい設定が明らかになりました」を1回出し、
  `revealedLoreIds` へ追記する
- **ロアの中身はトーストに出さない**（本編で自然に出るべきもの。ここで見せると興を削ぐ）

**判定タイミングをレビュー確定時に限る理由**: 状態が動くのはレビューだけ（ADR-1）なので、
毎ターン評価しても結果は変わらない。無駄な計算をしない。

### 3.4 UI（`WorldEditor.tsx` のロアセクション）

ロア1行に**折りたたみの「解禁条件」**を追加する（上位設計 §1.2 の「既存のロア1行にオプション欄が1つ増えるだけ」）。

- 既定は閉じていて、条件が設定済みなら見出しに「条件あり」を出す
- 中身は既存の条件エディタ（`ClauseRow` 群）をそのまま再利用
- 説明文（`HelpDetails` の `.desc`）: 「条件を満たすまで、この設定は AI に渡されません。
  `常に注入` にしていても渡されません。」
- **「秘密ロア」という第二の概念を新設しない**（上位設計の決定）

### 3.5 受け入れ基準

1. 条件未達のロアが本編にもレビューにも渡らない（プロンプトを目視 or `buildSystemPrompt` の直接検証）
2. `alwaysOn` かつ条件未達のロアが**注入されない**（優先順の確認）
3. 条件を満たした次のシーンから注入される／トーストが1回だけ出る
4. 条件を持たない既存ロアの挙動が一切変わらない

## 4. G4 — `WORLD_PRESETS` 廃止と複製（fork）導線

上位設計 §4.3 / §4.4。**順序は「複製が先・プリセット削除が後」**（複製は単体で価値があり、
プリセット削除は複製が無いと新規ユーザーを取り残すため）。

### 4.1 G4-a 複製（fork）導線

```ts
// store.ts
duplicateWorld(id: string): string | undefined      // 新 id を返す
duplicateCharacter(id: string): string | undefined
duplicatePersona(id: string): string | undefined
```

規則:

| 項目 | 扱い |
|---|---|
| `id` | 新規（`uid()`） |
| `name` | 「〜のコピー」を付ける。同名が既にあれば「のコピー2」…と連番 |
| `avatar.imageId` | **同じ画像 id を共有する**（画像は不変・GC は参照カウントではなく使用中集合なので共有で安全） |
| 世界観の内部 id（ロア・実績・エンディング・ロール・stat/counter の `defId`） | **振り直さない** |
| `Character.developments` | そのままコピー |

**内部 id を振り直さない理由**: World 内で完結する id なので別 World と衝突しない。
そのまま維持すると、**既存セッションの世界観を複製先へ差し替えても state（`defId` 参照）が生きる**。
振り直すと差し替えのたびに数値・実績が全部リセットされる。

**UI**: 各 Library の右クリックメニュー（`LibraryMultiSelect.tsx` の `CardContextMenu`）に「複製」を追加。
複数選択時は一括複製。複製後は**エディタを自動で開かない**（一覧に増えるだけ＝一括複製と挙動を揃える）。

これで上位設計 §4.4 の「取り込んだカセットの世界観を編集すると原本を直接書き換えてしまう」問題が解ける。

### 4.2 G4-b `WORLD_PRESETS` を中立な既定1つへ

- `newWorld()` に既定を仕込む:
  - `relationAspects`: `[{ name: '信頼' }]`
  - `stats`: `[{ name: '好感度', scope: 'character', default: 0, min: 0, max: 100, inject: false }]`
  - `counters`: `[]`（カウンターは作者が決めるもの。空でよい）
- `WORLD_PRESETS`（`store.ts:916`）と、`WorldEditor` のプリセット選択 UI を**削除**。

**中立な既定を置く理由**（上位設計 §4.2）: `relationAspects` が空のままだとレビューが劣化する
（`prompts.ts:396`「次元未定義のため relationUpdates.aspects は空配列にし、stance のみ更新する」）。
プリセットが実際に防いでいたのは手本の不在ではなく**空設定のまま遊び始めること**なので、
既定1つで目的は達せられる。

### 4.3 受け入れ基準

1. 世界観・キャラ・ペルソナを複製でき、原本を編集しても複製先が変わらない（逆も同様）
2. 複製した世界観に既存セッションを差し替えても、ステータス・実績が保持される（内部 id 維持の確認）
3. 新規世界観に「信頼」と「好感度」が入っている
4. 画像 GC を実行しても、複製元・複製先どちらのアバターも消えない（**共有 imageId の確認**）

## 5. G5 — `decayPerScene` の再開条件（保留のまま）

上位設計 §2.4 は「緊張感目的なら `reviewGuidance` で足りる＝優先度低。
**§2.3 の迎合固定化ループを断つ目的なら代替不能**＝その時は採用」と結論した。
本書は**判断を変えない**。ただし「その時」を判定する材料が無いので、**測り方だけ設計しておく**。

### 5.1 ループが実在するかを測る（PC0 に相乗り）

上位設計 §2.3 の主張は「数値が事実上**上振れ方向にしか動かない**」だった。これは**そのまま測れる**。

`docs/詳細設計_プロンプト構造とキャッシュ.md` §2.3 の `UsageRecord` に既に入れてある:

```ts
/** レビューのみ: statChanges の符号内訳 */
deltaSigns?: { plus: number; minus: number; zero: number }
```

`prepareSceneReview` がレビュー結果をパースした直後に集計して記録するだけ（**追加コストゼロ**）。

### 5.2 再開条件

- **1セッション（10シーン以上）で `minus` の比率が 1割未満** なら、§2.3 のループは実在する
  → `decayPerScene` の保留を解いて採用する
- `minus` が 2〜3割出ているなら、レビューは減点を出せている → **保留のまま**。
  `reviewGuidance` で足りるという上位設計の整理が正しかったことになる

この判定は PC0 の計測を1セッション回すだけで付く。**G1〜G4 より先に材料が揃う**ので、
実装順とは独立に進めてよい。
