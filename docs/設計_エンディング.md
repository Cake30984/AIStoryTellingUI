# 設計: エンディング定義（終わりの構造）

- 日付: 2026-07-17
- 対象: World のエンディング定義／シーン終了レビューでの到達判定／エピローグシーン／完結演出／周回横断の到達記録
- 位置づけ: 状態エンジン（ADR-1・`設計_ステータスエンジン.md`）の条件エンジン・実績の直系拡張。セーブ/ロードと分岐（`設計_セーブロードと分岐.md`）と組み合わせて「別エンディングを分岐で探す周回」を成立させる
- 実装状況: **E1〜E3 未着手**（2026-07-17 合意）

## 1. 背景と決定事項

既存ギャルゲ・TRPG との比較検討（2026-07-17）で、本システムには「条件を満たすとこのエンディングに到達する」「期間が満了すると物語が終わる」という**終わりの構造**が無いことが体験上の大きな欠落と整理された。タイムラインの `isNearEnd`（85% でクライマックス促し文言）はあるが、満了しても何も起きず、達成感と周回動機が生まれない。

条件エンジン（`evalCondition`）・実績（`unlockAchievements`）・レビュー確定（`confirmSceneReview`）が既にあるため、エンディングは**実績の親戚**として小さく足せる。原則は ADR-1 のまま:

- **到達判定はコード**（数・フラグ・実績のしきい値。prose は読まない・LLM に査定させない）
- **エピローグの中身だけ LLM が書く**（判断は言葉）
- 構造（名前つきエンディング・条件・優先順）が再現性を持つことが「共有可能なゲーム」の要

### ユーザー決定（選択式質問の回答・2026-07-17）

1. **突入方式は定義ごとに指定**（`EndingDef.auto`）。通常はレビューで「エンディングへ進む／まだ続ける」を選べるが、`auto: true` のエンディング（破滅バッドエンド等）は条件成立で強制突入する。緊張感と自由度の両立。
2. **エピローグは通常シーン型**。エピローグ専用シーンを作って最後の数ターンを対話で遊び、「🏁 物語を完結する」で締める。読み物型（全文一括生成＋セッションロック）は却下——ロック状態の管理が各操作ガード・restoreCheckpoint passthrough 判定に波及し、最後の別れの会話に介入もできないため。
3. **期間満了は既定選択で提示**。totalDays を超えるレビューで成立エンディング（無ければ fallback）を「エンディングへ進む」既定選択で提示する。「まだ続ける」も選べる＝無限サンドボックスの遊び方は殺さない。満了強制終了は却下。

### その他の設計判断（却下案含む）

- **判定はシーン境界（レビュー確定）のみ**。選択肢加点（小ポイント）では判定しない。シーン途中で物語がぶつ切りになるのを防ぐ。実績（小ポイントでも解除）と異なる点。HP0 即死のような演出は次のレビューまで遅延される制約として許容する。
- **完結後の操作ロックはしない**。読み返し・分岐復元・同シーン内での書き足しは自由。達成感は演出（完結オーバーレイ・バッジ）で出し、状態機械を増やさない。
- **判定関数はレビューモーダルのプレビューと確定処理で共有**する（後述 `applyReviewToState`）。プレビューと実際の発火が食い違う実装を禁止する。

## 2. データモデル

### 2.1 EndingDef（World に追加）

```ts
/** エンディングの定義（ワールド固定）。到達判定はコードが自動で行う */
export interface EndingDef {
  id: string
  name: string
  /** UI 表示用の説明（一覧・到達時に見せる。条件そのものは晒さない） */
  description: string
  /** 到達条件。fallback=true の定義は持たない（UI で条件エディタを隠し、判定でも無視） */
  condition?: Condition
  /** エピローグ生成への指示（結末のトーン・締め方）。到達後にのみ注入＝プレイ中のリークなし */
  epilogueGuidance: string
  /** 条件成立で強制突入する（レビューでの「まだ続ける」を出さない。バッドエンド向け） */
  auto?: boolean
  /** 未到達時に名前・内容を ??? 表示（実績の hidden と同じ） */
  hidden?: boolean
  /** 期間満了時、条件成立エンディングが無い場合に採用するノーマル/バッドエンド */
  fallback?: boolean
}

export interface World {
  // 既存フィールド...
  /** エンディング定義。未設定は空配列扱い。配列順=優先度（上が優先） */
  endings?: EndingDef[]
}
```

- **複数成立時は配列順で最上位の1つ**。実績と違い順序に意味があるため、WorldEditor に ↑↓ 並べ替えを付ける。
- `fallback` と `condition`/`auto` は排他（fallback は満了時の受け皿であり、条件判定・強制突入の対象にならない）。UI で fallback ON のとき条件エディタと auto を隠す。データに残っていても判定側が無視する。
- optional 追加のみ → **persist キー据え置き**（クリーンブレイク不要）。

### 2.2 到達状態（Session に追加）

```ts
export interface Session {
  // 既存フィールド...
  /** 到達したエンディング（セッション固有。チェックポイント対象＝分岐で戻れば未到達に戻る） */
  ending?: {
    defId: string
    name: string
    reachedAt: number
    /** エピローグシーンの id。このシーンが currentScene の間だけエンディング指示を注入する */
    epilogueSceneId: string
  }
}
```

- **restoreCheckpoint の passthrough には入れない**（本文・進行と結合した状態＝スナップショット側）。巻き戻せば未到達に戻る——これが「戻って別エンディングを狙う」周回の根幹。
- 「完結済み」は `ending` があり、かつ `epilogueSceneId` のシーンに `endedAt` が立っていることから**導出**する。別フラグは持たない。

### 2.3 到達記録（E3・AppState 直下）

```ts
/** エンディング到達の周回横断記録（エピローグ突入時に追記） */
export interface EndingRecord {
  worldId: string
  endingDefId: string
  sessionId: string
  reachedAt: number
}
// AppState 直下: endingRecords: EndingRecord[]
```

- ギャルゲの「攻略済みルート一覧」体験。World を使い回した別セッション・カセット周回でも「この世界で見た結末 n/m」が積み上がる。
- Session の外に置く理由: セッションは削除・複製されるが「見た」という事実は残したい。分岐で巻き戻しても消えない（見たものは見た）。
- 記録契機は**エピローグ突入時**（完結ボタンではない。押し忘れで記録漏れしないため）。同じ組の再到達も追記し、表示側で distinct 集計する。
- persist 対象・exportBundle/importBundle 対象（同値 dedupe でマージ）。World 削除時に該当 worldId のレコードを掃除する。画像を持たないため GC は無関係。

## 3. 判定ロジック

### 3.1 `applyReviewToState`（confirmSceneReview からの抽出）

現在 `confirmSceneReview` 内のクロージャ `applyState`（関係 prose 全文書き直し・flags 和集合・スタット clamp 加算・カウンター累計・実績反復解除）を、**モジュールレベルの純関数に抽出して export** する:

```ts
export function applyReviewToState(
  base: SessionState,
  world: World | undefined,
  characterIds: string[],
  sel: {
    relationUpdates: RelationUpdate[]
    statChanges: StatChange[]
    counterEvents: CounterEvent[]
    moodChanges: MoodChange[]
  },
): { state: SessionState; unlocked: AchievementDef[] }
```

- `confirmSceneReview`（確定）と `SceneReviewModal`（プレビュー）の**両方がこれを呼ぶ**ことで、モーダルに出した到達予告と実際の発火が必ず一致する。
- 純関数なので `preview_eval` で直接検証できる（検証ワークフロー方針に沿う）。

### 3.2 `checkEndings`（成立判定の純関数）

```ts
/** 条件成立エンディングを優先順で1つ返す（fallback・条件なしは対象外） */
export function checkEndings(
  endings: EndingDef[],
  state: SessionState,
  world: World | undefined,
  characterIds: string[],
): EndingDef | undefined
```

- `evalCondition` をそのまま使う。`fallback === true` または `condition` 未設定の定義はスキップ。
- **満了判定**は呼び出し側: レビュー確定で進む先が `nextTimeline.currentDay > totalDays` になるとき「満了モード」。候補は ①`checkEndings` の結果 → ②`fallback` の最上位。両方無ければ従来どおり続行（エンディング未定義ワールドの互換）。
- `session.ending` が既に set なら判定・提示・発火をすべてスキップ。過去シーンの再レビュー（isPastScene）でも判定しない。

### 3.3 SceneReviewModal のフロー

1. モーダルはローカルのチェック選択から `applyReviewToState` で「確定した場合の次 state」を計算し、`checkEndings`＋満了判定を行う。選択を変えるたびに再計算（純関数・軽量）。
2. 成立時、「🏁 エンディング」欄を表示:
   - **auto=false（通常）**: 「エンディング『○○』に到達できます」＋ラジオ「エンディングへ進む／まだ続ける」。既定は**まだ続ける**（確定ボタンの惰性押しで誤完結しない保守側）。
   - **auto=true**: 「エンディング『○○』に到達します」告知のみ（選択なし。確定＝突入）。
   - **満了モード**: 既定を**エンディングへ進む**に反転（それでも「まだ続ける」は選べる）。fallback 採用時はその旨を表示。
3. 確定時は `confirmSceneReview` の opts に `endingDefId?: string` を追加して渡す。
4. **confirm 側で再判定・検証**する: 渡された defId が world.endings に存在し、確定後 state で実際に成立している（または満了 fallback である）ことを確認。不一致なら無視して通常続行（防御）。auto 成立は opts に依らず confirm 側で強制する。
5. 「まだ続ける」を選んでも、条件を満たし続ければ次のレビューでまた提示される（それが自然。抑制フラグは作らない）。

## 4. エピローグシーンと完結

### 4.1 エピローグシーンの作成（confirmSceneReview 内の分岐）

エンディング発火時、「次シーン作成」を以下に差し替える:

- タイトル: `エピローグ：${ending.name}`／`timeLabel: 'エピローグ'`／`note: epilogueGuidance`／activeCharacterIds は前シーンを引き継ぐ
- **タイムラインは進めない**（`advanceTimeline` を呼ばない。もう時間の意味が無く、満了超過の「11日目」のような表示も避ける）
- state 適用・オーバーレイ追記・実績解除は通常どおり行う（最終状態も記録される）
- `session.ending` をセット（`epilogueSceneId` = 新シーン id）
- `usedEventIds` 等は通常フローのまま。特別イベントの同時発火は**エンディングが勝つ**（イベントは未消化のまま残す）
- `recordCheckpoint('scene', `🏁 エピローグ：${name}`, …)` → 分岐ツリーに突入ノードが残る
- 通常どおり `beginScene()` で導入生成 → 選択肢も choiceMode に従い生成（締めの場面でも介入の選択肢はあってよい）
- 到達トースト: 実績解除トースト（`newlyUnlockedAchievements`）と同じ仕組みで「🏁 エンディング『○○』へ」を表示

### 4.2 プロンプト注入（buildSystemPrompt）

`ResolvedRefs` に `ending?: { name: string; guidance: string }` を追加し、resolveRefs で「`session.ending` があり、かつ `currentSceneId === epilogueSceneId`」のときだけ詰める。注入ブロック（【時間】の後・【状態（現在）】の前）:

```
【エンディング】
この物語は結末「○○」のエピローグに入っています。（epilogueGuidance）
新しい事件・伏線を起こさず、これまでの感情と関係の帰着を描いてください。
数ターンで余韻を残して物語を締めくくる方向で書きます。
```

- `ending` が set の間は **nearEnd 注入をスキップ**（「クライマックスに向けて収束」とエピローグ指示が矛盾するため）。
- `epilogueSceneId` 以外のシーンでは注入しない＝将来「完結後にアフターストーリーのシーンを作る」導線を足しても自動的に自由な文体へ戻る。

### 4.3 完結

- ChatPanel: currentScene がエピローグシーンのとき、コンポーザーの「シーン終了」ボタンを「**🏁 物語を完結する**」に差し替え。
- 押下 → 新アクション `finalizeStory()`: レビューを**スキップ**して `scene.endedAt` をセット＋`recordCheckpoint('scene', '🏁 完結', …)`＋完結オーバーレイ表示。次シーンは作らない。
- 完結オーバーレイ: エンディング名・description・「閉じる」だけの簡素な演出（ModalShell ベース）。将来ここにエンディング CG・スタッフロール風演出を足せる。
- 完結後: トップバーに 🏁 完結バッジ（エンディング名）。操作ロックはしない。続きを遊びたければ分岐ツリーから復元する。

## 6. カード・カセット・既存機構との整合

- **World カード書き出しは World 丸ごと serialize**（`buildWorldCard` の `data: world`）のため `endings` は自動同梱。**取り込み側 `normalizeWorldFromData` はフィールド列挙式なので `endings: Array.isArray(raw.endings) ? raw.endings : []` の追加が必要**（忘れるとカード往復で定義が消える）。
- **`freshSessionOf`（cards.ts）に `ending: undefined` を追加**。忘れるとカセット出力→新規プレイで即「完結済み」表示になる。
- `sessionImageIds` / GC: エンディングは画像 id を持たないため影響なし（完結オーバーレイに CG を足す将来拡張時に要追加）。
- `restoreCheckpoint`: `ending` はスナップショット側（passthrough に入れない）。
- エクスポート: World 内包のため自動追随。E3 の `endingRecords` のみスキーマ変更手順（型 → 初期 state → exportBundle/importBundle → partialize）を踏む。

## 7. フェーズ分割

1ターン1フェーズ・各フェーズで型チェック→build→検証。

### E1: 定義と表示（判定はまだ動かない）
- `types.ts`: `EndingDef`・`World.endings?`・`Session.ending?`
- `WorldEditor.tsx`: エンディングセクション（並べ替え含む）
- `StatusView.tsx`/`StatusPanel.tsx`: 一覧表示（到達表示のロジックだけ先に入れる。`ending` はまだ誰もセットしない）
- `cards.ts`: `normalizeWorldFromData` に endings・`freshSessionOf` に ending リセット
- 検証: エディタで定義作成→保存→World カード書き出し→取り込みで endings が残る

### E2: 判定 → エピローグ → 完結
- `applyReviewToState` 抽出（confirmSceneReview を新関数経由に置換）・`checkEndings`
- `SceneReviewModal` のプレビュー欄・opts.endingDefId・confirm 側の再判定と発火（エピローグシーン作成・ending セット・タイムライン据え置き）
- `prompts.ts`/`resolveRefs`: 【エンディング】注入・nearEnd スキップ
- `finalizeStory()`・完結オーバーレイ・完結バッジ・到達トースト
- 検証: `preview_eval` で `applyReviewToState`/`checkEndings` を直叩き（条件成立・優先順・fallback・満了）。手動確認リストを完了報告に明記

### E3: 周回横断の到達記録
- `endingRecords`（AppState 直下・persist・export/import・World 削除時掃除）
- 突入時の記録追記・「見た結末 n/m」表示・カセット棚バッジ・`BranchNode.ending` とツリー 🏁
- 検証: 周回（カセット再プレイ・分岐で別エンディング）で記録が積み上がる

## 8. 将来拡張（設計のみ・実装しない）

- **周回解禁（New Game+）**: `endingRecords` を条件に使う（「トゥルー到達済みの周回では隠しイベント解禁」）。条件エンジンがセッション外の状態を読むことになり、素材不変原則・再現性との整理が必要。別設計で扱う。
- **`Clause` への `ending` 種別**: セッション内到達を実績条件に使う案。到達＝即エピローグのため実用場面が薄く、横断記録ベースの上記案に吸収見込み。
- **エンディング CG・回想**: 完結オーバーレイでの挿絵自動生成、到達エンディングのギャラリー横断表示。
- **アフターストーリー導線**: 完結オーバーレイから「続きを遊ぶ（新シーン作成）」。epilogueSceneId 方式により注入は自動で外れる設計済み。
