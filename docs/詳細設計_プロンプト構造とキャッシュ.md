## 0. 実測（PC0 の先取り実施）

上位設計は「本書の金額はすべて概算」「PC0 の実測で置き換える」（§9）としていた。詳細設計に入る前に、
**OpenRouter の実 API に対して計測を行った**ので、その結果を先に置く。以降のすべての設計判断はこの数字に基づく。

- 計測日: 2026-08-02
- モデル: `deepseek/deepseek-v4-flash`（入力 $0.14/M・出力 $0.28/M・**キャッシュ読み $0.028/M＝入力の 1/5**）
- 経路: OpenRouter `/chat/completions`（stream）
- スクリプト: 使い捨て（scratchpad）。本書の数字が結論なので再実行は不要

### 0.1 測定できた事実

| # | 事実 | 根拠 |
|---|---|---|
| **F1** | **`usage` は追加フラグ無しで最終 SSE チャンクに載る**。`{prompt_tokens, completion_tokens, cost, prompt_tokens_details:{cached_tokens, cache_write_tokens}, cost_details, completion_tokens_details:{reasoning_tokens}}` | 現行アプリと同一の body（model/messages/temperature/max_tokens/stream）で取得できた |
| **F2** | キャッシュヒット時の実コストは **1/3.9**（$0.000440 → $0.000113・同一リクエスト） | 単価表の 1/5 に対し、末尾の未キャッシュ分ぶん目減りする |
| **F3** | **キャッシュ粒度はメッセージ単位**。system を1文字でも変えると **system 全体が無効**になる | system の**中ほど**に1行挿入 → ヒット率 **2%（3/3）**。ブロック粒度なら手前は残るはずだった |
| **F4** | 配置別ヒット率（3周・完全再現） | 下表 |
| **F5** | **ヒットはレプリカ確率的**。まったく同一のリクエストでも 2% と 96% が混在する | 同一 body の連投で 2%→96%→2% が出る |
| **F6** | OpenRouter の既定ルーティングは**同一モデルでも上流を負荷分散**する（StreamLake / DeepInfra）。**別上流に飛ぶとキャッシュは無い** | `provider` フィールドで確認。`provider.order` で固定可能（slug は `DeepInfra` 等。`deepseek` は 404） |
| **F7** | **R2（選択肢）は現状 0% ではない**。system が固定なので**自分自身の前ターンの系列**に乗っている（実測 平均 46%・最大 65%） | 上位設計 §1 の「1トークンも再利用できない」は誤り |
| **F8** | `cache_control` 付き content ブロック配列は、**非 Anthropic モデルへ送ってもエラーにならない**（無視される） | OpenRouter 経由で 200 応答 |

**F4 の配置別ヒット率**（system 約3000トークン＋履歴8件・可変ブロック1つを各位置へ置いた場合）:

| 可変ブロックの置き場所 | ヒット率 | 再現性 |
|---|---|---|
| （対照）変えずに同一再送 | **96%** | 3/3 |
| **system の先頭**（＝現在の実装） | **2%** | 3/3 |
| **system の末尾** | **2%** | 3/3 |
| **system の中ほど** | **2%** | 3/3 |
| messages の末尾（深さ0） | **95%** | ヒット時 |
| **messages の深さ3** | **87%** | 3/3 |

### 0.2 上位設計のどこが裏づけられたか

- **「可変ロアを system 末尾に置く」の却下は正しかった**（§8 の却下表）。しかも理由は上位設計が書いた
  「後続の履歴が丸ごとミスする」だけではなく、**system 自身も丸ごと無効になる**（F3）。却下の根拠はより強い。
- **深さ注入という解法は正しい**。深さ3で 87% が実測で残る（F4）。
- **R3（レビュー）をキャッシュ対象外にした判断は正しい**。出力支配なうえ、そもそもヒットが確率的（F5）。
- **PC-C を PC3 の前に置いた判断は正しい**（§7 の注記）。むしろ F5 により**もっと重要**になった（§8）。

### 0.3 上位設計から変更した3点

| # | 上位設計 | 本書の判断 | 理由 |
|---|---|---|---|
| **C1** | PC1＝`buildSystemPrompt` の三層化（T1/T2 の並べ替え） | **並べ替えはキャッシュ目的では実施しない**。PC1 の目的を「**system を毎ターン byte 一致させる**」に置き換える | F3。粒度がメッセージ単位なので、system 内の順序はキャッシュに1トークンも寄与しない。効くのは「変わるか/変わらないか」の二値だけ |
| **C2** | PC2＝R2 の system 差し替えを廃止し R1 と接頭辞を共有（「**R2 が最優先**」） | **PC2 は却下**。対案（文脈を削る）を採る | F7＋F5。R2 は既に自系列でヒットしており、接頭辞共有は送信量を約1.6倍にして 1/5 引きを得る形＝ヒット時ほぼ同等・**ミス時は明確に悪化**。しかもミスは常時起こる |
| **C3** | PC-B の測定＝各案 × 各地点 × 入力3種 × N=5 で「即時受容率」を測る | **測定プロトコルを2ターン制に修正**する | 予備実測で、小説形式1応答では**帰結が描かれないケースが支配的**（判定不能）と判明。§4.3 |

## 2. PC0 — usage 計測の常設化

### 2.1 目的

R1〜R5 の実コスト・キャッシュヒット率・所要時間を1セッションぶん記録し、以降のフェーズの効果を測れるようにする。
**F1 により body の変更はほぼ不要**＝実装は極小。

### 2.2 `openrouter.ts`

```ts
export interface ChatUsage {
  promptTokens: number
  completionTokens: number
  /** プレフィックスキャッシュから読めた入力トークン数 */
  cachedTokens: number
  /** キャッシュ書き込みトークン数（Anthropic 系のみ非0になる） */
  cacheWriteTokens: number
  /** プロバイダ申告の実コスト（USD）。OpenRouter 以外は undefined */
  cost?: number
  /** 実際に処理した上流プロバイダ名。キャッシュはこの単位で効くので必ず記録する（F6） */
  upstream?: string
}

export interface ChatResult {
  text: string
  finishReason: string | null
  usage?: ChatUsage        // 追加
}
```

`streamChat` の SSE ループ内で、既存の `choice` 取り出しに加えて:

```ts
if (json.usage) lastUsage = json.usage      // 最後に来たものを採用
if (json.provider) upstream = json.provider // OpenRouter は各チャンクに載せてくる
```

`data: [DONE]` で早期 return している経路（`openrouter.ts:84`）でも usage を返すこと。
**現在の実装は `[DONE]` を見た時点で return するため、usage チャンクが `[DONE]` の後に来ると取りこぼす**。
実測では usage は `[DONE]` の前に来たが、順序を仮定しない書き方にする。

**`stream_options` の扱い**: OpenRouter は無くても返す（F1）ので**送らない**。
`provider.kind === 'openai'`（汎用 OpenAI 互換）のときだけ `stream_options: { include_usage: true }` を付ける。
理由は2つ——①現行の OpenRouter リクエストを1バイトも変えない（余計な差分を作らない）
②互換サーバの中には未知フィールドで 400 を返すものがあるため、必要な経路にだけ限定する。

## 3. PC-A — レビューの体感速度（実装済み・2026-08-02）

上位設計 §5。**依存ゼロ・発端の不満の片方に直接効く**。

> **実装メモ（設計との差分）**:
> - 進行表示は `SceneReviewModal` 内の別コンポーネント `ReviewProgressView` として描く（本体の全項目を
>   disabled にするのではなく、確定前は進行だけの軽い画面に差し替える）。中止のみ可能・×/オーバーレイ
>   クリックも中止と同義。
> - **進行の単位は「工程」ではなく「呼び出し」にした**（設計の `phase: ReviewPhase` を
>   `calls: ReviewCallProgress[]` に置き換え）。**理由は実使用のフィードバック**——工程の段階表示
>   （あらすじ→次シーン候補→状態の変化）では、**いま何本のリクエストが飛んでいるかが読めない**。
>   分割実行では B が開始直後に `"relationUpdates"` を出すので段階が一気に進み、逐次実行との区別も付かない。
>   呼び出し1本＝1行にして `waiting`/`streaming`/`done`/`failed` と**受信文字数**を出すと、
>   2行が同時に伸びること自体が並列実行の証拠になる。
> - 分割時、**片方が例外で落ちても続行する**（`AbortError` だけは両方の中断として外へ投げる）。設計が
>   「片方だけ失敗しても続行」と書いていたのは JSON 解釈の失敗だが、通信エラーでも同じ扱いにした方が
>   得るものが多いため。両方落ちた時だけエラーを出す。
> - `reviewSystem('all', ...)` の出力は**変更前とバイト一致**（トグル OFF で従来と同一結果＝受け入れ基準3）。
>
> **再試行が多い問題と対処（2026-08-02 追修）**: レビューの再試行（`maxAttempts=2`）が体感で頻発するとの指摘。
> 原因は3つに分かれ、そのうち2つが実装側の不備だった。
>
> | # | 内容 | 対処 |
> |---|---|---|
> | R1 | **`extractJson` が壊れた JSON を捨てていた**。実測で頻出するのは①**文字列内の生の改行**（system は「改行は `
` で書け」と指示しているが、あらすじのような複数段落の値でモデルがよく破る）②**末尾カンマ**。どちらも `JSON.parse` が必ず失敗する | `repairJsonText` を**素のパースが失敗した時だけ**通す修復フォールバックを追加（`json.ts`）。壊れていない出力の解釈は1バイトも変えない |
> | R2 | **再試行が同一リクエストの投げ直しだった**＝直る根拠が無く、運任せで2倍払っていた | 失敗理由に応じた**追伸を user メッセージで1通足す**（途中切れ→簡潔に／解釈失敗→JSON だけ・改行は `
`／summary 空→summary 必須） |
> | R3 | 再試行そのものは正当（本当に途中で切れた等）だが、**理由が画面に出ていなかった**ので「なぜか再試行される」に見えていた | 進行行に理由を出す（`ReviewCallProgress.note`）。以後どの原因かは画面で分かる |
>
> 検証（疑似サーバ）: 末尾カンマつきの B は**再試行なしで1回**、summary 欠落の A は再試行し、
> **2回目のリクエストに追伸が含まれる**ことをサーバ側で確認。進行行にも
> 「再試行2回目：あらすじ（summary）が空だったため」が出る。生の改行を含む JSON も本文まで通った。
> 修復対象外（途中切れ）は従来どおり再試行する。
>
> **並列実行の検証（2026-08-02）**: 疑似 OpenAI 互換サーバ（ローカル・SSE を遅延送出）を接続先に挿して実測。
> - サーバ側の受信時刻: A と B が **1〜3ms 差**で着弾（逐次なら応答長ぶん＝十数秒ずれる）。
>   `streamChat` 単体でも delta の到着が `ABABAB…` と1:1で交互になることを確認。
> - トグル OFF では**1本ずつ**（`summary` 欠落時のリトライも直列）であることをサーバログで確認。
> - 受け入れ基準1（即モーダル・あらすじが流れる）・4（中止で両方止まる）も同経路で確認済み。

### 3.1 A-1 ストリーミング段階表示

#### `json.ts`

```ts
/**
 * ストリーミング途中の未完成 JSON から、指定キーの文字列値を「読めるところまで」取り出す。
 * 閉じ引用符が未到達ならそこまでを返す（＝タイプライタ表示に使える）。
 */
export function partialString(buf: string, key: string): string | undefined
```

実装方針: `"<key>"` を探し、続く `:` と `"` を読み飛ばして1文字ずつ走査。`\\` エスケープを解釈し、
未エスケープの `"` で終了。バッファが尽きたらそこまでを返す。`\n` は実改行へ。**純粋関数**（テスト可能）。

#### `store.ts`

```ts
export type ReviewPhase = 'connecting' | 'summary' | 'suggestions' | 'state' | 'done'
// 非永続
reviewProgress: { sessionId: string; sceneId: string; summary: string; phase: ReviewPhase } | null
```

`prepareSceneReview` の `streamChat` の `onDelta` を実装する（現在は `() => {}`）:

- `acc` に貯め、**16ms スロットリング**で `set` する（毎トークン `set` すると再描画が重い）
- `summary` は `partialString(acc, 'summary')`
- `phase` は acc 内に `"suggestions"` が現れたら `suggestions`、`"relationUpdates"` が現れたら `state`

#### UI

`App.tsx` のモーダル表示ゲートを拡張:

```ts
(sceneReview?.sessionId === activeId || reviewProgress?.sessionId === activeId) && view === 'sessions'
```

`SceneReviewModal` は `review` が未確定で `progress` だけの間:
- ヘッダ「シーンを整理しています…」
- あらすじ欄に `progress.summary` を流し込む（読み取り専用）

### 3.2 A-2 2本に分割して並列

#### `prompts.ts`

```ts

  part: ReviewPart,
  aspectNames: string[],
```

| part | 出力させる項目 | 渡す拘束 |
|---|---|---|
| `a` | `summary` / `suggestions` / `characterGrowth` / `worldGrowth` | なし（次シーンの時間・イベントは user 文脈側） |

**`reviewGuidance` は B のみに入れる**。上位設計の分割線が「A＝何が起きたか / B＝状態がどう動いたか」で、
`reviewGuidance` は状態変動の方針（`prompts.ts:448`）だから。A に入れると無関係な指示で
`suggestions` が歪む。

#### `store.ts`

`prepareSceneReview` の呼び出し部を共通関数へ切り出す:

```ts

```
既存のリトライ（`maxAttempts = 2`・`finish_reason==='length'` 判定・`extractJson`）をこの中へ移す。


| 【状態（現在）】の値 | シーン境界のみ | system に残す |
| 【登場人物】の `developments` | シーン境界のみ（レビューで追記） | system に残す |
| 【これまでのあらすじ】【現在の場面】【時間】【エンディング】 | シーン境界のみ | system に残す |
| 【最初の方向付け】 | 最初のシーンのみ→消える | system に残す |

**結論**: ロアと話者指定の2つを system から追い出せば、system はシーン境界でしか変わらなくなる＝
**R1 のヒット率が実測 2% → 87〜96% になる**（F4）。

### 5.3 `prompts.ts`

`buildSystemPrompt` は `always` のみを【世界観】ブロックに入れる。`matched` は system に入れない。

`buildMessages` を深さ注入つきに書き換える:

```ts
/** 末尾から depth 件手前へ差し込む。履歴が足りなければ system 直後へクランプする */
function insertAtDepth(history: ChatMessage[], depth: number, content: string): ChatMessage[] {
  const at = Math.max(0, history.length - depth)
  return [...history.slice(0, at), { role: 'user', content }, ...history.slice(at)]
}
```

組み立て順:

1. system（T1+T2） … `buildSystemPrompt`
2. history … 現状どおり（現在シーンのみ・PC3 で拡張）
3. **深さ3の1通**を `insertAtDepth(history, 3, depth3)` で差し込む
4. **深さ0の1通**を末尾へ push
5. 呼び出し側の `extraUserNudge`（`CONTINUATION_NUDGE` 等）はさらにその後ろ（現状どおり・変更なし）

**深さ3の中身**（この順・上位設計 §3.3 の「素材 → 拘束」）:

```
【今回の場面に関わる設定】   ← matched なロア（あれば）
【状態→帰結の拘束文】        ← PC-B で決めた文面
【常に踏まえる重要事項】     ← session.authorNote
```

**深さ0の中身**（この順）:

```
【今回の応答】               ← 会話劇の話者指定（あれば）
【シーンの締め】/【シーンの収束】 ← 閾値超過時のみ
（短い形式の再掲）           ← 下記
```

**形式の再掲**（毎ターン非キャッシュなので**短さが命**）:

| 条件 | 文面 |
|---|---|
| `structuredOutput` ON | `（セリフは行頭 @名前 の1行、地の文は @ を付けない。1〜3段落で書く。）` |
| OFF | `（地の文とセリフを織り交ぜて1〜3段落。）` |

**空なら差し込まない**（空メッセージを送らない）。深さ3も深さ0も同じ規則。

### 5.4 クランプの挙動（上位設計 §3.3 のとおり）

## 7. PC-C + PC3 — cache_control と原文窓（セット・実装済み・2026-08-02）

> **実装メモ（設計との差分）**:
> - **`selectRawScenes` に第5引数 `previousFromSceneId` を足した**（本書 §7.2 の関数シグネチャに無い追加）。
>   **ヒステリシス（原則①）が引数だけでは実装できなかった**ため——「前回どこまで畳んだか」を渡さないと、
>   毎回その場で予算に切り直すことしかできず、**窓が1シーンずつ滑る**（原則①が禁じている挙動）。
>   実際、渡さない版を検証したところ 8シーン中5回起点が動いた。渡す版では 12シーン中2回まで下がる
>   （`s1 ×6 → s5 ×4 → s9 ×2` の階段）。値は `Session.rawWindowFromSceneId` をそのまま渡すだけ。
> - **畳む条件は「予算超過時のみ」**にした。`RAW_WINDOW_KEEP_RATIO`(0.6) を常時のしきい値にすると
>   結局毎シーン1つずつ落ちる。予算いっぱい（12000）まで使い、超えた時だけ 60% までまとめて落とす。
>   窓は**古い方へ戻さない**（前回の窓があるならそれより古いシーンは「落としたもの」）＝振動しない。

>   `selectRawScenes` の返す `bridgeTail` と同じ位置になるので、状態を二重に持つ必要がない。
>   **窓が現在シーンまで畳まれている（`from === currentSceneId`）場合こそ橋が要る**ので、
>   そこを「窓なし」と同一視しない（受け入れ基準1 の要）。
> - 橋の切り出しは**最低1件は必ず残す**（`RAW_WINDOW_BRIDGE_TOKENS` を超える1件しか無くても残す）。
>   0件にすると橋の意味が消えるため。
> - **`rawWindowFromSceneId` が使えないときは PC3 以前の挙動へ落とす**（未設定＝旧データ・最初のシーン／
>   分岐の巻き戻しでシーンごと消えた／現在シーンより後ろを指している）。次の `beginScene` で再確定される。
> - `freshSessionOf`（`cards.ts`）で `rawWindowFromSceneId` を落とす。参照切れなので残っても無視されるが、
>   配布物（カセット）に死んだ id を載せない。
> - PC-C のブレークポイント②は「履歴の末尾から4件手前」を**最終的な messages 配列の末尾から7件目**として
>   実装した。深さ3の1通・その後ろの履歴3件・深さ0の1通・呼び出し側の念押し1通＝**6件が毎ターン変わる**ので、
>   その手前になる。多めに数える方が安全（早すぎればキャッシュ範囲が少し狭まるだけだが、遅すぎると
>   毎ターン変わるメッセージを接頭辞に含めてブレークポイントが無駄になる）。

>   `currentSceneId` 不明・シーン0件・壊れた `previousFromSceneId` でも落ちない。
> - **階段状に畳む**: 12シーン連続で起点が動くのは2回だけ・動くときは1シーンより大きく跳ぶ・古い方へ戻らない。
> - `buildMessages`: 窓の範囲どおりに履歴が載る／橋が履歴の先頭に予算ぶんだけ載る／窓＝現在シーンでも橋は載る／

## 7.5 PC-A 追修 — JSON スキーマ（`response_format`）で裏方出力を固定する

2026-08-02 実装。**上位設計・本書のどちらにも無かった追加**（PC-A の再試行対策の延長）。

> **用語の注意**: 本プロジェクトの「**構造化出力**」（`Session.structuredOutput`・`docs/設計_構造化出力.md`）は
> 本文を `@名前「セリフ」` の行形式で書かせる別機能。ここで扱うのは API の `response_format`（json_schema）で
> **裏方 JSON を機械的に強制する**もので、本書では「**JSON スキーマ**」と呼び分ける。

### 7.5.1 なぜやるか

再試行の主因（§3 の R1）は JSON の崩れだった。`repairJsonText` は事後の修復だが、
**スキーマを送れる相手には最初から崩させない**方が根本的。summary 欠落・余計な前置き・
配列/オブジェクトの取り違えも同時に消える。

### 7.5.2 3段階のモードと降格（ここが設計の要点）

強制には**強さの違う3段**がある。相手に通る一番強い段を使う。

| モード | 送るもの | 保証されること |
|---|---|---|
| `schema` | `response_format:{type:'json_schema', strict}` | 項目・型まで固定 |
| `object` | `response_format:{type:'json_object'}` | **構文が壊れないことだけ**。§3 の R1（生の改行・末尾カンマ）はこれで消える |
| `none` | 何も付けない | 従来どおりプロンプト頼み |

**モデル名で系列判定してはいけない**——実測で `z-ai/glm` は12件中6件、`qwen/` は48件中40件しか
`structured_outputs` を申告しておらず、**同じ系列でもモデルごとに違う**（2026-08-02・OpenRouter `/models`）。

| 状況 | 初期モード |
|---|---|
| OpenRouter のモデル一覧を読み込み済み | `structured_outputs` あり→`schema` / `response_format` のみ→`object` / どちらも無し→`none`（**最優先・これが正**） |
| 一覧に申告が無い（直叩きの OpenAI 互換接続先・一覧未読込） | モデル名パターンが当たれば `schema` から試す（gpt/o系/gemini/claude/deepseek/qwen/kimi/glm）、外れれば `none` |
| 判定できない（例: `openrouter/auto`） | `none`＝従来どおり |

**外れても壊れないよう、`streamChat` が1段ずつ落として投げ直す**（`schema`→`object`→`none`）。
落とした先で通ったらそのモデルの上限として記憶し、以後は最初からその段で送る
（プロセス内のみ・非永続＝モデル側の対応は増えるので再起動で楽観に戻す）。

降格の判定は**エラー文言に頼らない**（401/403/429 以外の失敗はすべて降格を試す）。
ローカル/自前の OpenAI 互換サーバは `response_format` に触れない曖昧なエラー（`Invalid request` 等）を
返すことがあり、文言判定だと「対応していないのにエラーだけ出る」状態になるため。
認証・レート超過だけは明らかに別問題なので降格せずそのまま投げる。

**OpenRouter 以外の実例**:

| 接続先 | 結果 |
|---|---|
| OpenAI 直叩き | `json_schema` がそのまま通る |
| **DeepSeek 直叩き** | 公式ドキュメント上 `json_object` のみ（`json_schema` の記載なし・2026-08-02 確認）。1回目で弾かれて `object` に落ち着く＝**構文の崩れは防げる** |
| Groq・自前の OpenAI 互換（LM Studio 等） | 通る段まで自動で落ちる。何も通らなければ `none`＝従来と同じ挙動 |

> `json_object` は**メッセージ中に「JSON」の語が無いと 400 を返す**実装（OpenAI 等）があるため、
> スキーマを使う4種の system プロンプトすべてに語が含まれていることをテストで固定している。

`provider: { require_parameters: true }` を併せて送る（OpenRouter のみ）。F6 のとおり同一モデルでも
上流が分散するため、指定しないと**スキーマを無視する上流に当たった回だけ崩れる**という再現しない不具合になる。
（副次的に上流が絞られるので N2 のキャッシュ分散もいくらか減るはずだが、未計測。）

### 7.5.3 適用範囲とスキーマ

`jsonSchemas.ts` に集約。strict の制約（全 object に `additionalProperties:false`＋全プロパティ `required`）に
合わせ、省略可の項目は null 許容で表現する。

| 呼び出し | スキーマ | 備考 |
|---|---|---|
| レビュー A / B / 一括 | `reviewSchema(part)` | `reviewSystem` の part と1対1。A+B の項目が一括と一致することをテストで固定 |
| 選択肢 | `CHOICES_SCHEMA` | **strict の root は object 必須**なので `{choices:[…]}` に包む。`choicesSystem(mode, jsonSchema)` の書式指示も同じ形へ切替（指示とスキーマを食い違わせない）。`coerceChoices` は元からオブジェクト内の配列を拾うので受け側は無改修 |
| 次シーン候補 | `NEXT_SCENE_SCHEMA` | |
| 画像プロンプト起案 | `IMAGE_DRAFT_SCHEMA` | |

**本編（R1）には付けない**——散文を書かせる呼び出しなので対象外。

### 7.5.4 検証（2026-08-02）

- スキーマ定義: strict 規則（`additionalProperties`/`required`）を機械的に走査して全件合格。A+B=一括の項目一致も確認。
- 送信 body: OpenRouter では `response_format.json_schema.strict=true` ＋ `provider.require_parameters=true`、
  OpenAI 互換では `response_format` のみ（`provider` は付けない）。**モードを渡さない場合の body は従来と完全一致**。
- 降格: ①`json_schema` だけ拒否する疑似サーバ（DeepSeek 直叩き想定）→ `object` に落ちて成功、次回は最初から `object`。
  ②`response_format` 自体を曖昧なエラーで拒否する疑似サーバ（自前サーバ想定）→ `schema`→`object`→素と落ちて成功、
  次回は最初から素。③401 は降格せず即座に例外（握りつぶさない）。
- `json_object` の前提: スキーマを使う4種の system プロンプトすべてに「JSON」の語があることを確認。
- 実アプリ: 疑似 `/models` が `structured_outputs` を申告するモデルではレビュー A/B の両方にスキーマが載り、
  申告しないモデルでは**一切送らない**ことをサーバ側ログで確認。

## 8. 実測から出た新しい注意点（上位設計に無かったもの）

| # | 内容 | 影響 |
|---|---|---|
| **N1** | **キャッシュヒットは確率的**（F5）。同一リクエストでも 2% と 96% が混在する | 「効いているか」は**1回では判定できない**。PC0 の表は必ず**合計・平均**で見る。1リクエストの数字で一喜一憂しない |
| **N2** | **OpenRouter の既定ルーティングが上流を分散させる**（F6）。別上流に飛べばキャッシュはゼロ | 上流名を PC0 で記録する理由。将来 `provider.order` による固定を検討する余地はあるが、**可用性と引き換え**なのでユーザー設定にはしない |
| **N3** | **キャッシュ粒度がメッセージ単位**（F3） | system は「毎ターン byte 一致するか」の二値。**1文字でも動的な値を混ぜたら全損**。日付・トークン数・乱数などを system に入れないこと |
| **N4** | 深さ3（87%）と深さ0（95%）の差は**直近3件ぶん**＝約8ポイント | PC3 で原文窓を広げると分母が増えて割合の損は下がる（上位設計 §3.3 の予想どおり） |
| **N5** | `[DONE]` で早期 return すると usage を取りこぼす可能性 | PC0 の実装上の注意（§2.2） |
