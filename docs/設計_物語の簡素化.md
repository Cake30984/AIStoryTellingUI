# 設計_物語の簡素化（2026-09-07）

**作り込みの機構を全面的に降ろし、AI の即興に賭ける。** 世界観は「コンセプト＋少数のロア」だけを持ち、条件・数・到達目標・配役・特別イベント・固定タイムラインを廃止する。あわせて**ユーザーの立ち位置を「主人公」から「読者」へ変える**。

> **出発点となった3つの指摘（2026-09-05）**
>
> 1. **作り込みが凝るほど、AI を使う意義から外れる。** 求めているのは「その場で生成されたオリジナルのシナリオ／行動の結果で全く異なる分岐をたどる結末」であって、作者が先に書いた分岐ではない
> 2. **作り込みは生成の自然な流れを阻害し、文章の品質を下げる。** 条件による情報の解禁は、生成される文面が AI なだけでプロットは人間が考えたものと変わらない＝**オープンワールド性が損なわれる**
> 3. **ギャルゲという発想に引きずられた。** ターン制・時間帯の区切り・条件・エンディング・配役は、本質的テーマである「AI ラノベ」からのブレ。人力で設定するには面倒すぎる複雑さになっている

| ID | 内容 | 依存 | 状態 |
|---|---|---|---|

| **F2** | 時間と予定の作り直し（固定タイムライン廃止） | F1 | **実装済み（2026-09-07）** |

## 0. 判断の軸

**この変更は単なる簡素化ではなく、「作者の仕込み」を捨てて「AI の即興」に賭ける取引である。** 得るものと失うものを先に確定しておく。

| | 失うもの | 得るもの |
|---|---|---|
| 作者 | 分岐・到達目標・数値バランスの設計権 | 準備がほぼゼロになる（コンセプト＋少数のロア） |
| プレイヤー | 「目標へ向かう」構造・再現性 | 予測できない展開・オープンワールド性 |
| 実装 | 8月の G1〜G4・2026-08-30 の CG1/CG3 | `store.ts` の状態エンジンと `ConditionEditor` 全体 |

### 0.1 「設定が簡単になるとこの UI の必要性が薄まる」への答え

**薄まらない。価値の源泉が移る。**

今の暗黙の主張は「デリストは*作れる*から価値がある」（エディタの量＝価値）。新方針での主張は「デリストは*読める*から価値がある」。後者で残るもの——分岐ツリー・チェックポイント・シーン窓・レビューによる持ち越し・挿絵・書き出し・**状態が会話の外にあること**——は、素のチャット UI には無く、F1 の削除で1つも減らない（→ §7）。

**危険なのは逆側。** 設定を削った分の労力を読書体験へ移せなければ、本当に何も残らない。

## 2. 追加するもの

### 2.1 自由形式の現在時刻

```ts
// SessionState
now: string          // 「8月31日 夕方」「6月半ば」「翌年の春」
```

**コードは一切解釈しない**（比較も加算もしない）。暦を持たない世界があるので日付演算は最初から諦める。「過ぎたか」の判定も言語側（レビュー）で行うため、コードに `>` が必要な場所は1つも残らない。分岐で戻したときの巻き戻しはチェックポイントが担う。

```ts
// World
calendarFormat?: string   // 「◯月◯日／朝・昼・夕・夜」「第三紀・◯の月・◯日」
```

**書式見本を世界に1行だけ持たせる。** 無いとレビューが毎回違う書式を出し、「8月31日」と「夏の終わり」が混在する。**粒度は縛らない**（「◯月◯日」の書式でも「6月半ば」と書いてよい）——縛るとペース配分が死ぬ。

### 2.2 予定スリップ

```ts
interface PendingSlip {
  id: string
  /** 「8月31日」「6月後半」「降り続いた雨がやんだとき」。相対表現は書かない（§4.4） */
  when: string
  what: string
  /** 作られたシーン番号。棚卸しの表示にのみ使い、判定には使わない */
  bornAt: number
}
// SessionState
pending: PendingSlip[]
```

- **日時と条件を型で分けない。** 分けた瞬間に条件エンジンの再来になる
- **上限は設けない**（§4.2 の実測より）
- 更新操作は **`add` と `done` の2つだけ**。`update` は作らない（変更＝`done` してから `add`）
- `done` は即削除。ただし**状態パネルに数シーン残して見せる**——黙って消すと、レビューの誤判定で大事な予定が消えたときに気づけない

**「予定」より広い概念**（約束・締切・予兆・懸念）を含むため、内部名は `pending`（これから起きること）とする。

### 2.3 固定トラッカー枠

```ts
// SessionState — 毎レビューで上書き
now: string           // §2.1
place: string
presentIds: string[]  // 居合わせている人
situation: string     // 天候・季節・空気（1〜2行）
```

**可変なのは `pending` だけ。** 天候のように上書きされる情報は固定枠側に置く。「何を追跡するか」を LLM に毎回選ばせない——枠が変わると前回との差分が取れず、更新も削除もできなくなる（Tracker 系拡張が固定フィールドを持つ理由と同じ）。

### 2.3.1 「出来事の記録」（`happened`）は F2 に入れない

§1.2 で数のクランプを捨てることで、関係性が単調に良くなる**漂流**のリスクが残る。その代償措置として「取り返しのつかない出来事を追記専用で積む」案（`happened`）を検討したが、**F2 のスコープから外す**（2026-09-07 決定）。

理由は2つ。

1. **測定4.1 と同じ失敗をする恐れがある。** 溜まる一方の配列を本編プロンプトへ入れると「いま語るべき話題」として列挙される——それは `pending` で実証済みで、`happened` は `pending` より確実に溜まる
2. **漂流が実際に起きるかを、まだ測っていない。** 対策を先に入れるのは順序が逆

**F2 完了後に「30シーン走らせて関係性が単調に良くなるか」を実測し、起きることを確認してから設計する。** 起きた場合の候補は、上限つきの追記／プロンプトへ入れず表示専用／ユーザーによるピン留めの3つ（`authorNote` に近い役割）。`pending` だけで F2 は成立するので、これを落としても止まらない。

### 2.4 前景（照合済みの一文）と、時間・予定の呼び出し

```
本編（毎ターン・高頻度）         ← 照合済みの一文だけを受け取る
時間と予定の呼び出し（シーン境界） ← ここで現在時刻 × pending 全件を照合する
```

**照合はレビュー A/B とは別の第3の呼び出しに分ける**（2026-09-07 決定）。返すもの:

```
now:        "8月31日 朝"
place:      "祖母の家の縁側"
presentIds: [...]
situation:  "朝から晴れている。蝉の声"
foreground: "今日は8月31日、夏休みの最終日。今日中に東京へ帰らなければならない。"
done:       ["田舎から東京へ帰る"]   ← id ではなく what の引用（§2.4.2）
add:        [{ when, what }]
```

#### 2.4.1 注入する層

| 何を | どこへ | 理由 |
|---|---|---|
| `now`（現在時刻） | **system の【時間】ブロック** | シーン境界でしか変わらない＝`buildSystemPrompt` の層と一致し、キャッシュを壊さない。**実測B はこの構成で行った**（対照 W3 は現在時刻だけで 23/30 が正しく推論できている） |
| `foreground`（前景一文） | **深さ0** | 空なら何も入れない |
| `pending`（予定リスト） | **どこにも入れない** | §4.1。今回最大の単純化 |

> ❌ 「【現在】8月31日 /【控えていること】夏休み最終日: 東京へ帰る」→ 読み手が突き合わせる必要がある
> ✅ 「今日は8月31日、夏休みの最終日。今日中に東京へ帰らなければならない。」→ 突き合わせ済み

#### 2.4.2 なぜ第3の呼び出しに分けるか

| 案 | 帰結 |
|---|---|
| レビュー A（何が起きたか）に載せる | A へ `pending` を渡すことになり、**次シーン提案が予定リストに引きずられる**（§4.1 のレビュー版）。「A に状態変動の拘束を入れない」という既存の設計原則（[`prompts.ts:733`](../src/lib/prompts.ts)）を破る最初の例になる |
| レビュー B（状態がどう動いたか）に載せる | 原則は壊さないが **B が重くなる**（現状2フィールドに7つ追加）。並列2本の負荷が偏り、PC-A A-2 の「待ち時間半減」が薄れる |
| **第3の呼び出しに分ける（採用）** | **入力が小さいのが決め手**——照合に必要なのは本文＋`now`＋`pending` だけで、キャラ定義もロアも関係性も要らない。安いモデルに固定でき、3本並列なら待ち時間も増えない。責務が分かれ、失敗しても A/B が生きる。代償はシーン終了あたりのコスト約2割増 |

#### 2.4.3 消化（`done`）は id ではなく引用で指定する

`done` に id を返させるのは**実測で壊れた形**（§4.3・450回中50回）。取りこぼしなら予定が残るだけだが（棚卸しで拾える）、**誤爆は予定が消える＝害が大きい**。

**`what` の引用を返させ、コードが照合する。** 実測で id を落としたとき、モデルは `p01 いつ: 夏休み最終日 / なに: 田舎から東京へ帰る` と行全体を引用していた＝**この形式なら成功していた**。id の書き写しという苦手作業を、得意な引用に置き換える。

「残る予定を全部書き直させる」案は採らない。`relationUpdates` は落ちても次のシーンで復活できるが、**予定は消えたら戻らない**。

### 2.5 中心人物（`focusCharacterId`）

```ts
// Session
focusCharacterId: string   // 必須。null を許さない
```

| モード | 意味 |
|---|---|
| story（読者） | **その人の主観で書かれる**。ユーザーは読者に徹する |
| roleplay | **その人をユーザーが演じる**。入力はその人の発言 |

1フィールドで両方を賄う。**`null`（中心なしの三人称）は許さない**（2026-09-07 決定）。

理由は関係性の本数。ペルソナ廃止で `hero` という特別値が消えると全関係が characterId 対 characterId になり、中心が無ければ有向ペアは **N×(N−1) 通り**（3人で6、5人で20）。レビューが毎回全部書くのは非現実的で、状態パネルの表示も破綻する。中心を必須にすれば「全員→中心」＋「中心→全員」の **2(N−1) 本**に収まり、**現状とまったく同じ構造**になる＝実装が変わらない。

読者モデルは「主人公視点で書かれた読者」なので、そもそも中心人物が常に存在する前提である。三人称で書く場合も「誰を中心に据えるか」は決められる。**名前を `povCharacterId` ではなく `focusCharacterId` にするのは、視点だけでなく関係性の中心も兼ねるため。**

将来「実際に絡んだペアも拾う」を足すことは可能で、必須化とは排他ではない。

### 2.6 初期の予定スリップ

```ts
// World.startPreset
initialPending?: { when: string; what: string }[]
```

廃止した `ScheduledEvent` の受け皿。「3日目の夜に祭りがある」は `{ when: "3日目の夜", what: "町で祭りがある" }` として最初から積まれた1件になる。**条件なし・ID 参照なし・作者コストは2フィールド。**

### 2.7 任意タイミングのエンディング

いつでも「どんな終わり方があり得るか」を AI に提案させ（3〜5案）、

- 目標として保持する（以後ゆるい方向付けとしてプロンプトへ）
- その場で確定して終わる（エピローグ生成）
- 何も選ばない

世界側のエンディング定義は持たない。**提案の主体は AI、選ぶ主体はプレイヤー。**

### 2.8 文字数ベースの表示

| 用途 | 単位 |
|---|---|
| ユーザーに見せる長さ（シーンの分量・収束ナッジの閾値） | **文字数** |
| コストと文脈窓の管理 | **トークン** |

**選択制にはしない。** 「800字くらい」は直感的だが日本語のトークン係数は誰にも読めない。逆に窓とコストを文字数で管理すると計算が合わない。ユーザーに選ぶ基準がない設定は増やさない。

### 2.9 別視点の幕間

同じ場面を、主人公以外の人物の視点で描き直す（なろう系の幕間。特に**勘違い系**——主人公は無自覚だが、他者から見ると神業や自己犠牲に映るという型）。**実測済み**（[`計測_別視点の幕間.md`](./計測_別視点の幕間.md)）。

```ts
// Scene
interludes?: { characterId: string; text: string; createdAt: number }[]
```

#### 2.9.1 なぜこの設計と相性がいいのか

1. **状態管理の問題ではなく書き換えの問題。** LLM が弱いのは時間をまたいだ帳簿合わせで、測定でもそこだけが壊れた。幕間は一発生成・読み専用で、その軸に触れない
2. **材料がすでにある。** 削除後に残る `relations` は有向ペアの prose＝**「X が Y をどう見ているか」**そのもの。幕間は `relation[その人物 → 中心]` を読んで書く
3. **関係の保持数は増えない。** §2.5 の中心必須構造（2(N−1) 本）がそのまま材料を出す。**幕間は保持している関係を読む機能であって、新しく保持する機能ではない**——`focusCharacterId` の必須化を否定するどころか前提にする

#### 2.9.2 仕様

| 項目 | 決め |
|---|---|
| 起動 | ユーザーが明示的に要求したときだけ（シーンごと・人物ごと）。**終了したシーンにしか作れない**（2026-09-09 改訂・下記） |
| 入力 | そのシーンの本文＋その人物の定義＋`relation[その人物 → 中心]`＋`now`／`place` |
| 対象 | 既定は `presentIds` の人物。遠くから見ていた設定も許すが既定には出さない |
| 状態への書き込み | **しない。** レビューも第3の呼び出しも走らせない |
| 本編プロンプト | **積まない。** 窓にもキャッシュにも影響しない |
| 再生成 | 何度でも（読者モデルの主操作と同じ扱い） |
| 書き出し | `storyExport` には幕間として含める |
| **後処理** | **本文冒頭の見出し（`#` で始まる行）を削る**（実測で 13%。§4.7） |

#### 2.9.2.1 単位はシーン丸ごと1本（2026-09-09 改訂）

**当初は「シーンごと・人物ごと」とだけ決めていたが、進行中のシーンでも作れる実装になっていた。**
実使用で不具合として現れた——幕間を作ってから「続ける」で本文を足すと、
**新しい本文が幕間の手前に入り、読む順序が壊れる**。

最初に検討した対策は「幕間を生成時点の本文へアンカーする」（挿絵の `messageId` と同じ規約）。
位置は直るが、**範囲が不整合なまま残る**ので撤回した——幕間の対象はシーン先頭から生成時点までなので、
シーン途中で作ると「話の途中まで」を書き直した半端な1本になり、続けてもう一度作ると
前半を含めて二重に書き直すことになる。

採ったのは**シーン終了後のみに制限する**案。根拠は媒体の慣習にある。

> **1シーンはなろう系の1話に相当し、他者視点は話の途中に挿さるものではなく、
> 独立した1話として後ろに置かれる。**

これで3つが同時に片づく。

| | |
|---|---|
| 位置 | シーンが閉じているので**もう本文が増えない**＝末尾が動かない |
| 範囲 | 常に**シーン1つ丸ごと**＝話として完結した単位を書き直す |
| 引き直し | 何度引いても同じ範囲。前半だけを重ねて書き直す事故が起きない |

判定は `isSceneClosed(session, scene)`（`endedAt` があるか、現在シーンでないか）。
進行中のシーンでは入口を**隠さず無効にして理由をその場に書く**
（「別の視点で読む（このシーンを終えると使えます）」）＝黙って隠すと機能が無いように見えるため。

#### 2.9.3 捏造の線引き

3種類に分けて、3番目だけを禁じる。

| 種類 | 扱い |
|---|---|
| **解釈の追加**（同じ出来事を別様に受け取る） | **常に許す**（これが本体） |
| **観察の追加**（主人公が見ていないものをその人物は見ていた） | **許す。** 幕間の面白さはここにある |
| **世界設定・過去の出来事の捏造** | 禁じる（ただし実測では 3〜7% と稀） |

**この緩い規則が許せるのは、幕間が読み専用だから。** 何を書いても本編の状態は汚れない。

#### 2.9.4 正典性

**既定は非正典（読み物）。** 気に入った解釈だけ、ユーザーが「この幕間の解釈を関係性へ反映する」ボタンで取り込む——`characterGrowth` の承認と同じ形なので、UI もコードも既存の型で済む。これで「後から本編と矛盾した」問題が起きない。

## 3. 読者モデル（入力の意味論の変更）

### 3.1 何が問題だったか

ユーザーが「右腕を上げる」と入力しても、AI が行間を埋めた結果は必ずしもイメージと一致しない。これは**入力の意味論の不一致**であって、プロンプトの改善では消えない。

| | ユーザーの意図 | システムの解釈 |
|---|---|---|
| ロールプレイ入力 | 「わたしはこうした」＝**確定した事実** | 「こう書いてほしい」＝**要望**としてしか受け取れない |

読者モデルはこの不一致を**定義から消す**。すべての入力は書き手への指示であり、ユーザーはその世界の住人としてロールプレイしない。

`docs/公開計画_マネタイズと配布.md` §0 の位置づけ（「ノベルゲームではなく挿絵入りの本」）とも一致する——**むしろ従来のロールプレイ入力の方が位置づけとズレていた。**

### 3.2 操作系

| 操作 | 意味 |
|---|---|
| **続ける** | 主操作。入力なしで次を書かせる |
| **再生成** | 気に入らなければ引き直す（＝ふつうの操作になる） |
| **尺の指示** | 〈もっと詳しく〉〈先へ飛ばす〉を常設ボタンに |
| **書き手への指示** | 何度か引き直しても駄目なとき、方向を指示として注入 |

**尺の指示が一級市民になるのが最大の副産物。** ロールプレイ入力では尺の指示はメタ発言＝世界観を壊す異物だが、すべての入力が書き手への指示なら自然に置ける。§1.6 で捨てるスロット単位のペース配分は、ここで取り戻す。

**再生成が主操作になる副作用**: 分岐ツリーの価値が上がる（枝が自然に増える）一方、**課金コストがユーザーの目に見える形で増える**。§2.8 の表示の話と直結する。

### 3.3 モード境界の原則

**`SessionMode` の `roleplay` は残す**（単体キャラとの会話を楽しむ別軸）。ただし:

> **モードで分けるのは「入力の意味論」と「操作系」だけ。機構（シーン・レビュー・時間・予定・分岐）は両モードで共通に通す。**

ここを分けると二重実装になり、削った複雑さがモード分岐として戻ってくる。

### 3.4 選択肢

`ChoiceMode`（`'off' | 'always' | 'auto'`）を**型ごと廃止**し、「続ける」の隣の〈展開を選ぶ〉ボタン1つにする（オンデマンド生成）。

- `always` は「続ける」が主操作なら大半が捨てられる＝無駄なコスト
- `auto` は判断のための呼び出しが要る上に外れる。オンデマンドなら外れようがない
- 設定項目が1つ減る

`NextSceneSuggestion`（シーン境界・レビューがついでに返す）とは**統合しない**。読者モデルでは両方「書き手への提案」で意味は同じだが、粒度と生成コストが違う（次シーン提案は追加コストなし、選択肢は専用の呼び出しが要る）。UI の見た目だけ揃える。

> `docs/公開計画_マネタイズと配布.md` §0 の成長レバー「インタラクション密度」とは矛盾しない。「続ける」を押すこと自体が毎回の操作なので密度は保たれる。

### 3.5 出力形式は現状維持

`narrativeStyle`（`novel`/`chat`）と `structuredOutput`（`@名前「セリフ」` の行形式）は**独立した2軸**で、既定は story→`novel`＋構造化 ON、roleplay→`chat`＋構造化 ON（[`store.ts:1102`](../src/store.ts)）。読者モデルは入力側の話なので衝突しない。**今回は触らない。**

> 将来の安いトリム: `narrativeStyle` は既にモードから導出しており、ユーザー設定から外せば項目がもう1つ減る。

## 4. 実測が決めたこと

詳細は [`計測_時間と予定.md`](./計測_時間と予定.md)（2026-09-06・1214呼び出し・$0.153）。

### 4.1 予定リストを本編へ常時注入してはいけない（→ §2.4）

該当予定が無い時点で、15件のリストを本編プロンプトへ入れると **28/30** が無関係な先の予定（七回忌・衣替え・12月24日の待ち合わせ）を本文に列挙した。リスト無しの対照は **0/30**。

判別力のある場面での比較:

| 本編へ渡すもの | 触れてほしい予定に触れた | 無関係な予定が漏れた |
|---|---|---|
| 現在だけ | 6/30 | 0/30 |
| リスト15件 | 27/30 | **17/30** |
| リスト＋前景一文 | 30/30 | 6/30 |
| **前景一文のみ** | **26/30** | **0/30** |

**リストは背景情報として静かに保持されない。「いま語るべき話題」として読まれる。**

### 4.2 件数の上限は不要（→ §2.2）

照合精度は 3件 91% / 8件 86% / 15件 89%。**「件数が増えると取りこぼす」という事前の仮説は外れた。** 当初案の「上限8件」は撤回。

### 4.3 照合に id を返させない（→ §2.4）

`foreground` の文で採点すると 86〜91%、`fire`（id 配列）で採点すると 74〜81%。差の正体は読解ではなく帳簿で、**450回中50回が「文は当たっているのに id を書き落とす」**。→ レビューには前景の一文だけを書かせる。`done` の判定は別の呼び出しに分ける。

### 4.4 相対表現は書かせない（→ §2.2）

「来週水曜」「三日後の夜」は 30回中2回しか発火せず、その2回とも誤り（基準日が無いので解釈できない）。→ 本文に「来週水曜に会う約束をした」と出たら、**記録する時点で絶対表現へ解決する**。

### 4.5 条件つきは「状態」として読まれる（→ ガイドへ）

「雨が止んだら」は雨が降っていない平時のあいだずっと成立し、「冬になる前」は秋のあいだずっと成立する。害ではない（「6月後半に中間試験」が6月後半じゅう出続けるのは正しい）が、**書き方の指針が要る**。

- **点**（8月31日・明日）→ その時だけ出る
- **遷移**（降り続いた雨が**やんだとき**）→ 一度だけ出やすい
- **幅**（冬になる前・6月後半）→ その期間ずっと出続ける

「一度きり」にしたいなら遷移で書く。**機構は不要、ガイドの1節で済む。**

### 4.6 照合の入力に場面の状況は要らない

固定枠（場所・居合わせている人・状況）を照合へ足しても誤発火は減らなかった（23/30 → 25/30）。フラグの立った12件を人手で読んだ結果、**判断そのものを誤っていたものは無い**（フィクスチャの曖昧さと §4.3 の帳簿の失敗）。固定枠は表示と引き継ぎのために残すが、**照合のための入力ではない**。

### 4.7 別視点の幕間（→ §2.9）

詳細は [`計測_別視点の幕間.md`](./計測_別視点の幕間.md)（2026-09-07・491呼び出し・$0.095）。

**⚠ 数字は破棄した。** 「解釈が異なるか」という構文は安い判定 LLM では測れず、段階指標が 0/4 の二値へ退化した上で**両方向に誤った**（解釈ゼロの言い換えに偽陽性9/30・手読みで明確なギャップがある11件を偽陰性）。採用したのは手読み12件と語の出現だけ。

| 事前の想定 | 実測後 |
|---|---|
| 「言い換えに潰れる」のが最大の失敗モード | **起きなかった。** 最弱条件（薄い prose・指示なし）でも読んだ4件すべてにギャップが出た。**素材が勘違い系の構造を持てば、視点を移すだけでギャップが生まれる** |
| 効くのは指示文ではなく関係 prose の濃さ（前2回の実測からの類推） | **どちらも決め手ではない。** prose は「ギャップの有無」ではなく**具体性**に効く（過去の類似場面を持ち込む）。指示は害が無いので入れてよいが、それ頼みにしない |
| 捏造の抑制が要る | **稀**（元の場面に無い出来事の混入は 3〜7%・条件差なし）。読み専用で運用するなら実害はさらに小さい |
| — | **見出しの混入 13% に後処理で対処する**（§2.9.2） |
| — | **この機能の品質は自動では測れない。** 実装後の確認は人手で読む前提にする |

**F3 実装時の補足**: 型は `string | null` ではなく **`string`** にし、**空文字＝未選択**とした。

- 中心人物も `characterBlock` でフル定義（口調・外見・セリフ例）が入る。

**関係性の本数は N−1 のままにした。** §2.5 は上限として 2(N−1) を挙げているが、
「中心→全員」の向きは今のレビューが書いていない。F3 の範囲は
「宛先を `'hero'` から `focusCharacterId` へ移す」ことなので、向きは増やしていない
（F6 が読むのは `relation[その人物 → 中心]` ＝既存の向きなので、これで足りる）。

## 6. 実装フェーズ

**F1 → F2 → F3 → F4 → F5。** 各フェーズごとに `npx tsc --noEmit` → `npm run build`。Tauri 固有部を触った時のみ `npm run tauri:dev` の手動チェックリストも実施。

### F1 削除（条件・数・目標・配役・特別イベント）

**最初に置く理由**: F2 の予定スリップは特別イベントの受け皿なので、先に消しておかないと二重になる。また互換性不要（`lib/schema.ts` の移行チェーンごと捨てる）なので、この段階でコードが最も減る。

削除の順序は **UI → store → types**（参照する側から）。

1. `ConditionEditor` / `WorldEditor` の該当タブ / `SessionEditor` の配役 UI / `StatusPanel`・`StatusView` の数・実績・結末 / `OpeningBriefing` / `SceneReviewModal` の数の増減
2. `store.ts` の条件エンジン（`matchGroups`／`evalCondition`／`ConditionContext`／`gateLoreByCondition`／キャラゲート／実績解除／エンディング到達／イベント発火）・`casting.ts`
3. `types.ts` の該当型・`prompts.ts` の注入・`jsonSchemas.ts` のレビュースキーマ・`cards.ts` の入出力・`schema.ts` のリセット

### F2 時間と予定

固定タイムライン廃止と `now`/`pending` 導入は**同時でないと動かない**（`Scene.timeLabel` の置き換えを含む）。実測で形が決まっているので設計上の未決は少ない。

1. 型（`SessionState` の新フィールド・`PendingSlip`・`TrackerResult`・`World.calendarFormat`・`initialPending`）
2. **第3の呼び出し**（時間と予定）のプロンプトとスキーマ。A/B と並列に投げる。既定モデルは安いものに固定
3. 本編プロンプト（**`now` は system の【時間】へ**・深さ0へ `foreground` の一文のみ・**`pending` は渡さない**）
4. 状態パネル（現在・場所・居合わせている人・これから起きること・消化した予定）
5. `pendingDone` の引用照合（`what` の部分一致。曖昧なら消さずに残す）

### F3 ペルソナ統合

`Persona` → `Character`、`personaId` → `focusCharacterId`（**必須化**）、`Relation.toId` の `'hero'` 廃止。素材ライブラリが1種類減る。

### F4 読者モデル

入力の意味論の変更・操作系（続ける／再生成／尺の指示／書き手への指示）・`ChoiceMode` 廃止と〈展開を選ぶ〉ボタン・エンディング提案。

**F4 実装時の補足**

| 決めたこと | 中身 |
|---|---|
| 入力の二分化（IN1）は **roleplay にだけ残す** | 物語モードは入力の意味が1つに定まったので**選ばせるものが無い**（チップを撤去し、すべて `kind: 'directive'` で積む）。roleplay は「演じて書く／書き手に指示」のままで、§3.3 の「モードで分けるのは入力の意味論と操作系だけ」に従う |
| 尺の指示は**進行マーカー**として積む | `PACE_DETAIL_PROMPT` / `PACE_SKIP_PROMPT` を `CONTINUE_PROMPT` と同じ枠で履歴に入れ、表示・書き出し・ツリーのラベルから外す。判定は `MARKER_PROMPTS`／`isMarkerContent` の**1箇所**に集約した（従来は ChatPanel・storyExport・store の3箇所に同じ条件が散っていた） |

| 提案の文脈は選択肢と同じ圧縮文脈 | `choicesMessages` を再利用する。結末の相談に効くのは「誰が居て・関係がどうで・何があったか」だけなので、本編の system も履歴全文も要らない（PC2'） |

### F6 別視点の幕間

`Scene.interludes`・生成の呼び出し・見出しの後処理・「関係性へ反映」ボタン・`storyExport` への同梱。**F3（中心人物の必須化）と F4（読者モデル）の両方に依存する。**

これは §0.1 で挙げたリスク——「設定を削った分の労力を読書体験へ移せなければ何も残らない」——への具体的な回答の1つ目にあたる。

**F6 実装時の補足**

| 決めたこと | 中身 |
|---|---|
| 見出しは**二重に**防ぐ | プロンプトで禁じたうえで `stripInterludeHeadings` でも削る（実測 13%）。削るのは**先頭の連続する見出し・区切り・強調だけの行**に限り、本文中の `#` は触らない＝削りすぎない |
| 生成に渡す文脈は§2.9.2どおり4点だけ | そのシーンの本文（`isStoryText` でマーカーと指示を除く）＋視点人物の定義＋`relation[その人物 → 中心]`＋時と場所。**本編の system も履歴全文も使わない**（一発生成・読み専用なので要らない） |
| 候補は中心人物を除いた参加キャラ | `presentIds` の人物を**先頭に並べる**（除外はしない）。`presentIds` は現在シーンの状態なので、過去シーンでは並び順が効かないだけで壊れない |
| 「関係性へ反映」は**承認制の一段** | 幕間の本文＋現在の関係＋次元名を渡して `{stance, aspects}` を作らせ、**ユーザーが承認したときだけ** `applyReviewToState` へ流す（レビューの `relationUpdates` と同じ型・同じ適用経路＝新しい書き込み口を増やさない） |
| 「引き直す」は置き換えではなく**追加** | 読者モデルでは再生成が主操作なので、前の解釈も残して読み比べられる方がよい。要らない方は削除できる |
| 出しどころは story モードのみ | roleplay は単体キャラとの会話が主で、「中心人物を外から見る」構図が成立しない |
| **終了したシーンにしか作れない**（2026-09-09 改訂） | 実使用で「続ける」の本文が幕間の手前に入る不具合として現れた。アンカー方式を検討したが範囲の不整合が残るため撤回し、**1シーン＝1話・幕間は独立した1話**という媒体の慣習に合わせた（→ §2.9.2.1） |

**⚠ この機能の品質は自動では測れない**（`計測_別視点の幕間.md` §4）。安い判定 LLM は「解釈が異なるか」を両方向に誤る。実運用の確認は**人が読む**前提にする。

### F5 仕上げ

文字数表示・`カセット作成ガイド_AI用.md` の全面書き直し（**大半が消えて短くなるのが成果**）・`AGENTS.md` の更新。

|---|---|

| 案 | 理由 |
|---|---|
| **特別イベントを `day`/`slot` だけ残す**（当初の推奨） | **撤回**。固定タイムラインを廃止すると座標系が無くなる。初期の予定スリップ（§2.6）が受け皿になる |
| **予定を上限8件にする**（当初の設計） | **撤回**。件数は精度にほぼ効かなかった（§4.2） |
| **予定リストを背景として常時注入する**（当初の設計） | **撤回**。有害だった（§4.1） |
| **照合の入力に場面の状況を足す**（当初の推奨） | **撤回**。照合精度は変わらなかった（§4.6）。固定枠は別の理由で残す |
| 条件を自然文で書かせてレビューに判定させる | 「作者が条件を書く」構造自体が廃止対象。形を変えて残す意味がない（§1.1） |
| 予定を `LoreEntry` と同じ配列に入れる | 寿命が違う（ロアは不変・予定は必ず消える）／注入位置が違う（深さ3 vs 深さ0）／`SessionOverlay.lore` が予定で埋まる |

| 数の状態を prose の band（5段階の言葉）で残す | `Relation` が既に band を捨てて prose 一本で成立している。二の轍 |

| 時間と予定をレビュー A または B に載せる | A は次シーン提案が予定に引きずられ、B は負荷が偏る。第3の呼び出しに分ける（§2.4.2） |

| 残る予定を毎回全文書き直させる | 黙って落ちる事故が致命的。関係性と違い**予定は消えたら戻らない**（§2.4.3） |
| `roleplay` では `pending` を使わない | `pending` は本編へ出ないので使っても副作用はほぼ無い。避けて得るのは第3呼び出しのコストだけで、そのためにモード分岐を増やすのは割に合わない（§3.3） |
| 深さ0へ現在時刻を毎ターン入れる | `now` はシーン境界でしか変わらない＝system の層。深さ0は「毎ターン変わるもの」の層（§2.4.1） |
| `happened` を F2 で入れる | 溜まる配列を本編へ入れる失敗は実証済み。漂流が起きることを測ってから設計する（§2.3.1） |
| `focusCharacterId` に `null`（中心なし）を許す | 関係性が N×(N−1) に膨らむ。中心必須なら現状と同じ 2(N−1) 本（§2.5） |
| 幕間を正典（状態へ書き戻す）にする | 本編と矛盾する。既定は非正典にし、ユーザーが選んだときだけ関係性へ反映する（§2.9.4） |
| 幕間で「観察の追加」を禁じる | 幕間の面白さはそこにある。読み専用なので本編は汚れない。禁じるのは世界設定・過去の出来事の捏造だけ（§2.9.3） |
| 幕間の品質を判定 LLM で自動確認する | **測れなかった**（§4.7）。実装後の確認は人手で読む |
