# 設計_物語の簡素化（2026-09-07）

**作り込みの機構を全面的に降ろし、AI の即興に賭ける。** 世界観は「コンセプト＋少数のロア」だけを持ち、条件・数・到達目標・配役・特別イベント・固定タイムラインを廃止する。あわせて**ユーザーの立ち位置を「主人公」から「読者」へ変える**。

> **出発点となった3つの指摘（2026-09-05）**
>
> 1. **作り込みが凝るほど、AI を使う意義から外れる。** 求めているのは「その場で生成されたオリジナルのシナリオ／行動の結果で全く異なる分岐をたどる結末」であって、作者が先に書いた分岐ではない
> 2. **作り込みは生成の自然な流れを阻害し、文章の品質を下げる。** 条件による情報の解禁は、生成される文面が AI なだけでプロットは人間が考えたものと変わらない＝**オープンワールド性が損なわれる**
> 3. **ギャルゲという発想に引きずられた。** ターン制・時間帯の区切り・条件・エンディング・配役は、本質的テーマである「AI ラノベ」からのブレ。人力で設定するには面倒すぎる複雑さになっている

| ID | 内容 | 依存 | 状態 |
|---|---|---|---|
| **F1** | 条件エンジン・数・到達目標・配役・特別イベントの削除 | なし | 未着手 |
| **F2** | 時間と予定の作り直し（固定タイムライン廃止） | F1 | 未着手（**実測済み**） |
| **F3** | ペルソナを Character へ統合・POV の導入 | F1 | 未着手 |
| **F4** | 読者モデル（入力の意味論の変更）・選択肢のオンデマンド化・エンディング | F3 | 未着手 |
| **F5** | 文字数表示・ガイド書き直し・AGENTS.md | F1〜F4 | 未着手 |

**互換性は考慮しない**（未公開のため。2026-09-06 決定）。`lib/schema.ts` の移行チェーンは捨ててバージョンをリセットし、開発中の既存セッション・カセットは読めなくなってよい。これにより F1 の削除は「読み捨て処理を書く」ではなく**純粋な削除**になる。

## 0. 判断の軸

**この変更は単なる簡素化ではなく、「作者の仕込み」を捨てて「AI の即興」に賭ける取引である。** 得るものと失うものを先に確定しておく。

| | 失うもの | 得るもの |
|---|---|---|
| 作者 | 分岐・到達目標・数値バランスの設計権 | 準備がほぼゼロになる（コンセプト＋少数のロア） |
| プレイヤー | 「目標へ向かう」構造・再現性 | 予測できない展開・オープンワールド性 |
| 実装 | 8月の G1〜G4・2026-08-30 の CG1/CG3 | `store.ts` の状態エンジンと `ConditionEditor` 全体 |

### 0.1 「設定が簡単になるとこの UI の必要性が薄まる」への答え

**薄まらない。価値の源泉が移る。**

今の暗黙の主張は「デリストは*作れる*から価値がある」（エディタの量＝価値）。新方針での主張は「デリストは*読める*から価値がある」。後者で残るもの——分岐ツリー・チェックポイント・シーン窓・レビューによる持ち越し・挿絵・書き出し・**状態が会話の外にあること**——は、素のチャット UI には無く、F1 の削除で1つも減らない（→ §7）。

**危険なのは逆側。** 設定を削った分の労力を読書体験へ移せなければ、本当に何も残らない。

## 2. 追加するもの

### 2.1 自由形式の現在時刻

```ts
// SessionState
now: string          // 「8月31日 夕方」「6月半ば」「翌年の春」
```

**コードは一切解釈しない**（比較も加算もしない）。暦を持たない世界があるので日付演算は最初から諦める。「過ぎたか」の判定も言語側（レビュー）で行うため、コードに `>` が必要な場所は1つも残らない。分岐で戻したときの巻き戻しはチェックポイントが担う。

```ts
// World
calendarFormat?: string   // 「◯月◯日／朝・昼・夕・夜」「第三紀・◯の月・◯日」
```

**書式見本を世界に1行だけ持たせる。** 無いとレビューが毎回違う書式を出し、「8月31日」と「夏の終わり」が混在する。**粒度は縛らない**（「◯月◯日」の書式でも「6月半ば」と書いてよい）——縛るとペース配分が死ぬ。

### 2.2 予定スリップ

```ts
interface PendingSlip {
  id: string
  /** 「8月31日」「6月後半」「降り続いた雨がやんだとき」。相対表現は書かない（§4.4） */
  when: string
  what: string
  /** 作られたシーン番号。棚卸しの表示にのみ使い、判定には使わない */
  bornAt: number
}
// SessionState
pending: PendingSlip[]
```

- **日時と条件を型で分けない。** 分けた瞬間に条件エンジンの再来になる
- **上限は設けない**（§4.2 の実測より）
- 更新操作は **`add` と `done` の2つだけ**。`update` は作らない（変更＝`done` してから `add`）
- `done` は即削除。ただし**状態パネルに数シーン残して見せる**——黙って消すと、レビューの誤判定で大事な予定が消えたときに気づけない

**「予定」より広い概念**（約束・締切・予兆・懸念）を含むため、内部名は `pending`（これから起きること）とする。

### 2.3 固定トラッカー枠と出来事の記録

```ts
// SessionState — 毎レビューで上書き
now: string           // §2.1
place: string
presentIds: string[]  // 居合わせている人
situation: string     // 天候・季節・空気（1〜2行）
/** 追記専用。取り返しのつかない出来事を積む（上書きしない） */
happened: { text: string; bornAt: number }[]
```

**可変なのは `pending` と `happened` だけ。** 天候のように上書きされる情報は固定枠側に置く。「何を追跡するか」を LLM に毎回選ばせない——枠が変わると前回との差分が取れず、更新も削除もできなくなる（Tracker 系拡張が固定フィールドを持つ理由と同じ）。

`happened` は §1.2 で失う不可逆性の代償措置。**規則ではなく記憶**なので「こうしたら、こうさせる」の廃止と矛盾しない。コードは判定に使わず、プロンプトへ入れるだけ。

### 2.4 前景（照合済みの一文）

```
本編（毎ターン・高頻度）      ← 照合済みの一文だけを受け取る
レビュー（シーン境界・低頻度） ← ここで現在時刻 × pending 全件を照合する
```

レビューが返すもの:

```
now:        "8月31日 朝"
foreground: "今日は8月31日、夏休みの最終日。今日中に東京へ帰らなければならない。"
done:       [消化した予定]
add:        [新しく生まれた予定]
```

本編の深さ0へ入れるのは **`foreground` の一文だけ**。空なら何も入れない。

> ❌ 「【現在】8月31日 /【控えていること】夏休み最終日: 東京へ帰る」→ 読み手が突き合わせる必要がある
> ✅ 「今日は8月31日、夏休みの最終日。今日中に東京へ帰らなければならない。」→ 突き合わせ済み

**`pending` は本編プロンプトへ出さない**（§4.1 の実測より。これが今回最大の単純化）。

### 2.5 視点（POV）

```ts
// Session
povCharacterId: string | null
```

| モード | 意味 |
|---|---|
| story（読者） | **その人の主観で書かれる**。ユーザーは読者に徹する |
| roleplay | **その人をユーザーが演じる**。入力はその人の発言 |

1フィールドで両方を賄う。`null` は三人称（story のみ）。

### 2.6 初期の予定スリップ

```ts
// World.startPreset
initialPending?: { when: string; what: string }[]
```

廃止した `ScheduledEvent` の受け皿。「3日目の夜に祭りがある」は `{ when: "3日目の夜", what: "町で祭りがある" }` として最初から積まれた1件になる。**条件なし・ID 参照なし・作者コストは2フィールド。**

### 2.7 任意タイミングのエンディング

いつでも「どんな終わり方があり得るか」を AI に提案させ（3〜5案）、

- 目標として保持する（以後ゆるい方向付けとしてプロンプトへ）
- その場で確定して終わる（エピローグ生成）
- 何も選ばない

世界側のエンディング定義は持たない。**提案の主体は AI、選ぶ主体はプレイヤー。**

### 2.8 文字数ベースの表示

| 用途 | 単位 |
|---|---|
| ユーザーに見せる長さ（シーンの分量・収束ナッジの閾値） | **文字数** |
| コストと文脈窓の管理 | **トークン** |

**選択制にはしない。** 「800字くらい」は直感的だが日本語のトークン係数は誰にも読めない。逆に窓とコストを文字数で管理すると計算が合わない。ユーザーに選ぶ基準がない設定は増やさない。

## 3. 読者モデル（入力の意味論の変更）

### 3.1 何が問題だったか

ユーザーが「右腕を上げる」と入力しても、AI が行間を埋めた結果は必ずしもイメージと一致しない。これは**入力の意味論の不一致**であって、プロンプトの改善では消えない。

| | ユーザーの意図 | システムの解釈 |
|---|---|---|
| ロールプレイ入力 | 「わたしはこうした」＝**確定した事実** | 「こう書いてほしい」＝**要望**としてしか受け取れない |

読者モデルはこの不一致を**定義から消す**。すべての入力は書き手への指示であり、ユーザーはその世界の住人としてロールプレイしない。

`docs/公開計画_マネタイズと配布.md` §0 の位置づけ（「ノベルゲームではなく挿絵入りの本」）とも一致する——**むしろ従来のロールプレイ入力の方が位置づけとズレていた。**

### 3.2 操作系

| 操作 | 意味 |
|---|---|
| **続ける** | 主操作。入力なしで次を書かせる |
| **再生成** | 気に入らなければ引き直す（＝ふつうの操作になる） |
| **尺の指示** | 〈もっと詳しく〉〈先へ飛ばす〉を常設ボタンに |
| **書き手への指示** | 何度か引き直しても駄目なとき、方向を指示として注入 |

**尺の指示が一級市民になるのが最大の副産物。** ロールプレイ入力では尺の指示はメタ発言＝世界観を壊す異物だが、すべての入力が書き手への指示なら自然に置ける。§1.6 で捨てるスロット単位のペース配分は、ここで取り戻す。

**再生成が主操作になる副作用**: 分岐ツリーの価値が上がる（枝が自然に増える）一方、**課金コストがユーザーの目に見える形で増える**。§2.8 の表示の話と直結する。

### 3.3 モード境界の原則

**`SessionMode` の `roleplay` は残す**（単体キャラとの会話を楽しむ別軸）。ただし:

> **モードで分けるのは「入力の意味論」と「操作系」だけ。機構（シーン・レビュー・時間・予定・分岐）は両モードで共通に通す。**

ここを分けると二重実装になり、削った複雑さがモード分岐として戻ってくる。

### 3.4 選択肢

`ChoiceMode`（`'off' | 'always' | 'auto'`）を**型ごと廃止**し、「続ける」の隣の〈展開を選ぶ〉ボタン1つにする（オンデマンド生成）。

- `always` は「続ける」が主操作なら大半が捨てられる＝無駄なコスト
- `auto` は判断のための呼び出しが要る上に外れる。オンデマンドなら外れようがない
- 設定項目が1つ減る

`NextSceneSuggestion`（シーン境界・レビューがついでに返す）とは**統合しない**。読者モデルでは両方「書き手への提案」で意味は同じだが、粒度と生成コストが違う（次シーン提案は追加コストなし、選択肢は専用の呼び出しが要る）。UI の見た目だけ揃える。

> `docs/公開計画_マネタイズと配布.md` §0 の成長レバー「インタラクション密度」とは矛盾しない。「続ける」を押すこと自体が毎回の操作なので密度は保たれる。

### 3.5 出力形式は現状維持

`narrativeStyle`（`novel`/`chat`）と `structuredOutput`（`@名前「セリフ」` の行形式）は**独立した2軸**で、既定は story→`novel`＋構造化 ON、roleplay→`chat`＋構造化 ON（[`store.ts:1102`](../src/store.ts)）。読者モデルは入力側の話なので衝突しない。**今回は触らない。**

> 将来の安いトリム: `narrativeStyle` は既にモードから導出しており、ユーザー設定から外せば項目がもう1つ減る。

## 4. 実測が決めたこと

詳細は [`計測_時間と予定.md`](./計測_時間と予定.md)（2026-09-06・1214呼び出し・$0.153）。

### 4.1 予定リストを本編へ常時注入してはいけない（→ §2.4）

該当予定が無い時点で、15件のリストを本編プロンプトへ入れると **28/30** が無関係な先の予定（七回忌・衣替え・12月24日の待ち合わせ）を本文に列挙した。リスト無しの対照は **0/30**。

判別力のある場面での比較:

| 本編へ渡すもの | 触れてほしい予定に触れた | 無関係な予定が漏れた |
|---|---|---|
| 現在だけ | 6/30 | 0/30 |
| リスト15件 | 27/30 | **17/30** |
| リスト＋前景一文 | 30/30 | 6/30 |
| **前景一文のみ** | **26/30** | **0/30** |

**リストは背景情報として静かに保持されない。「いま語るべき話題」として読まれる。**

### 4.2 件数の上限は不要（→ §2.2）

照合精度は 3件 91% / 8件 86% / 15件 89%。**「件数が増えると取りこぼす」という事前の仮説は外れた。** 当初案の「上限8件」は撤回。

### 4.3 照合に id を返させない（→ §2.4）

`foreground` の文で採点すると 86〜91%、`fire`（id 配列）で採点すると 74〜81%。差の正体は読解ではなく帳簿で、**450回中50回が「文は当たっているのに id を書き落とす」**。→ レビューには前景の一文だけを書かせる。`done` の判定は別の呼び出しに分ける。

### 4.4 相対表現は書かせない（→ §2.2）

「来週水曜」「三日後の夜」は 30回中2回しか発火せず、その2回とも誤り（基準日が無いので解釈できない）。→ 本文に「来週水曜に会う約束をした」と出たら、**記録する時点で絶対表現へ解決する**。

### 4.5 条件つきは「状態」として読まれる（→ ガイドへ）

「雨が止んだら」は雨が降っていない平時のあいだずっと成立し、「冬になる前」は秋のあいだずっと成立する。害ではない（「6月後半に中間試験」が6月後半じゅう出続けるのは正しい）が、**書き方の指針が要る**。

- **点**（8月31日・明日）→ その時だけ出る
- **遷移**（降り続いた雨が**やんだとき**）→ 一度だけ出やすい
- **幅**（冬になる前・6月後半）→ その期間ずっと出続ける

「一度きり」にしたいなら遷移で書く。**機構は不要、ガイドの1節で済む。**

### 4.6 照合の入力に場面の状況は要らない

固定枠（場所・居合わせている人・状況）を照合へ足しても誤発火は減らなかった（23/30 → 25/30）。フラグの立った12件を人手で読んだ結果、**判断そのものを誤っていたものは無い**（フィクスチャの曖昧さと §4.3 の帳簿の失敗）。固定枠は表示と引き継ぎのために残すが、**照合のための入力ではない**。

## 6. 実装フェーズ

**F1 → F2 → F3 → F4 → F5。** 各フェーズごとに `npx tsc --noEmit` → `npm run build`。Tauri 固有部を触った時のみ `npm run tauri:dev` の手動チェックリストも実施。

### F1 削除（条件・数・目標・配役・特別イベント）

**最初に置く理由**: F2 の予定スリップは特別イベントの受け皿なので、先に消しておかないと二重になる。また互換性不要（`lib/schema.ts` の移行チェーンごと捨てる）なので、この段階でコードが最も減る。

削除の順序は **UI → store → types**（参照する側から）。

1. `ConditionEditor` / `WorldEditor` の該当タブ / `SessionEditor` の配役 UI / `StatusPanel`・`StatusView` の数・実績・結末 / `OpeningBriefing` / `SceneReviewModal` の数の増減
2. `store.ts` の条件エンジン（`matchGroups`／`evalCondition`／`ConditionContext`／`gateLoreByCondition`／キャラゲート／実績解除／エンディング到達／イベント発火）・`casting.ts`
3. `types.ts` の該当型・`prompts.ts` の注入・`jsonSchemas.ts` のレビュースキーマ・`cards.ts` の入出力・`schema.ts` のリセット

### F2 時間と予定

固定タイムライン廃止と `now`/`pending` 導入は**同時でないと動かない**（`Scene.timeLabel` の置き換えを含む）。実測で形が決まっているので設計上の未決は少ない。

1. 型（`SessionState` の新フィールド・`PendingSlip`・`World.calendarFormat`・`initialPending`）
2. レビューのプロンプトとスキーマ（`now`／`place`／`presentIds`／`situation`／`foreground`／`pendingAdd`／`pendingDone`／`happenedAdd`）
3. 本編プロンプト（深さ0へ `foreground` の一文のみ・**`pending` は渡さない**）
4. 状態パネル（現在・場所・居合わせている人・これから起きること・消化した予定・出来事）

### F3 ペルソナ統合

`Persona` → `Character`、`personaId` → `povCharacterId`、`Relation.toId` の `'hero'` 廃止。素材ライブラリが1種類減る。

### F4 読者モデル

入力の意味論の変更・操作系（続ける／再生成／尺の指示／書き手への指示）・`ChoiceMode` 廃止と〈展開を選ぶ〉ボタン・エンディング提案。

### F5 仕上げ

文字数表示・`カセット作成ガイド_AI用.md` の全面書き直し（**大半が消えて短くなるのが成果**）・`AGENTS.md` の更新。

## 8. 却下・撤回した案

| 案 | 理由 |
|---|---|
| **特別イベントを `day`/`slot` だけ残す**（当初の推奨） | **撤回**。固定タイムラインを廃止すると座標系が無くなる。初期の予定スリップ（§2.6）が受け皿になる |
| **予定を上限8件にする**（当初の設計） | **撤回**。件数は精度にほぼ効かなかった（§4.2） |
| **予定リストを背景として常時注入する**（当初の設計） | **撤回**。有害だった（§4.1） |
| **照合の入力に場面の状況を足す**（当初の推奨） | **撤回**。照合精度は変わらなかった（§4.6）。固定枠は別の理由で残す |
| 条件を自然文で書かせてレビューに判定させる | 「作者が条件を書く」構造自体が廃止対象。形を変えて残す意味がない（§1.1） |
| 予定を `LoreEntry` と同じ配列に入れる | 寿命が違う（ロアは不変・予定は必ず消える）／注入位置が違う（深さ3 vs 深さ0）／`SessionOverlay.lore` が予定で埋まる |
| コードで時計を回す（AI Dungeon 方式） | 最も厳密だが作者コストが最も高い。今回降りる流派そのもの |
| トークン／文字数を選べるようにする | ユーザーに選ぶ基準がない。用途で固定する（§2.8） |
| 数の状態を prose の band（5段階の言葉）で残す | `Relation` が既に band を捨てて prose 一本で成立している。二の轍 |
| `roleplay` モードの廃止 | 単体キャラとの会話は読者モデルと競合しない別軸。残す（§3.3） |
