# 設計仕様 — 状態エンジン（関係性 prose ＋ 事実の数）

> 「自由度の極めて高いギャルゲ」を実現するため、ワールドごとに独自のゲームシステムを構築できる基盤の設計。
> **後方互換性は不要**（旧 localStorage は破棄＝クリーンブレイク）。設計の美しさとテーマ実現を最優先する。
> 根本方針の決定経緯と却下案は CLAUDE.md「設計上の根本分岐（ADR）」を参照。

## 0. 原則
**事実は数、判断は言葉。**
- **判断**（感情の機微・関係の質）＝ **prose**（言語記述）。LLM が読み、生成と没入に使う。**条件判定には使わない**。
- **事実**（好感度ポイント・回数・所持金・レベル・日数）＝ **数 / フラグ**。プレイヤーとコードが読み、**イベント発火の条件**に使う。
- 関係の「進捗（レベル上げの楽しみ）」は prose とは**別レイヤーの加点ポイント**で表現する（採用案A）。ポイントは**イベント/行動を踏むと固定値で加算される事実**であり、LLM に「現在値を査定させる」連続評価値（却下した「信頼60」）とは別物。
- イベント発火は**人の承認なし・コードの自動判定**（ポイント/フラグ/カウンターのしきい値）。LLM 言語判定（非再現・早漏）も人承認（無粋）も不採用。

## 1. 全体像：2レイヤー
| レイヤー | 中身 | 消費者 | 用途 |
|---|---|---|---|
| **prose 関係性** | stance ＋ aspects（ワールド固定の次元ごとの記述） | LLM・読者 | キャラ描写・没入。条件には使わない |
| **事実の数** | 好感度ポイント / 各種スタット / カウンター / フラグ / 実績 | プレイヤー・コード | 進捗の可視化・イベント発火・分岐 |

両者は同じ「信頼」を二重化してもよい（prose=機微、ポイント=メーター）。役割が違うので矛盾しない。

## 2. データモデル

### 2.1 定義 — すべて World に集約（ワールド＝ゲームシステム）
```ts
// prose 関係性の次元（ワールド固定。自動発見はしない）
interface RelationAspectDef {
  id: string
  name: string            // 例: 信頼 / 恋愛 / 警戒
  guidance?: string       // レビューへの指示。例:「相手の言動の何を信じ何を疑うか」
}

// 事実の数（好感度メーター・レベル・所持金・名声・HP 等）
type StatScope = 'character' | 'global'    // character=キャラ別1値（対主人公の好感度メーター含む） / global=主人公・世界で1値
interface StatDef {
  id: string
  name: string            // 例: 好感度 / レベル / 所持金 / 名声
  scope: StatScope
  default: number
  min?: number
  max?: number
  inject: boolean         // 本編プロンプトに現在値を注入するか（好感度メーターは通常 false＝LLM は prose を読む）
}

interface CounterDef {    // P2  単調増加の累計（回数）
  id: string; name: string; scope: StatScope; inject: boolean
}

interface AchievementDef {// P3
  id: string; name: string; description: string
  condition: Condition    // §5
  hidden?: boolean
}

interface World {
  // ...既存(name, description, entries, scheduledEvents)
  relationAspects: RelationAspectDef[]
  stats: StatDef[]
  counters: CounterDef[]       // P2
  achievements: AchievementDef[]// P3
}
```
- **プリセット**：World 編集に「恋愛」「RPG」「経営」等のテンプレを用意し、aspects/stats/counters/achievements をワンクリック投入（自由に編集可）。
- ステータス系を使うセッションは World を参照する（`worldId` 必須運用）。

### 2.2 値 — すべて SessionState（プレイスルー固有）
```ts
// prose 関係性（キャラ→主人公 等の有向ペアごと）
interface Relation {
  fromId: string
  toId: string                                   // 'hero' = 主人公、または characterId
  stance: string                                 // 関係の現在地を1〜2文。本編注入と表示の中心
  aspects: { aspectId: string; note: string }[]  // ワールド固定の次元ごとの prose。band は持たない
  flags: string[]                                // ゲート用に立った恒久事実。例: ["命を救われた","秘密を共有"]
  updatedAt: number
}

interface StatValue { defId: string; characterId?: string; value: number }   // characterId 無し = global
interface CounterValue { defId: string; characterId?: string; value: number }// P2

interface SessionState {
  relations: Relation[]
  moods: { characterId: string; mood: string }[]        // キャラ自身の一時的な気分（prose・毎回上書き）
  stats: StatValue[]
  counters: CounterValue[]                              // P2
  achievements: { defId: string; unlockedAt: number }[] // P3
}
```
- **実効値 = `StatValue` があればその値、無ければ `def.default`**（疎な上書き）。
- 役割分担：**機微は stance/aspects（言い換わってよい）／恒久事実は flags（失ってはいけない約束・秘密・不可逆な出来事）／進捗は stats（好感度ポイント）**。

## 3. 加点（進捗）の仕組み — 「細かく上昇する」を作る
好感度ポイント等の StatValue は**行動・イベントを踏むと固定値で加算**する。査定ではなく事実。供給源：
- **レビュー時の delta**（基本・確実）：シーン終了レビューが「今シーンで起きたこと」に対応する `statChanges`（delta）を出力 → コードが clamp 加算。
- **選択肢連動（P5・"細かさ"用）**：生成された各選択肢に `effect?: { statName, delta }[]` を持たせ、選んだ瞬間に適用。頻繁な行動ごとに小刻みに上がる＝レベル上げの手応え。既存の選択肢システムを活用。

数値の計算は常にコードが行う（LLM は delta を提案するだけ）。

## 4. プロンプト注入（prose を LLM へ、数値は最小）
```
【関係性（現在）】
- ルナ → 主人公: 主人公が庇ったことで不信より信頼が勝り始めた。
    信頼: 迷わず庇ってくれた。隠し事への警戒は薄れた。
    恋愛: 胸の高鳴りを自覚し始めた。
  気分: 照れと戸惑い
※この記述と矛盾しない態度・距離感で演じる。記述やメタ情報を台詞に出さない。
```
- 関係性は `stance` ＋（登場キャラ分の）`aspects` ＋ `mood`。
- 数値は `inject:true` のものだけ別ブロックで（好感度メーターは原則 inject:false＝LLM は prose を読むため）。
- `buildStateInfo()` が `ResolvedRefs.stateInfo` を組み立て本編 system へ1ブロック追加。

## 5. 条件エンジン（数・フラグ・実績のみ。prose は読まない）— P4
```ts
type Op = '>=' | '>' | '<=' | '<' | '==' | '!='
type Clause =
  | { kind:'stat';         defId:string; characterId?:string; op:Op; value:number }
  | { kind:'counter';      defId:string; characterId?:string; op:Op; value:number }
  | { kind:'relationFlag'; fromId:string; toId:string; flag:string; have:boolean }
  | { kind:'achievement';  defId:string; have:boolean }
type Condition = { all: Clause[] } | { any: Clause[] }   // ネスト可
```
- `evalCondition(cond, state, refs): boolean` を1つ用意し、**イベント自動発火**と**実績判定**で共用。
- **ScheduledEvent 拡張**：
  ```ts
  interface ScheduledEvent { /* ...id,name,note */ day?: number; condition?: Condition }
  ```
  `directNextScene` のイベント抽出：未消化かつ `(day==null || day<=nextDay)` かつ `(condition==null || evalCondition)`。**人の承認なしで自動発火**（裏でサイレント）。これで「好感度50で告白」「戦闘10回で称号」「会話100回で解放」「N日目」が同一枠で、没入を切らさず・再現可能に実現。

## 6. 更新フロー（レビュー＝唯一の書き手）
`reviewSystem()` 出力 JSON（最終形）：
```jsonc
"relationUpdates": [
  { "from":"ルナ","to":"主人公",
    "stance":"主人公が庇ったことで信頼が勝り始めた。",          // ← stance を全文置換（追記しない）
    "aspects":[ {"name":"信頼","note":"..."}, {"name":"恋愛","note":"..."} ],
    "flags_add":["命を救われた"], "reason":"..." }
],
"moodUpdates":  [ {"character":"ルナ","mood":"照れと戸惑い"} ],
"statChanges":  [ {"name":"好感度","character":"ルナ","delta":3,"reason":"..."} ],  // 事実の加点
"counterEvents":[ {"name":"デート","character":"ルナ","amount":1} ]                  // P2
```
コード適用（`prepareSceneReview` 解析 → `confirmSceneReview` 適用）:
- `stance`/`aspects.note` は**全文置換**（矛盾と肥大を防ぐ。未変化の具体は維持するよう指示）。`flags_add` は和集合。
- `statChanges` は `clamp(min..max)` で加減算、`counterEvents` は加算。**数えるのはコード**。
- 反映は**現在シーン確定時のみ**（過去シーン再レビューでは書き換えない＝既存ルール踏襲）。
- 適用後、実績条件を評価し新規達成を記録・通知（P3）。`name`→`defId`/`aspectId` は World 定義から解決（未定義は無視＝ワールド固定）。

## 7. UI
- **定義**：`WorldEditor.tsx` に「関係性の次元 / ステータス / カウンター / 実績」セクション＋プリセット＋条件ビルダー（イベント・実績、P4）。カンマ区切りは必ず `CsvInput`。
- **現在値**：`ChatPanel.tsx` にステータスパネル（好感度メーター・各スタット・関係性 prose・達成済み実績）。手動編集可。
- **差分確認**：`SceneReviewModal.tsx` に relationUpdates / statChanges / counterEvents / 新規実績を表示（現行 relationshipDeltas 表示を置換）。

## 8. ストアのクリーンブレイク
- persist `name` を新キー（例 `'ai-storytelling-store-v2'`）へ → 旧データは読まれず新スキーマで開始。
- `migrateV0toV1`〜`migrateV8toV9` と persist の `migrate`/`version` 連鎖を**全廃**（`store.ts` を大幅減量）。
- `importBundle` は現行スキーマのみを id マージ（正規化連鎖を削除）。`exportBundle` の `version` をリセット。

## 9. フェーズ計画と影響範囲
> 各フェーズ＝「型 → store → prompts → UI → 型チェック → build → Preview 検証 → commit/push」を1サイクル。

### P1 — 状態モデルの土台（prose 関係性 ＋ 事実の数）＋クリーンブレイク
- `types.ts`：RelationAspectDef/Relation、StatDef/StatValue/StatScope、World に relationAspects/stats、SessionState を `{relations,moods,stats,counters:[],achievements:[]}` に置換、SceneReview に relationUpdates/statChanges。旧 `Relationship` 型を削除。
- `store.ts`：移行連鎖削除＋persist キー変更、初期 state/factory、`buildStateInfo`（`buildRelationshipInfo` 置換）、`resolveRefs`（relationshipInfo→stateInfo）、`prepareSceneReview`（relationUpdates/statChanges 解析・name 解決）、`confirmSceneReview`（applyState 置換：stance/aspects 全文置換・flags 和集合・stat clamp 加算・現在シーン限定）、`exportBundle`/`importBundle`、World プリセット seed。
- `prompts.ts`：`reviewSystem` を新出力契約へ、本編注入を prose 中心に一般化、`ResolvedRefs.stateInfo`。
- UI：`WorldEditor`（次元・スタット定義＋プリセット）、`ChatPanel`（ステータスパネル）、`SceneReviewModal`（差分）。
- 完了時：従来の好感度・気分が「prose 関係性＋好感度メーター」として動作し、任意スタット（レベル/所持金等）も定義・追跡・手動編集できる。

### P2 — 行動カウンター
- CounterDef/CounterValue、World.counters、SessionState.counters、SceneReview.counterEvents、注入・表示。

### P3 — 実績（フラグ）
- AchievementDef/achievements、適用後の実績評価・記録・通知、UI 定義・一覧。

### P4 — 条件エンジン＋自動発火
- Condition/Clause/Op、ScheduledEvent.day 任意化＋condition、AchievementDef.condition、`evalCondition`、`directNextScene` の条件発火、条件ビルダー UI。

### P5（任意）— 選択肢連動の小刻み加点
- 生成選択肢に `effect`、選択時適用。"細かく上昇する" 手応えの強化。

## 10. 落とし穴
- 旧データは破棄される（persist キー変更）。残したい既存セッションは**実装前にエクスポート**。
- プロンプト肥大化：`inject` で注入を絞る。好感度メーターは原則 LLM に注入しない（prose を読ませる）。
- LLM の delta 提案は不正確になりうる → コード側 clamp ＋手動編集で吸収。厳密な計算が要る系の「ルール式」は本設計の対象外。
- prose 関係性は条件に使わない（再現性・ドリフト耐性のため、ゲートは数/フラグのみ）。
- カンマ区切り入力は必ず `CsvInput`（CLAUDE.md 規約）。
```
