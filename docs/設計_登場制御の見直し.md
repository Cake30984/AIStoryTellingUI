**シーンの状況メモ（可視・半自動）＋作者の固定メモ（可視・任意）＋システムの一文（不可視・最小）** の三層で解く。

## 0. いま何が困っているか

セッションに参加しているキャラが、**文脈上ありえない形で登場する**ことがある。

- 二人きりの場面に第三者が理由なく割り込む
- 特定のキャラとの関係を深めたい場面で、別のキャラが会話を奪う
- 前のシーンで別の場所に居たはずの人物が、移動の描写なしに会話へ加わる

これに対する現在の答えが `Scene.activeCharacterIds` による絞り込み（要件定義書 FR-34）で、
シーン設定でチップを外したキャラは `resolveRefs`（[`store.ts:2181`](../src/store.ts)）でプロンプトから落ちる。

### この方式が機能していない理由

1. **粒度が細かすぎて誰もやらない。** 新規シーンは常にセッション全員をコピーして作られる
   （`cards.ts:451` / `store.ts:3937` / `SessionEditor.tsx:58`）。「絞る」はシーンが変わるたびに手で外す操作で、
   物語を書いている最中にその手間を払う人はいない。結果として**実態は常に全員入り**＝制御として働いていない。
2. **絞れば絞ったで硬い。** 外したキャラは存在ごとプロンプトから消えるので、「居るけど今は喋らない」
   「呼べば来る」が表現できない。**「その場に居るか」と「プロンプトに定義があるか」を1つのスイッチで兼ねている**のが構造的な誤り。
3. **キャッシュに不利。** [`設計_プロンプト構造とキャッシュ.md`](./設計_プロンプト構造とキャッシュ.md) §2 の三層化で
   【登場人物】は T2（シーン境界で変化）に分類されている。キャストがシーンごとに入れ替わりうることがその一因で、
   キャラ定義はプロンプト中で最も長いブロックのひとつ。

### そもそも事故は起きているのか

実使用の体感では、**モデルの性能に強く依存する**。deepseek v4 flash クラスでは、キャストを絞らなくても
文脈を読んで不自然な登場をしない。事故が目立つのは低性能モデル＝[`ガイド_ローカルLLMで動かす.md`](./ガイド_ローカルLLMで動かす.md)
が対象にしている帯。**この見立て自体が未検証**なので、対策の設計より先に測る（§7）。

## 1. 決定

| 決めたこと | 内容 |
|---|---|
| シーン単位のキャスト | **廃止**。プロンプトのキャストは常に `session.characterIds`（顔ぶれ）で固定 |
| 「今この場に誰が居るか」 | **シーンの状況メモ（`Scene.note`）が担う**。レビューが自動で書き、ユーザーが確認・編集できる |
| 登場の作法（世界ごとの方針） | `authorNote`（作者の領分） |
| 不可視のシステム文 | **文法として真な一文に限る**。それ以外は足さない |
| 追加の順序 | **まず何も足さずに撤去し、実測してから足す**（§7） |
| スキーマ | `SAVE_DATA_VERSION` は **1 のまま**。旧データの `activeCharacterIds` は**読み捨て**（§3.3） |

### 却下した案

- **シーン単位の絞り込みを残したまま既定を「全員」にする** → 今と同じ。使われないUIと、使われないぶんだけ
  混乱する説明文（「空にすると全員が対象になります」）が残るだけで、キャッシュの不利も消えない。
- **「登場させない」を不可視のシステム文だけで解く**（`newCharacterPolicy` 方式の拡張） → 部分的には採る（CS3）が、
  これ単独は不可。**どのキャラがどれくらい前に出るかは世界ごとの価値判断**で、システムが一律に決める筋合いがない（§2）。
- **全部 `authorNote` に寄せる**（システム側は何もしない） → `authorNote` は**セッション全体**の設定なので
  「このシーンは二人きり」が原理的に書けない。加えて「作者が書かなければ事故る」状態は、
  チップを外す手間を作文の手間に置き換えただけで、準備ゼロという製品の判定軸に反する。
- **AI にシーンごとの登場者を宣言させて `activeCharacterIds` を自動で埋める** → 自動化としては筋が良いが、
  **フィールドを残す前提**なので上の 2.（「居るけど喋らない」が表現できない）が解けない。
  同じ推論結果を自然文で `note` に書けば済む。
- **「その場に居ない人物」を状態エンジン（位置ステータス）で管理する** → 場所を数値・列挙で持つ仕組みは
  物語の場所の曖昧さ（「隣の部屋」「電話越し」）を表現できず、作者に位置の定義を強いる。却下。

## 2. 領分の整理

[`設計_プロンプト構造とキャッシュ.md`](./設計_プロンプト構造とキャッシュ.md) §6.2 の線引き
（**可視性ではなく主張の種類**で引く）に、今回の話を載せると3つに割れる。

| 層 | 主張の種類 | 担当 | 可視性 | 例 |
|---|---|---|---|---|
| **文法** | ジャンルに依らず真・構造的 | システム（`prompts.ts`） | 不可視・**一文だけ** | 場面に居ない人物を、移動や来訪の描写なしに会話へ加えない |
| **事実** | いま何が起きているか | シーンの状況メモ `Scene.note` | **可視・編集可**・半自動 | 「夕暮れの教室。二人きり。」 |
| **方針** | 世界ごとの価値判断 | `authorNote` / キャラ定義 | **可視**・任意 | 「この学園では生徒が頻繁に出入りする」「彼女は空気を読まず割り込む」 |

**「見えないプロンプトは避ける」という要求は、authorNote へ寄せなくても満たせる。** 前例が2つある。

- `newCharacterPolicy`（[`prompts.ts:203`](../src/lib/prompts.ts)）— **設定は見えるが文面は生成**。見える ≠ 作者が書く
- §6.2 の「既定文の扱い」— 新規世界観の `startPreset.authorNote` に**書かれた状態で置き、消せるようにする**。
  押し付け（変更不能な既定）と放置（空欄）の中間

CS2 はこれをさらに進めた形になる。**レビューが生成した「誰が居るか」の文を、ユーザーが確定前に読んで直せる**
（`SceneReviewModal.tsx:538` で `suggestions[].note` は編集可能）。生成物でありながら、
不可視でも作文の強制でもない位置に落ちる。

### 不可視プロンプトについての原則（明文化）

全面禁止は現状と矛盾する。`buildSystemPrompt` は丸ごと不可視で、`story.initialDirective`（最初の方向づけ）は
**仕様として意図的に非表示注入**されている。実行可能な粒度として次を原則にする。

> **新しい振る舞い制御を不可視で足さない。** 足すのは §2 の「文法」に該当するものだけで、それも一文に限る。
> 価値判断は可視の置き場所（`authorNote` / `Scene.note` / 明示的な設定）に置く。

より本質的な解は [`設計_プロンプト構造とキャッシュ.md`](./設計_プロンプト構造とキャッシュ.md) §6.3-6 が既に示唆している
——「本アプリは作者にプロンプトを見せる方向にある」。**実際に送信しているプロンプトを確認できるUI**を持てば
不可視への懸念は構造的に消える。本書の範囲外だが、別トラックとして残す（§9）。

## 3. CS1: `Scene.activeCharacterIds` の撤去

### 3.1 型

```ts
export interface Scene {
  id: string
  title: string
  // activeCharacterIds: string[]  ← 削除
  /** 時・場所・状況メモ（誰がこの場に居るかを含む。【現在の場面】として注入） */
  note: string
  // …以下そのまま
}
```

`newScene(title, activeCharacterIds, timeLabel)`（[`store.ts:1026`](../src/store.ts)）の第2引数を落とし、
`newScene(title, timeLabel)` にする。呼び出しは4箇所（`newSession` / エピローグ `store.ts:3851` /
次シーン生成 `store.ts:3937` / `freshSessionOf` `cards.ts:451`）。

### 3.2 消費者の始末

| 箇所 | 現状 | 撤去後 |
|---|---|---|
| [`store.ts:2181`](../src/store.ts) `resolveRefs` | プロンプトのキャストを絞る | `session.characterIds` に一本化。`castIds` 変数ごと削除し、`characters` と `allCharacters` が同一になる（**`allCharacters` を消して `characters` に寄せた**＝参照は `characters` が多数派で、`allCharacters` は配役解決の1箇所だけだったため） |
| [`ChatPanel.tsx:230`](../src/components/ChatPanel.tsx) `castIds` | 話者チップ・`participants` の候補 | `session.characterIds` へ。roleplay の群像判定 `groupMode` もこれに従う（挙動は実質変わらない＝現状も全員入り） |
| [`ChatPanel.tsx:499`](../src/components/ChatPanel.tsx) `sceneParticipants` | 過去シーンの配役（FB6-B・後付け画像生成の文脈） | `session.characterIds` を返すだけになるので関数を畳む |

未解決話者の ？バッジ・発見キャラ（FB7-E）は影響を受けない。

### 3.3 データ移行

**`SAVE_DATA_VERSION` は上げない。** 旧セーブ・旧カセットの JSON に残る `activeCharacterIds` は、
型から消えれば単に読まれなくなるだけで、破壊も参照切れも起こさない（`lib/schema.ts` の方針でいう
「未知キーは保存して素通し」と同じ扱い）。**版番を上げると、上げたぶんだけ移行チェーンの保守対象が増える**ので、
値を捨てるためだけに 2 へ上げる価値はない。

- 書き出し側（`cards.ts`）は新しい型で書くので、以後のカードにこのキーは含まれない
- 読み込み側は既にキー単位の検証をしていないため変更不要
- [`カセット作成ガイド_AI用.md`](./カセット作成ガイド_AI用.md) の `scenes` サンプル2箇所（311行目付近・402行目付近）から
  `activeCharacterIds` を削る。**削除後も古い記述を持つカセットは読める**（無視されるだけ）

## 4. CS2: 状況メモに「誰が居るか」を書かせる

`Scene.note` は既に【現在の場面】として注入されており（[`prompts.ts:122`](../src/lib/prompts.ts)）、
シーン終了レビューが次シーンの `note` を自動で埋める（[`store.ts:3938`](../src/store.ts) `next.note = sug?.note || evNote || ''`）。
**器も自動化も既にある。中身が「誰が居るか」を書いていないだけ**なので、レビューの指示文を直す。

### 4.1 レビュー側（プロンプト2箇所）

`suggestions[].note` の説明を、登場者を含めるよう書き換える。対象は
[`prompts.ts:797`](../src/lib/prompts.ts)（シーン終了レビュー本体）と
[`prompts.ts:850`](../src/lib/prompts.ts)（次シーン候補の作り直し）の**両方**。片方だけ直すと、
作り直したときに登場者の記述が消える。

```
現行: "note":"次シーンの状況・方向性の説明（2〜3文）"
変更: "note":"次シーンの状況・方向性の説明（2〜3文）。**時・場所と、その場に居合わせる人物を必ず含める**"
```

補足の箇条書き（`prompts.ts:814` 付近）にも1行足す:

```
- 各案の note には、その場面に居合わせる人物を明記する。全員が同席する必然性が無ければ一部でよい
  （登場人物として定義されていても、その場に居ないことはある）。
```

**注意**: ここは「絞れ」と言う場所ではない。**居合わせる人物を書け**と言うだけで、誰を選ぶかはモデルが文脈から決める。
「なるべく少人数に」等の価値判断を入れると §2 の線を越える（＝ CS4 の領分）。

### 4.2 UI

- `SceneEditor` の状況メモに説明文を足す:
  「時・場所と、この場に居る人物を書きます。ここに書かれた顔ぶれが、そのシーンの登場人物の目安になります。」
- プレースホルダは現行の「例: 夕暮れの教室。二人きり。」がそのまま適切（**既に人数を含んだ例文になっている**）
- `SceneReviewModal` 側は変更不要（`suggestions[].note` は既に編集可能・550行目付近の確定表示も既存）

### 4.3 最初のシーンだけ空になる問題

レビューが埋めるのは**2シーン目以降**。1シーン目の `note` は空のままなので、開始直後は
「誰が居るか」の手がかりが導入文（`story.opening`）しかない。

対応は**世界観の開始テンプレートに寄せる**（W1 の仕組みに乗る）。`WorldStartPreset` に
`openingSceneNote?: string` を足し、セッション開始時に1シーン目の `note` へコピーする。
カセット作者が「第一話は主人公と幼馴染の二人だけ」と書ける場所ができる。**空なら何も起きない**（現状と同じ）。

> これは `startPreset` へのフィールド追加なので `CASSETTE_DATA_VERSION` の対象に見えるが、
> **任意フィールドの追加は読み側が `?? ''` で吸収できる**ため版番は上げない（`newCharacterPolicy` 追加時と同じ扱い）。

## 5. CS3: システム側の文法一文（実測後に採否）

§2 の「文法」に該当するもの**だけ**を、【現在の場面】の直後に置く。候補:

| # | 文面 | 狙い / 懸念 |
|---|---|---|
| **W0** | （何も足さない） | **対照群**。CS1+CS2 だけで足りるなら、これが採用案 |
| **W1** | 【現在の場面】に居ると書かれていない人物を、移動・来訪の描写なしに会話へ加えないでください。 | 本命。**禁止しているのは「描写なしの出現」だけ**で、登場そのものは禁じていない＝ワープを塞ぐだけの純粋な文法 |
| **W2** | 誰がその場に居るかは【現在の場面】と直前までの流れから決まります。人物を新たに場面へ入れる時は、そうなった経緯を描いてください。 | W1 の帰属型。命令ではなく「どこから決まるか」を言う（§6.1 の V2 と同型）。柔らかいぶん弱い可能性 |

**W1 を本命に、W0 を必ず一緒に回す。** 迎合対策（§6.1）で V4 が「作者の領分に入っている」として保留されたのと同じ理由で、
「登場は最小限に」「二人きりの場面を邪魔しない」といった**量や好みに踏み込む文面は候補に入れない**。

置き場所は **T2 の末尾**（【現在の場面】の直後）。参照する対象がすぐ上にあり、シーン境界でしか変わらない層なので
キャッシュを毎ターン壊さない。深さ注入（PC4）は待たない——文面が効くかどうかは system 内でも測れる。

### 5.1 結果: **不採用**（2026-08-16）

| 案 | ①割り込み（deepseek・N=40） | ①第三者登場（qwen3-8b・N=20・人手確認後） |
|---|---|---|
| **W0** | **0/40** | **2/20** |
| W1 | 0/40 | 5/20 |
| W2 | 2/40 | （未測定） |

**W0 が既に床なので、採用条件「W0 より明確に下がる」を満たしうる案が存在しない。**
低性能帯では事故が残るが、W1 を足しても減らない＝**足りないのは指示ではなく読解力**。
詳細は [`計測_登場制御.md`](./計測_登場制御.md)。`prompts.ts` には何も足さない。

## 6. CS4: 作者の領分の支え方（**既定文は書かない**）

当初案は「新規世界観の `startPreset.authorNote` に既定文を置く」だったが、
**先行実測がこれを既に否決している**ため撤回する。

[`archive/計測_迎合対策文面.md`](./archive/計測_迎合対策文面.md) §4.4:

> 汎用の1文が効かないことがこの実測の結論なので、**同じ内容を `authorNote` に移しても効かない**。
> 既定で入れれば毎ターン非キャッシュのトークンを増やすだけになる。
> 作者の領分に寄せるという方針自体は維持し、**既定値ではなく入力欄の案内**で支える。

740会話の実測で、深さ3に置いた汎用の拘束文6案はすべて対照を上回らなかった（§7.5 も参照）。
**同じ轍を踏まない。** よって CS4 は次の形にする。

- **`authorNote` に既定文を置かない**（新規世界観は空欄のまま）
- 代わりに**入力欄の案内**（`desc` とプレースホルダ）で「ここに書ける」ことを示す。
  世界ごとに違う価値判断——「この学園は人の出入りが多い」「彼女は空気を読まず割り込む」——は、
  **作者が自分の言葉で書いたときだけ効く**（先行実測 §4.2-3: 実際に効いているのはキャラ定義と関係性 prose）
- 登場の作法をキャラ単位で効かせたい作者には、`authorNote` ではなく**キャラクターの人格欄**を案内する
  （`WorldEditor` の固定メモ欄に既にある「人物の芯は人格欄に書く方がよく効きます」と同じ趣旨）

## 7. 実測

メモリ／[`設計_プロンプト構造とキャッシュ.md`](./設計_プロンプト構造とキャッシュ.md) §6.1 の方針に従い、
**文面を設計してから測るのではなく、測ってから足すかどうかを決める**。過去に「実測で判断が3点ひっくり返った」
（2026-08-02）実績がある領域なので、ここは省略しない。

### 7.1 測る順序

1. **CS1+CS2 を実装し、何も足さずに測る**（＝ W0）
2. 事故率が許容できるなら **CS3 も CS4 も作らない**。設計終了
3. 許容できない場合のみ CS3 を入れて再測。W1 → W2 の順に1つずつ
4. CS3 で足りない・または過剰に効く場合のみ CS4

### 7.2 条件

- **モデルは3帯**: ①普段使い（deepseek v4 flash 相当）②低性能ローカル（Ollama 実機。R5 で通した構成をそのまま使う）
  ③中位クラウド。**②が本番**——事故が起きるのはここだという見立て自体の検証を兼ねる
- **セーブのチェックポイント機構を A/B に使う**（§6.1 と同じ手口）。同一の復元地点から同一入力を投げれば、
  変えた1変数以外の条件が揃う
- 検証地点は2つ:
  - **P-二人**: 三人以上が参加登録されているが、直前のシーンで2人だけになった地点
  - **P-離散**: 参加キャラの1人が明確に別の場所に居る（前シーンで「先に帰った」等）地点
- 各地点で**同一の入力3種** × N=5:
  - ①**二人のやり取りを深める入力**（第三者が割り込んだら失敗）
  - ②**その場に居ない人物に会いに行く入力**（移動描写なしに合流したら失敗／会えないのも失敗）
  - ③**全員が集まって然るべき入力**（集まらなければ過剰抑制）

### 7.3 指標

| 指標 | 望ましい方向 | 失敗の見え方 |
|---|---|---|
| 不自然な合流率（入力①） | **下げる** | W0 で高いならシステム側の対策が要る＝ CS3 へ進む根拠 |
| 過剰抑制（入力③） | 上げない | 集合すべき場面で人が集まらない・「彼はここに居ない」と繰り返す |
| 移動描写の有無（入力②） | 描写されること | ワープ＝失敗。逆に「会いに行けない」もそのシーンの失敗 |
| 文体の劣化 | 出さない | 「この場に居ないため」等、**仕組みが地の文に漏れる**のが典型 |
| モデル帯による差 | 記録する | ①③帯で W0 が既に十分なら、CS3 は**低性能帯だけの問題**＝ローカルLLMガイド側の記述で足りる可能性 |

### 7.4 採用条件

入力①の不自然な合流が W0 より明確に下がり、かつ入力③の過剰抑制と文体劣化が W0 と同等——を満たす案のうち、
**最も短い文面**を採る。どれも満たさない場合は **CS3 を入れず CS4（作者の領分）へ寄せる**。
§6.2 のとおり、**システムが肩代わりしないことは敗北ではない**。

### 7.5 先行実測（必読）

[`archive/計測_迎合対策文面.md`](./archive/計測_迎合対策文面.md)——740会話で、深さ3に置く汎用の拘束文6案が
**すべて対照を上回らなかった**という記録。§4.3「再挑戦するなら文面の強度ではなく置き場所か形式を変える設計にすること」、
§4.4「既定文は実施しない・入力欄の案内で支える」は本書にそのまま効く（§6 はこれに従って書き換えた）。

CS3 が先行実測の V 系列と違うのは、**汎用の behavior 指示ではなく、プロンプト中の具体的な記述（【現在の場面】）を
参照させる**点だけ。この違いに賭けて測ったが、**結果は同じだった**（§7.6）。

### 7.6 実測の結果（2026-08-16・確定）

[`計測_登場制御.md`](./計測_登場制御.md) に記録。要点:

- 普段使い帯（`deepseek-v4-flash`・360会話）: **W0 の事故 0/40**。W1 は 0/40（変化なし）、W2 は 2/40（悪化）
- 経緯なしの合流（②③）は**全案・全地点で 0**
- 低性能帯（`qwen3-8b`・120会話）: W0 で 2/20、W1 で 5/20＝**改善しない**
- `leak` は 0/480
- **判定モデルは低性能帯で過検出する**（登場していない「声が届いた」「黒い影」を拾う）。
  フラグの立った件は人手で読み直した——先行実測 §2.1 と同じ落とし穴

→ **CS3 不採用。CS1+CS2 で確定**。
