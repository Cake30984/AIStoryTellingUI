# 設計_登場条件と目標提示（2026-08-30）

3つの指摘——**キャラの登場条件が書けない／カセット作成ガイドが仕様を網羅していない／導入文だけでは何をすればいいか分からない**——を1本にまとめる。
別々の話に見えるが、原因は同じ構造にある。

> **共通構造**: このアプリは「作者が仕込んだ情報を、条件付きで出し分ける」機構を既に持っている
> （`LoreEntry.condition`・`AchievementDef.hidden`・`EndingDef.hidden`・`ScheduledEvent.condition`）。
> しかしその機構が **① キャラクターには掛かっていない ② 作者（＝カセットを書く AI）に伝わっていない
> ③ プレイヤーには届いていない**。3つとも「出し分けの機構が、届くべき相手に届いていない」という同じ欠落の別の面。

| ID | 内容 | 依存 | 状態 |
|---|---|---|---|
| **CG1** | キャラクターの登場条件（条件を満たすまでプロンプトへ注入しない） | なし | **実装済み**（2026-08-30） |
| **CG2** | カセット作成ガイドの網羅性回復（欠落11項目・誤り3件） | なし | **実装済み**（2026-08-30・全面書き直し） |
| **CG3** | 開始時の目標提示（何をすればいいか・どこへ向かうか） | なし | **設計中**（本書） |

実装順は **CG2 → CG1 → CG3**。CG2 が最も安く、かつ CG1 を入れても
**ガイドに書かなければ誰も使えない**（＝ CG1 単独では今回の問題が再発する）ため先に置く。

## 1. CG1: キャラクターの登場条件

### 1.1 何が困っているか

セッションに参加登録したキャラは、**開始1ターン目から全員ぶんの定義がプロンプトに入る**。
「終盤まで存在を伏せたい人物」「特定の実績を取るまで現れない人物」を作者が仕込めない。
ロアには `condition` があるのに、**人物にだけ無い**のは機構の穴で、設計判断の結果ではない。

### 1.2 `設計_登場制御の見直し`（CS1）との関係——矛盾しない

[`設計_登場制御の見直し.md`](./設計_登場制御の見直し.md) は「シーン単位のキャスト絞り込み（`Scene.activeCharacterIds`）」を
**廃止**し、その却下理由に「**『その場に居るか』と『プロンプトに定義があるか』を1つのスイッチで兼ねているのが構造的な誤り**」を挙げた。
本書はこれを覆さない。**別の軸の話**だから。

| | CS1 が廃止したもの | CG1 が足すもの |
|---|---|---|
| 粒度 | **シーンごと**に手で外す | **世界に1回**書く条件式 |
| 可逆性 | 行ったり来たり（今この場に居る／居ない） | **単調・不可逆**（一度解禁されたら戻らない） |
| 意味 | その場に**居合わせているか** | その人物が**物語に登場したか** |
| 手間 | シーンが変わるたび＝誰もやらない | 作者が仕込む1回＝カセットの表現力 |
| キャッシュ | シーン境界で毎回入れ替わる | 解禁時に一度だけ変わる |

CS1 の却下理由（「粒度が細かすぎて誰もやらない」「居るけど喋らないが表現できない」）は
**どちらもシーン単位であることから来ている**。世界に1回書く単調な解禁条件には掛からない。
むしろ CS1 が「その場に居るか」を `Scene.note`（自然文）へ寄せた結果、
**「まだ物語に出てきていない」を表す場所が1つも無くなっている**——CG1 はその空席を埋める。

### 1.3 条件をどこに置くか（4案）

| 案 | 置き場所 | 判断 |
|---|---|---|
| a | `Character.appearCondition` | **却下**。Character は世界をまたいで再利用する素材で、条件は `stats[].id` 等**特定 World の定義を参照する**。素材が世界に依存する＝ライブラリの前提が壊れる |
| b | `World.characterGates[]`（characterId を持つ） | **却下**。World も配役に依存しない素材（`roles` はあっても `roleAssignments` は持たない）。World が実キャラ id を持つと、同じ世界を別キャストで遊べなくなる |
| c | `World.roles[].condition`（ロール単位で解禁） | **保留**。世界の概念で書けて筋は良いが、実サンプルでロールは「客」「乗員」のような**グループ**にも使われており（`日没後の占い館`＝7人2ロール）、ロール単位だと粒度が粗すぎて当たらない場合がある |
| **d** | **`Session.characterGates[]`**（＝カセットが持つ） | **採用**。世界と実キャラが出会う層はセッションだけで、`roleAssignments` / `introBindings` が**まさに同じ理由でここに居る**。前例そのままの置き場所 |

```ts
/** キャラクターの登場条件（CG1）。条件を満たすまでプロンプトへ注入しない＝AI はその人物を知らない。 */
export interface CharacterGate {
  characterId: string
  /** 解禁条件。`LoreEntry.condition` と同じ Condition。ゲートを持たないキャラは条件なし＝最初から登場可 */
  condition: Condition
}

export interface Session {
  // …
  /** 登場条件つきキャラ（CG1）。未設定＝全員が最初から居る＝現行の挙動 */
  characterGates?: CharacterGate[]
  /** 既に解禁を通知したキャラの id（CG1。`revealedLoreIds` と同じ役割・通知の重複防止だけに使う） */
  revealedCharacterIds?: string[]
}
```

`WorldStartPreset` には**足さない**。ゲートは配役と同じくキャスト固有の情報で、
World 素材だけを選んだ新規セッションには対応する実キャラが居ない（`roleAssignments` が startPreset に無いのと同じ理由）。

### 1.4 どこで落とすか

**`resolveRefs` の1箇所**（`gateLoreByCondition` の直後）。`gateCharactersByCondition` を
同じ形の純関数として書き、`sessionCharacters` を絞る。これで
**本編 system・【配役】・選択肢・レビュー・後付け画像生成の全経路が同時に「解禁済みだけ」を見る**
（`refs.characters` が唯一の供給元になっているため。[`prompts.ts:65,175,687`](../src/lib/prompts.ts)／[`store.ts:3159`](../src/store.ts)）。

**`resolveRefs` だけでは漏れる4経路**（ここは個別に塞ぐ）:

| # | 経路 | 漏れ方 | 対応 |
|---|---|---|---|
| 1 | `buildStateInfo`（[`store.ts:1800`](../src/store.ts)） | `inject:true` のキャラ別 stat/counter が**未解禁キャラの実名つきで**【状態（現在）】に載る | 解禁済み id を渡して relations/moods/stats/counters を絞る |
| 2 | `StatusView` / `StatusPanel` | プレイヤー側 UI に未解禁キャラの関係性・気分が並ぶ＝ネタバレ | プレイ画面（ドック）では未解禁キャラを出さない。**セッション設定（作者側）では出す** |
| 3 | レビューの `newCharacters` | 未解禁キャラの名前が本文に出た時、「新規の人物」として起案され**同名が二重にできる** | 既知の名前リストは**全 `characterIds`**（ゲート前）で作る。名前は起案の除外判定にしか使わないので注入は増えない |
| 4 | `knownSpeakersOf`（？バッジ・[`store.ts:1089`](../src/store.ts)） | 同上（未解決話者として ？ が付く） | 同じく**ゲート前**の `characterIds` を見続ける＝現行のまま変更しない |

**原則**: 「AI に渡すもの」だけをゲートし、**「アプリが同一性を判定するために持つもの」はゲートしない**。
これを外すと発見キャラ（FB7-E）と衝突する。

### 1.5 解禁の通知

`newlyRevealedLoreIds` / `revealedLoreIds` / `infoNotice: '新しい設定が明らかになりました'`
（[`store.ts:3876`](../src/store.ts)）を**そのまま複製**する。文面は `'新しい人物が物語に加わりました'`。
**名前は出さない**（ロアが中身を出さないのと同じ理由＝本編で自然に出るべきもの）。

### 1.6 キャッシュへの影響——無い

条件の入力（stat / counter / achievement / eventFired / group）は**すべてシーン境界でしか動かない**
（stat/counter/achievement はレビュー確定時、eventFired は `beginScene` の抽選時）。
したがってゲートが開くのもシーン境界だけで、**system プロンプトはシーン中は不変**という PC1+PC4 の制約
（[`prompts.ts:180`](../src/lib/prompts.ts) のコメント）を破らない。
例外は `StatusPanel` の実績手動トグルだけ（手動編集はもともとキャッシュを壊す）。

むしろ**キャッシュには有利**: 序盤は【登場人物】が短くなる（プロンプト中で最も長いブロックのひとつ）。

### 1.7 却下した案

- **未解禁キャラを `characterIds` から外し、解禁時に追加する**（状態を書き換える方式）
  → 分岐・チェックポイント復元のたびに `characterIds` の履歴が要る。
  **判定は毎回条件から導出する**（`gateLoreByCondition` と同じ）ほうが状態を持たずに済む。
- **「未解禁キャラは居るが喋らない」をプロンプト文で伝える**
  → [`計測_登場制御.md`](./計測_登場制御.md) が同型の指示文（CS3）を**全案不採用**にしている。
  定義を渡した上で「出すな」と言うのは効かない。**渡さない**のが唯一確実な手段。
- **条件を自然文で書かせる（`condition` ではなく prose）**
  → 条件エンジンの大原則「prose は読まない＝数・実績のみで判定（再現性のため）」（[`types.ts:151`](../src/types.ts)）に反する。

### 1.8 未決（実装前に決める）

1. **導入文（`opening`）に未解禁キャラが書かれていたら？** ——バリデーションで弾くか、許すか。
   **弾かない**方向を推す（導入文はそのまま掲載されるだけでモデルには渡らない）。
2. **`required:true` のロールに未解禁キャラしか居ない場合**の開始バリデーション。現行 `validateCasting` はゲートを見ないので開始できる。**そのままでよい**と考える（配役は作者の宣言、ゲートは登場のタイミング）。
3. **UI**——`SessionEditor` のキャラチップに条件エディタを付けるか、`CassetteEditor` 側に置くか。条件エディタは `WorldEditor` に既存（実績・エンディング）なので**部品は流用できる**。

## 2. CG2: カセット作成ガイドの網羅性

「ロアの注入条件がどれにも書かれていなかった」「トリガーが空だった」は**AI の失敗ではなくガイドの欠落**。
実際に `types.ts` と突き合わせた結果が下表。

### 2.1 欠落（ガイドに1文字も無い）

| 項目 | 型 | 何が書けなくなっているか |
|---|---|---|
| `LoreEntry.condition` | `Condition` | **今回の指摘そのもの**。条件付き解禁ロアが書けない |
| `ScheduledEvent` **の項ごと** | `day` / `slot` / `name` / `note` / `condition` | 世界の骨組みには載っているのに定義が無い＝特別イベントを正しく書けない |
| `Clause` の `eventFired` | `{kind:'eventFired', eventId, have}` | イベントの連鎖（「あの事件のあとだけ」）が書けない。**バックログで最優先とされた節** |
| `Clause` の `group` ＋ `Quantifier` ＋ `subject` | ロールへの定量条件・当事者指定 | 「常連の2人以上が好感度60以上」型が書けない。エンディングの当事者選択も |
| `StatDef.deltaMin/deltaMax` | `number?` | レビュー1回あたりの変動幅を作者が縛れない |
| `CounterDef.note/amountMin/amountMax` | `string?`/`number?` | **`note` は「一度きりの出来事」を狙って当てるための唯一の担保**（型のコメントにそう書いてある） |
| `World.reviewGuidance` | `string?` | 世界固定のレビュー方針（「体力は毎シーン必ず消耗させる」）が書けない |
| `startPreset.initialDirective` | `string?` | 序盤の立ち上げ方の非表示指示 |
| `startPreset.newCharacterPolicy` | `'allow'\|'avoid'` | 未定義キャラの登場可否 |
| `startPreset.openingSceneNote` | `string?` | **1シーン目に誰が居るか**。CS2 で新設したが、同書 §9 に書いた「ガイドへ追記」が実施されていない |
| `startPreset.introTags` ＋ `session.introBindings` | `IntroTag[]` | 導入文の `@タグ` 置換（後述のとおりガイドの記述は古い方式のまま） |

### 2.2 誤り（ガイドが**間違ったことを教えている**）

1. **`relationFlag` 節**（ガイド §4）。この kind は FB9-C で**型から撤去済み**。
   ガイド通りに書かれた条件は、読み込み時に `stripLegacyFlagClauses`（[`store.ts:491`](../src/store.ts)）が**黙って削除する**。
   実績・エンディング・イベントが**理由の分からないまま発火しなくなる**。
   > さらに `stripLegacyFlagClauses` は `entries`（`LoreEntry.condition`）を掃除対象に含めていない。
   > 旧データには存在しない組み合わせなので既存セーブでは起きないが、**ガイド通りに新規作成されたカセットでは
   > 未知 kind が `evalClause` の `default: false` に落ち、そのロアが永久に解禁されない**。CG2 で原因は消えるが、
   > 掃除側にも `entries` を足しておくのが安全（1行）。
2. **導入文の `@ロール名`**（ガイド §2・§7）。A-1 で置換タグは `roles` から `IntroTag` へ**分離済み**。
   `roles` は【配役】のプロンプト注入専用で、導入文の置換は担わない。ガイドは旧方式のまま。
   `introTags` が空のまま `@マスター` と書かれた導入文は、`resolveIntroText` が置換対象を1つも見つけず
   **そのまま画面に出る**（エラーにもならない）。
3. **導入文の `@名前(感情)「セリフ」`**（ガイド §7。**書き直しの最中に見つけた3件目**）。
   構造化出力のパーサ（[`structured.ts:46`](../src/lib/structured.ts)）は名前を「行頭 `@` から最初の `「` まで」で
   取るだけで、**感情の括弧を解釈しない**。`@マスター(neutral)「…」` は `マスター(neutral)` という名前の
   話者として扱われ、参加キャラに解決できず**未解決話者の ？バッジ＝発見キャラの導線**に流れる。
   ガイドが参照していた2本のサンプルは、この書き方を **9件・4件**含んでいた。

### 2.3 参照サンプルが古い

ガイドは「参考にできる完成品が `samples/純喫茶こはく.json` と `samples/螺旋塔アルシオン.json` にある」と書くが、
実測するとこの2本には **`condition` 付きロア0件・`eventFired`/`group` 0件・`openingSceneNote`/`initialDirective`/`newCharacterPolicy`/`introTags` すべて無し**。
一方 `日没後の占い館.json`（ロア条件5件・`eventFired`・`group` あり）と `深海基地シレーヌ.json`（同3件）は**ガイドから参照されていない**。

**AI は仕様書より実例に強く引かれる。** 加えて古い2本は §2.2-3 の `(感情)` 記法を9件・4件含んでおり、
参照させると誤りごと写される。（パスも実体は `samples/samples/` 配下で、ガイドの記述 `samples/…` と食い違っている。）

> **決定（2026-08-30）: サンプルへの参照は消す。** 差し替えではなく削除。ガイドが実例に依存している限り、
> 実例が古くなるたび同じ事故が起きる。**ガイド1ファイルで完結させ**、代わりに §11 のチェックリストを
> 「構造／条件まわり／出し惜しみ／導入文」の4群に厚くして、仕様側だけで自己検査できるようにした。

### 2.4 空トリガーが黙って死ぬ

`keys: []` かつ `alwaysOn: false` のロアは `splitLoreEntries` のどちらの籠にも入らない＝**永久に注入されない**。
`WorldEditor` にも取り込み時にも警告が無いので、作者は「書いたのに効かない」に気付けない。

**対策は2段**:
- ガイド側: `alwaysOn:false` なら `keys` は1語以上必須、と明記＋§10 チェックリストに1行
- アプリ側: `WorldEditor` のロア項目に警告バッジ（「トリガー語が空で『常時』もオフ＝注入されません」）。
  実装は既存の `added-badge` と同じ見た目で数行

### 2.5 対策のまとめ

ガイドを「型定義から機械的に導出できる網羅表」＋「作例」の二段構成にする。
`types.ts` に項目が増えるたびガイドが腐るのが今回の根本原因なので、
**AGENTS.md の「編集を伴うコミットでは AGENTS.md も同じコミットで更新する」と同じ規約を、
`types.ts` の公開データ型 → `カセット作成ガイド_AI用.md` にも掛ける**（AGENTS.md に1行追記）。

## 3. CG3: 開始時の目標提示

### 3.1 現状——材料は全部あるのに、見せていない

| 材料 | 現状の置き場所 | プレイヤーに届いているか |
|---|---|---|
| 結末の一覧と説明（`EndingDef.name/description`、`hidden` でネタバレ制御済み） | ドックの「状態」タブ | **届かない**（`DEFAULT_UI.dockTab` が `null` ＝**既定でドックは閉じている**） |
| 実績（`AchievementDef`、`hidden` あり） | 同上 | 同上 |
| 期間（`timeline.spanLabel`＝「閉店までの三日間」・`totalDays`） | どこにも出ていない | **届かない**（トップバーは `scene.timeLabel`＝「1日目 朝」だけ） |
| 次の一手 | 導入直後の選択肢（`choiceMode !== 'off'`） | **届いている** |

つまり**「行動の指針」（戦術）は既にあり、欠けているのは「ゴール」（大域）**。
そしてゴールの材料は作者が既に書いており、`hidden` フラグという**ネタバレ方針まで作者が宣言済み**。
出していないだけ。

### 3.2 案

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | **開始ブリーフィング**——導入文の直後に、既存データから自動組み立てた1枚のカードを出す。`spanLabel`＋総日数／`hidden:false` のエンディング名＋説明／同じく実績の数／「状態パネルでいつでも見られます」の1行 | **本命**。作者の追記ゼロで既存カセットにも効く（＝**準備ゼロ**の判定軸を満たす）。`hidden` を尊重するのでネタバレしない |
| **B** | 作者が書く「目的」欄を新設（`WorldStartPreset.objective`） | **保留**。A で足りない場合のみ。[`設計_登場制御の見直し.md`](./設計_登場制御の見直し.md) §6（CS4）が「**既定文は書かない・入力欄の案内で支える**」を実測で結論づけており、新しい必須記入欄を足す方向は同じ轍 |
| **C** | 初回セッションだけドックを既定で開く（`messages.length === 0` のとき `dockTab: 'status'`） | **A と併用で採用**。A が「ドックに続きがある」と言うなら、最初は実際に開いておくのが素直 |

### 3.3 推奨

**A ＋ C**。B は A を出してから判断する（未実装のまま残す）。
A の中身は**エンディング一覧が主役**——`EndingDef.description` は「一覧・到達時に見せる説明（条件そのものは晒さない）」と
型のコメントが既に定義しており、**プレイヤー向けの目標提示文としてそのまま使える**。

エンディングを1件も定義していないカセット（`螺旋塔アルシオン` がそう）では、
ブリーフィングは期間と操作案内だけに縮む。**空なら出さない**を徹底する（情報の無いカードを出さない）。

> 副次的な効果として、**カセット作者がエンディングと実績を書く動機**になる。
> 今は書いても閉じたパネルの中にしか出ないので、書く理由が弱い。

### 3.4 ついでに直すもの

`ChatPanel.tsx:1243` の開始前ヒント「**登場キャラはシーン編集で絞れます。**」は
CS1 でシーン単位の絞り込みを撤去した際の**消し漏れ**（`SceneEditor` にその UI はもう無い）。
群像モードの初回に、存在しない機能を案内している。

### 検証

- 既存カセット（`characterGates` なし）を開始 → **全キャラが従来どおり最初から登場する**

- 未解禁キャラの名前をプレイヤーが本文に書いた場合、**発見キャラとして二重に起案されない**
