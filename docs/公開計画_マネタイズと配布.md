# 公開計画 — マネタイズ・配布・公開前実装要件

2026-07-25 の戦略議論で確定した内容。**事業判断と、それに紐づく公開前の実装要件**をまとめる。
機能そのものの設計は `設計_*.md` 側にあるので、ここには「公開するために決めたこと」だけを置く。

> **出典の確度表記**：【公式】＝エイシス公式告知等の一次情報／【二次】＝個人ブログ・まとめ記事のみ／【未確認】＝調べたが記述を発見できず、問い合わせが必要。

## 0. 製品の位置づけ（すべての前提）

**「ノベルゲーム」ではなく「挿絵入りの本（ライトノベル形式）」を目指す。**

VN の画面構成（絵がメイン・文章は下のボックス）は、AI 生成とは構造的に噛み合わない。
理由は「AI の出力を事前に予測できないため、素材を用意しておけない」こと。
一方で挿絵は「本文の後から生成する」ものなので、この問題が原理的に発生しない。

| 要素 | 決定 | 根拠 |
|---|---|---|
| 全面背景・立ち絵（透かし） | **廃止** | 同一ピクセルに2つの注意対象を置く構造問題。濃さ調整では解けない（絵は見るに堪えず・文字はコントラストを失う両損） |
| 挿絵 | **残す**（本文フローに逐次挟む図版） | 視線が「読む→絵に到達→見る→続きを読む」と逐次になり、競合しない。ラノベの形式そのもの |
| 挿絵の役割 | 読解補助では**なく**、**獲得（SNS拡散）・報酬（収集）資産** | 絵を足しても体験の95%は読むこと。読まない層は絵の有無で動かない |
| 音 | 単一のアンビエント床か**無音** | 情報量の多い素材（セミの声＝夏・屋外・昼）は予測不能な文章に否定されて壊れる。主張しない素材は壊れようがない |
| ムード色 | 将来の代償措置として検討 | 背景喪失で失う「持続する空気感」を、文字と絶対に喧嘩しない色で部分的に補う |

**「本に寄せるとパイが狭まる」への結論：狭まらない。**
選択肢は「狭い読書層 vs 広い絵の層」ではなく「狭い読書層をちゃんと満たす vs 中途半端に満たして絵の層も獲れない」。
日本市場の反証＝なろう・カクヨム・テキスト主体のキャラチャットは挿絵ゼロで巨大規模。

**成長レバーは絵ではない：**
1. **インタラクション密度**（3000字を黙って読ませるより 300字×10回＋毎回選択）
2. **絵の量をユーザーが選べる可変比率**（VN は制作時に焼き込まれるが AI 生成は可変。しかも絵を欲しがる層ほど計算コストを食う＝課金意欲と一致）

## 1. プラットフォームと規約

### 1.1 結論：DLsite ＝ 棚（集客）／BOOTH ＝ 母艦（自由）／Steam ＝ 回避

| | 役割 | 置くもの |
|---|---|---|
| **DLsite** | 集客。棚に並ぶこと自体が広告 | 制作版（ツール/アクセサリ）、自作カセット（作品として主要フロアへ） |
| **BOOTH** | 自由度。審査なし・頻繁な更新可 | 無料版の配布、実験版 |
| **Steam** | **使わない** | — |

### 1.2 Steam を避ける理由

- 決済の圧力元は Steam ではなく**カード会社**。Steam を避けても自前でカード決済を持てば同じリスクが追ってくる。逃げ先は「Steam 以外」ではなく「この種の作品を前提に決済網が組まれている場所」＝ DLsite / BOOTH。
- Steam は**アプリ内課金の外部決済を認めない**ため、BYOK ＋ 外部クレジット販売と構造的に相性が悪い。
- ライブ生成 AI は開示に加え「違法コンテンツを防ぐガードレールがある旨」の表明が要る。BYOK では「保証できません」になりがちで審査摩擦になる。

### 1.3 DLsite はツールを扱う（当初の想定は誤り）

**【公式・実地確認】** 作品形式「ツール/アクセサリ」が**通常の同人フロア**に約 1,089 件存在する。
<https://www.dlsite.com/home/works/type/=/work_type/TOL>

並んでいるもの：RPGツクールMZ／SRPG Studio／ティラノビルダー PRO／アクションゲームツクールMV／Voice Script Editor 3／**HermitNode「孤高のAI執筆室」(¥990)**／Waifu2x (¥55)／Anime2x (¥110)。

- 「DLsite は作品を扱いツールは扱わない」という線引きは**存在しない**。制作エンジンがまさに売られている。
- **ティラノビルダーは本計画のほぼ完全な先例**（エンジンをツールとして売り、それで作られた作品は各作者が売り、ランタイムは無料）。

### 1.4 AI 生成フロアの隔離リスク → ほぼ回避できる見込み

**【公式】** AI生成フロア（2024/2/21 公開）は既存フロアから**分離した独立フロア**。
全年齢 <https://www.dlsite.com/ai/> ／ R18 <https://www.dlsite.com/aix/>
さらにユーザー側に「AI一部利用を除外」チェックと非表示設定がある。

**【公式】** 区分の定義（[エイシス告知](https://info.eisys.co.jp/dlsite/bb3b0b976520e0fd?locale=default)）：

- **AI生成作品** ＝「AIでの生成物をメインコンテンツとして利用している場合」
- **AI一部利用** ＝「マンガ、ゲームの背景使用等、AI生成物の利用が限定的な部分に留まり」利用者がその限定性を認識できる場合

**本製品は隔離対象外の線が濃い。** 根拠：

1. **HermitNode「孤高のAI執筆室」が AI生成フロアではなく通常フロアのツール棚にある。** Waifu2x・Anime2x も同様。
2. AIフロアのルール群（収録枚数上限、LoRA規制、写実NG、制作過程のPSD提出要求）は明らかに**作品に同梱される事前生成素材**を想定して書かれている。
3. 本製品は**出荷物に AI 生成物が1バイトも含まれず**、生成は購入者が自分の契約で実行時に行う。

**注意：** AI補助ツールに対し DLsite が厳しいとする記事は、**作者が自分の絵をAIで作った場合**の話であり軸が違う（キャラ絵にAIを使うと「AI生成作品」になる、という運用）。本ケースには効かない。

→ ただし運用の観察からの推測なので、**問い合わせで確定させる**（§4）。

### 1.5 TRPG 二次創作と SPLL

**【公式】** DLsite は TRPG 二次創作の**公式電子出版サイト**に指定され、SPLL（小規模事業者限定ライセンス）を運用している。
<https://info.eisys.co.jp/dlsite/7b39a26bf1a41f67?locale=default>

- 対象は**ガイドライン掲載の特定 TRPG のみ**（全 TRPG ではない）
- 電子作品は売上額にかかわらず対象。登録前に TRPG 権利部から**申請番号の取得**が必要
- **売上に対しライセンス料 10%**
- 公式の計算例：1,000円の作品で**作者手取り 479円**（SPLL 10%＋源泉徴収込み）

**オリジナル世界観なら無関係。** ただし UGC を進めるなら、**カセット作者向けに「既存 TRPG を題材にする場合の手続き」を案内する責任**が発生する。

裏返せば、TRPG 層が DLsite に公式に招かれているという事実は、ターゲット選定の裏付けでもある（TRPG 層は CoC もシノビガミも画面が文字とダイスだけ＝**絵がなくても金を払うことを実証済みの客**）。

### 1.6 成人向け：3つの決定に分解する

「許容するか」を単一の決定として扱わない。

| | 決定 | 判断 |
|---|---|---|
| a | 技術的にフィルタしない | **YES**（BYOK＝道具屋の帰結） |
| b | **本体を R18 作品として登録する** | **NO** |
| c | カセットの R18 を許す／自分でも作る | **YES**（ここが R18 市場の収益経路） |

**b を NO にする理由：**

- **【二次】** DLsite では成人向けが全年齢の **10倍以上**売れている（[濡羽十色](https://note.com/dlwatcher/n/nfe0db6350561)）。作品数も男性向け成人ゲーム約26,000 vs 全年齢ゲーム約3,000。
- しかし **RPGツクールもティラノビルダーも全年齢ソフト**。R18 フロアはツクール製・ティラノ製の成人向け作品で溢れているのに、**エンジン自体に R18 ラベルは付いていない**。
- 本体を全年齢にすると：全年齢フロアに載る ＋ R18 フロアのカセットからも逆流を受ける＝**両取り**。
- 本体を R18 にすると：全年齢フロアを丸ごと失う。ツールは「抜けるかどうか」で買われないので R18 ラベルの集客効果がほぼ働かず、**リーチが狭まるだけでリターンがない**。

**BYOK との衝突（重要）：**

**【公式報道】** 主要モデルは現状ほぼ全て成人向けを禁止している。OpenAI の「adult mode」は **2026年3月に無期限保留**（年齢確認で未成年の約12%を成人と誤判定したことが理由）。Anthropic・Google も禁止。

→ R18 を看板にして買った人が、案内どおり Gemini 無料枠を設定し、最初のシーンで拒否される＝**最悪の初体験**。返金とレビュー爆撃のコンボになる。

**したがって：訴求しない・塞がない。** 実装で必要なのはフィルタ削除ではなく**モデル選択の案内**（§5.7）。

**テキスト主体は法的に有利：**

- 文章：日本では成人向けテキストの流通は確立しており、モザイク等は直接かからない。
- 画像：刑法175条のモザイク要件、AI生成フロア規則（写実的NG・LoRA規制）が絡む。ただし**実行時にユーザーの手元で生成する＝頒布ではない**ので本体側には原則かからない。
- **危険なのはカセットに画像を同梱した瞬間**。そこで初めて「自分が頒布している」になる。
  → **カセットに画像を同梱しない設計**にすれば、この問題群を構造的に回避できる（§5.2 に実装要件）。

**絶対に譲れない線：**

1. **未成年の性的描写**を、自分が配る看板カセット・サンプル・宣伝物に入れない（児童ポルノ禁止法・プラットフォーム規約ともに一発アウト）。
2. **ストアページ・サンプル・宣伝物**で成人向けを売り文句にしない。トラブルはほぼ全部ここから来る。

### 1.7 クレジット販売はしない

- **【未確認】** DLsite サークル規約に、追加課金・外部決済・外部サービス必須の作品に関する条項は**見つからなかった**（禁止も許可もされていない）。<https://www.dlsite.com/home/circle/regulations>
- そもそも **BYOK 一本にすれば、この論点ごと消える。**
- クレジットを売って自分の鍵で回すと、**自分がコンテンツ生成の当事者**になる。出力の責任・決済事業者への説明責任・通報対応が全部乗る。BYOK なら「テキストエディタを売っている道具屋」で済む。
- 日本で**残高型のクレジット（前払式支払手段）**を売ると、未使用残高が一定額を超えた時点で資金決済法上の届出・供託義務が発生しうる。個人開発で背負うには重い。
- **APIキーを取れない人への救済は OpenRouter への誘導で足りる**（1回の登録で全モデルに届き、決済もコンプラも先方が持つ）。自作するより圧倒的に得。

## 2. 商品構成と価格

### 2.1 三層モデル

| 層 | 内容 | 価格 | 置き場 |
|---|---|---|---|
| **無料版** | プレイヤーとして**無制限**。他人のカセットを何本でも遊べる。ペルソナ・セッション設定は編集可。**キャラ・世界観は閲覧のみ** | ¥0 | BOOTH・自サイト |
| **カセット** | 完成した物語（世界観＋キャラ＋ペルソナ＋開始設定のセット） | ¥300〜700 | DLsite / BOOTH（第三者作者も販売） |
| **制作版** | **エンジンの制作ライセンス**。キャラ・世界観の作成／カセットの書き出し | ¥2,500〜3,500 | DLsite（ツール/アクセサリ） |

**価値のはしご：** 無料で遊ぶ → 気に入った話を数百円で買う → 自分でも作りたくなって数千円払う。
各段が別の欲求に対応し、上の段が下の段を殺さない。

**制作版に全カセットを同梱しない。** 軸を分ける（制作版が売るのは**コンテンツではなく作る権利**）。同梱するとカセット売上と本体売上が食い合い、値付けも説明も崩れる。

### 2.2 値付けの根拠

- DLsite のツール棚は二極化している。**ユーティリティ ¥55〜990／制作エンジン数千円**。
  → **「ユーティリティ」に見えると ¥1,000 の帯に引きずられる。**「エンジン／制作ツール」として提示できるかがそのまま価格帯を決める。
- DLsite はセールが売上の主戦場なので、**30〜50%引きに耐える定価**にする。定価を安くしすぎるとセールで戦えない。
- カセットは**衝動買いの帯**（¥300〜700）を外さない。

### 2.3 「エディタが薄いのに課金してよいのか」への回答

価値の本体はランタイムであり、エディタは実質 JSON 入力で薄い。しかし——

> **有料ティアが売っているのは、エディタの実装量ではなく「無料ランタイムの観客へのアクセス権」。**

薄いフォームでも、その出力を再生できる人が1万人いれば、1万人分のオーディエンスへの入場券の価値がつく。逆にどれだけ豪華でも、遊べる人がゼロなら無価値。
**価値は無料ランタイムの普及数に比例し、エディタの実装量はこの式に出てこない。**
しかも無料ランタイムが広まるほど、薄いままのエディタの価値が上がる。

「実装が軽いから課金が気引ける」は**労働価値説の罠**。価格は自分の手間ではなく買い手の便益と代替手段で決まる。非プログラマが JSON スキーマを学び分岐の整合を手で保つのに40時間かかるなら、それを30秒に変えるツールは一晩で作っていても40時間分の価値がある。

→ **名乗りを「JSONエディタ」ではなく「AIストーリーエンジン（の制作ライセンス）」にする。** 中身を1バイトも変えずに価値の伝わり方が変わる。

## 3. マーケティング戦略

### 3.1 前提：広告費では勝てない

競合（サーガ&シーカー）は広告を焚いている。同じ土俵では勝てないので、**製品の副産物が勝手に宣伝になる**構造を作る。

### 3.2 集客の本体はカセット（ツクール構造）

**DLsite のツール棚は入口ではなく着地点。**

ツール棚 1,089 件は DLsite 全体では見えない量で、自分から掘らないと辿り着けない。
「ツールを見たことがない」という感覚は正確で、原因は方針ではなく**導線**（DLsite の導線は音声・マンガ・ゲームで作られている）。**これは BOOTH でも同じなので、BOOTH に逃げても解決しない。**

RPGツクール／ティラノビルダーが売れているのは、ツール棚が閲覧されているからではなく、**それで作られた作品が主要フロアに大量に並んでいるから**。プレイヤーが遊び、「これで作れるのか」と本体に逆流する。

→ **カセット層は収益源であると同時に、本体の唯一の集客導線。**
→ 優先順位：**本体のストアページを磨くより、カセットを主要フロアに並べることのほうが効く。**
→ 自作の看板カセットは、ツールではなく**ゲーム／ノベル作品として**登録する。

### 3.3 2つの自走する宣伝装置

1. **プレイ結果を小説／リプレイとして書き出せること**
   「本に寄せる」決断の最大の副次効果。VN のセーブデータは他人に見せられないが、**きれいに組版された物語テキストはそのままカクヨムにも note にも X にも貼れる**。面白い話ができるたびに宣伝物が世に出る。
   TRPG 界隈には**リプレイ文化**（セッション記録を読み物として公開する）があり、これに直結する。

2. **カセットを1ファイルで配布できること**
   SillyTavern がキャラクターカードのエコシステムで伸びたのと同じ構造。しかも本製品は条件やキャラ変数まで組めるので、**配布物が「プロンプト」ではなく「作品」になる**。競合の「シンプルな設定項目」に対する明確な差別化。
   カセットが20本並べば、**エンジンの広告が20個、無料で棚に並ぶ**。

### 3.4 自作カセットは全年齢と R18 の両方を出す（役割が違う）

**R18 は「到達」は強いが「拡散」は弱い。**

| | 全年齢カセット | R18 カセット |
|---|---|---|
| 役割 | **拡散**（SNS共有・実況可。本体ストアのサンプル兼用） | **到達**（10倍フロアでの発見） |
| 前提モデル | Gemini 無料枠でそのまま動く | 無検閲モデルへの案内が必須 |
| 分量 | 看板として厚く | 短編で可 |

- R18 は**実況・配信が不可能**、X でもセンシティブ扱いで検索から落ちる、公開の場に貼れない。
  → §3.3 の拡散仮説（プレイヤーが物語を書き出して共有する）と**構造的に相性が悪い**。
- **順序は全年齢が先。** 無料枠オンボーディングが本当に3分で通るかを先に検証する必要がある。R18 を先に出すと、オンボーディングの不備とモデル拒否が混ざって原因を切り分けられない。
- **R18 カセットには、モデル設定案内を最初の画面に同梱する。** これがないと拒否されて終わる人を量産する。
- 看板級を2本作るのは個人開発では重いので、R18 側は短編で割り切る。

### 3.5 やらないこと

- **Ci-en / Fanbox**：継続的なプレッシャーが本人の性に合わないため採用しない。初期認知は §3.3 の2つに全振りする。
- **広告出稿**：しない。

### 3.6 必要規模の見積もり

想定を大きくしすぎない。**個人開発の副業として意味のある水準は 1000本程度**で、¥2,500 なら 250万円。
DLsite ＋ X ＋ TRPG/AI 界隈で数回話題になれば届く範囲で、広告費は要らない。
**無理筋なのは「万人に安く広く」のほうで、「狭くて濃い層に、道具として売る」なら買い切りは十分成立する。**

## 4. 必要手続き

### 4.1 DLsite への問い合わせ（公開前に必須）

§1.4 の分類が確定するまで、DLsite 前提の設計を固めない。

```text
作品形式「ツール/アクセサリ」での登録を検討しているソフトウェアについて
確認させてください。

1. 本ソフトは、購入者自身が契約したAIモデルのAPIキーを設定し、
   実行時に文章生成を行う創作支援ツールです。配布物にAI生成物は
   含まれません。この場合「AI生成作品」「AI一部利用」の申告は
   必要でしょうか。また通常フロアでのお取り扱いとなりますか。

2. 動作に購入者自身の外部サービス契約（APIキー）が必要な作品の
   販売は可能でしょうか。審査時の動作確認について、どのように
   ご対応すればよいかご教示ください。

3. 買い切り作品の購入後に、当方が別途提供する有償の生成代行
   （消費型のクレジット等）を購入できる形は認められますか。
   認められない場合、当方の外部サイトでの提供も不可となりますか。

4. 本ソフトウェア用のシナリオデータを、第三者の作者様が
   DLsiteで販売することは問題ありませんか（本体ランタイムは
   無償配布する想定です）。
```

- **1** は §1.4 の先例からほぼ答えが見えている（通常フロア）
- **2 が本当の未確認事項。** DLsite の審査には**動作確認**が含まれるため、**審査担当者が実際に起動できる必要がある**。ユーザー自身の API キーが必須の製品は「キーがないと何も動かない」問題に当たる。審査用の手順書、またはダミー動作モードの用意が必要かもしれない。**規約より先に潰しておくべき現実的な論点。**

- **4** は UGC 計画の成否が懸かる。ティラノビルダー／ツクールの前例があるので通る見込みが高い

## 5. 実装要件

### 5.1 無料版と有料版の線引き

**課金点は「配布」ではなく「能力」に置く。**

当初は「作成は自由・配布に課金」を検討したが、**カセットがプレーンテキスト（JSON）である以上、この方式は原理的に機能しない**：

- 作成できてしまえば JSON は既にディスク上にある。「書き出し」は工程ではなく**ファイルをコピーするだけ**。ゲートを置く場所が物理的に存在しない。
- 逆向きも成立する。**他人のカセットのテキストを自分のエディタに貼れば、そこから改変してフル機能に到達できる。**
- 規約に制限を書いても**実行力がない**。

ツクールで配布課金が機能するのは**出力がパッケージだから**（ビルドという実際の工程があり、そこにゲートを置ける）。本製品はその条件を満たさない。

**線引き：**

| 機能 | 無料版 | 制作版 |
|---|---|---|
| カセットを遊ぶ | ○ 無制限 | ○ |
| ペルソナの編集 | ○（**フィールドを絞る**・§5.2） | ○ |
| セッション設定の編集 | ○ | ○ |
| キャラクターの**閲覧** | ○（読み取り専用） | ○ |
| 世界観の**閲覧** | ○（読み取り専用） | ○ |
| キャラクターの**編集・新規作成** | **×** | ○ |
| 世界観の**編集・新規作成** | **×** | ○ |
| カセットの作成・書き出し | **×** | ○ |
| 未署名カセットの読み込み | **×**（§5.5） | ○ |

**閲覧は許可する。** カセットの JSON はどのみち手元のディスクにあるので、読めること自体は何も渡していない。
そして「こう作るのか」が見えることが、**制作版への最も自然な導線**になる。編集操作で「制作版が必要です」と出す。

**説明可能な境界：「遊び方を変える」は無料、「世界を作る」は有料。**

**収益上の副次効果：** 課金点が「配布したい人」から「何か作りたい人」に移るので、**支払い母数が広がる**。

### 5.2 抜け道の精査

| # | 抜け道 | 対策 | 状態 |
|---|---|---|---|
| 1 | **ペルソナに全部書く** — ペルソナのスキーマがキャラクターと同等に豊かだと、キャラを何人もペルソナ欄に詰めて実質的な作成ができる | ペルソナのフィールドを絞る（名前・容姿・性格程度）。**変数・条件・関係性は持たせない** | 要確認・要実装 |
| 2 | **プレイ中の編集経路** — セッション途中でキャラ設定を調整できる導線があれば同じ穴 | プレイ中の編集 UI を洗い出して無料版で塞ぐ | 要調査 |
| 3 | **手書き JSON の読み込み** | **カセット署名**（§5.5） | 要実装 |
| 4 | **他人のカセットを改変して再利用** | 署名が壊れるので拒否される（§5.5） | 要実装 |
| 5 | **実行時フラグの反転** | ビルド時にコードを除去（§5.3） | 要実装 |
| 6 | **セッション設定経由の書き込み** — Session 型がカセット定義とプレイ進行を兼ねているため（§5.6-③）、設定編集画面から定義部分に書けてしまう可能性 | 無料版が書けるフィールドのリストを明示的に定義する | **要調査（最優先）** |
| 7 | **カセットへの画像同梱** — 法務リスク（§1.6）。抜け道ではないが同じ「同梱物」の論点 | カセットに画像を含めない設計にする | 要判断 |

**突破ラインの目標：** 「**JSON を手書きできる人**」まで下げる。
それは「構造がわかればツールは要らない層」と**同じ集団**で、最初から顧客ではない。
ローカルアプリの防御としてはそこが妥当な底で、それ以上は費用対効果が合わない。

### 5.3 ビルドの分離

**方針：コードベースは1つ、ビルド成果物は2つ。**

- 保守が分岐する問題は**単一リポジトリ＋ビルドフラグ**で回避できる。
- **実行時フラグ（`if (isPaid)`）は使わない。** ローカルアプリでは設定ファイルや devtools で簡単に反転される。
- **無料ビルドには編集系のコードそのものを含めない**（別エントリポイント、またはビルド時の dead-code 除去）。

これで突破ラインが §5.2 の目標水準まで下がる。

**実装メモ：** 現状 Vite + React + Tauri。`import.meta.env` のビルド時定数で分岐し、Rollup の tree-shaking で編集系モジュールを落とす形が素直。ただし**動的 import 越しに残らないか**をビルド成果物で実際に確認すること（バンドルを grep して編集系の文字列が残っていないか見る）。

### 5.4 認証・ライセンス

**結論：まず認証コード機構を作らない（実装ゼロ）。**

理由：**DLsite で売るなら、購入＝制作版のダウンロード。** 認証コードを挟む必要がない。

- 無料版は BOOTH・自サイトで別バイナリとして配る
- 制作版は DLsite の購入者だけがダウンロードする
- アップグレードは「制作版を落とし直す」だけ。データは `%APPDATA%` に残るので引き継がれる

**認証コードによる機能開放は、ビルド分離と正面から衝突する：**

- 無料ビルドから編集コードをビルド時に除去すれば、認証コードは「無いコード」を開放できない
- 認証コードで機能が生えるということは、**編集コードが無料ビルドに入っている＝実行時フラグ**ということ。§5.3 で退けた地点に戻る

**将来どうしても必要になったら**（無料版の中からその場でアップグレードさせたい UX を取る時）：

- **オフラインの署名付きライセンスファイル**にする（Ed25519 等。公開鍵をバイナリに、秘密鍵は手元）
- キー ＝ 購入 ID ＋ 発行日を署名したトークン
- **オンライン認証にしない。** サーバ運用・プライバシー・オフライン起動不能の三重負債で、同人規模では割に合わない
- 失効はできない（オフラインのため）。流出したら次バージョンでブロックリストを同梱する程度

### 5.5 カセット署名（暗号化ではなく署名）

**目的を精密にすると、塞ぎたいのは「読めてしまうこと」ではなく「作れてしまうこと」。**

**実装：カセットに署名を付け、ランタイムは署名の無いカセットを拒否する。署名鍵は制作版だけが持つ。**

- 手書き JSON → 署名が無い → 読み込み拒否。**目的を正確に達成**
- 他人のカセットを改変 → 署名が壊れる → 拒否
- 実装コストが低い（既に `spec_version` を持つカード形式に `sig` を足すだけ）
- 副産物として**作者の同一性証明**が付く。UGC マーケットで後々効く

**暗号化はしない。** 理由：

- 鍵がクライアントにある以上、解読可能＝難読化にすぎない
- 壊れたカセットのサポートで中身が見られない
- **他人のカセットを読んで学ぶ・フォークするという UGC の成長ループを殺す**
- 「何を隠しているのか」という不信感
- そして——**技術に疎い人にとっては JSON を手書きすること自体が既に無限のハードル。** 暗号化が効くのは「JSON は手書きできるが暗号は解かない」という狭い中間帯だけで、ROI は見積もりより低い

**既知の限界：** 署名鍵は制作版バイナリの中にあるので、購入者が抽出すれば署名オラクルを作れる。ただしそれは §5.2 の突破ライン（JSON を手書きできる層）と同じ水準で、許容する。

### 5.6 スキーマ・バージョニング（公開前の最優先事項）

**「完璧な構造にしてから公開」は不可能かつ不要。** 未実装機能（ダイス判定・シークレットロア・発見キャラ等）が将来フィールドを要求する以上、完璧なスキーマは今書けない。完璧を待つほど、未実装機能を空想で設計する泥沼に入る。

**後方互換は「構造の固定」ではなく「バージョン番号＋マイグレーション」で達成する。**
公開前に固めるのは**スキーマ全体ではなく「封筒」だけ**。

#### ソース確認の結果（2026-07-25 時点）

| # | 項目 | 現状 | 対応 |
|---|---|---|---|
| ① | **アプリ状態の `schemaVersion`** | **無い。** [store.ts:4559](../src/store.ts) の persist 設定に zustand の `version` も `migrate` も無く、「クリーンブレイク：…後方互換は不要なため migrate 連鎖は持たない」と明記されている | **最優先で追加。唯一あとから足せない** |
| ② | **配布カードの `spec_version`** | **ある。** [cards.ts:436](../src/lib/cards.ts) で `{ spec: 'aist_cassette', spec_version: '1.0', data }`。世界観・ペルソナカードも同様。**ただし読み込み側で検証していない**（書いているが見ていない） | 検証入口を1箇所作る。`minRuntimeVersion` と署名検証も相乗りさせる |
| ③ | **カセット定義とプレイ進行の分離** | **型としては未分離。** [types.ts:639](../src/types.ts) の `Cassette.session: Session`、[cards.ts:47](../src/lib/cards.ts) の `CassetteBundle`。分離は `freshSessionOf` でリセットするという**規約**であって型ではない | 無料版が書けるフィールドの境界を明示的に定義（§5.2 #6 と同じ作業） |
| ④ | **未知フィールドの扱い** | **トップレベルは破棄。** [io.ts:22](../src/lib/io.ts) の `parseBundle` がホワイトリストで再構築している。将来トップレベルに新しいコレクションを足すと、旧版で読み書きした時点で**静かに消える**。中身（characters 等の各要素）は素通しなので被害は限定的 | 未知キーを保存する形に変更 |

#### 公開前に必ず入れるもの

- **`schemaVersion`**（アプリ状態。**唯一あとから足せない要素**）
- **安定 ID 体系**（既存の `uid()` ベースで問題ないか確認）
- **未知フィールドを無視して読み進むパーサ**（厳格にしすぎない）
- **カセットの `minRuntimeVersion`** — 新しいカセットを古いランタイムで開いたとき、黙って半分だけ動いて破綻するのが最悪。**明示的に「本体を更新してください」と拒否する**
- **カセット定義とセーブデータを別々にバージョニング**（片方の変更がもう片方を壊さないように。セーブは「途中まで遊んだ人の思い出」なので定義以上に壊すと恨まれる）

#### 互換の2方向

| 方向 | 難度 | 対策 |
|---|---|---|
| **古いカセット → 新しいランタイム** | 易 | 読み込み時に v3→v5 と変換関数を連鎖させる |
| **新しいカセット → 古いランタイム** | **難** | ①未知フィールドは無視して読み進む ②`minRuntimeVersion` で明示的に拒否 |

### 5.7 初回チュートリアル（API 案内）

**ファネルの一番広いところ（無料版）に、一番高い障害物（API キー設定）がある。**
無料版を配ってもキー設定で大半が落ちたら意味がない。**ここは本体の機能より売上に効く。**

**外部ドキュメントではなく、アプリ内の初回ウィザードを主にする。** ドキュメントは読まれない。

#### 3ステップに固定する（分岐を作らない）

1. プロバイダを選ぶ
2. キーを取る（外部リンク）
3. 貼って**接続テスト**

**接続テストのボタンが最重要。** 極小のリクエストを投げて成否を即出す。
BYOK の支援コストは、ほぼ全部「動かないが理由がわからない」から来る。ここで潰す。

#### プロバイダ一覧（正直なラベルで）

| ラベル | 中身 |
|---|---|
| **無料で始める** | Gemini 無料枠 ← **初期値** |
| 品質重視 | Claude / GPT |
| 多モデル・従量 | OpenRouter |
| 表現の制限が緩いモデル | OpenRouter 経由の特定モデル |

最後の行があることで、R18 利用者が自力で正しい場所に着地できる。
**訴求はしないが塞がない**（§1.6）の実装がこれ。

#### エラーを日本語の原因に翻訳する

生の API エラーを出さない。最低限この4分類：

| 原因 | 出す導線 |
|---|---|
| キーが不正 | 貼り直し |
| 残高・レート上限 | 課金／待機の説明 |
| モデル名が不正 | 選び直し |
| **コンテンツフィルタによる拒否** | **モデル選択画面へ誘導** |

**4つ目が専用メッセージになっていないと、R18 利用者が「壊れている」と誤解して返金に行く。**

#### 制作・設置

- **手順のスクショは最小限に。** プロバイダの UI は頻繁に変わりスクショは腐る。直リンクと、変わらない要点（無料枠の有無・必要な同意）だけをテキストで持つ
- **2分程度の無音キャプチャ動画**を1本。この層には文章より圧倒的に効く
- **設置は二重化**：アプリ内にオフライン HTML を同梱（ネットなしでも読める）＋**購入前に読める公開版**を Web に置く。公開版は返金抑止と「APIキー 取り方」系の検索流入を兼ねる＝**案内そのものが集客物になる**
- **プレイ1時間あたりの目安コスト**を必ず載せる。BYOK で最も大きい購入前の不安
- **免責を1段落**（§4.3）

### 5.8 製品方向性に伴う UI 変更（§0 の実装）
