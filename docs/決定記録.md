# 決定記録（再提案しないことの一覧）

**用途**: 「一度決めた・却下したこと」を1行ずつ置く。新しい案を出す前にここを見る。
理由の詳細は出典の文書（多くは `docs/archive/`）にあるが、**この表を読めば足りるように書く**。

- 2026-09-13 に `AGENTS.md` の「決着済み」「ADR」節と各設計書の却下案をここへ集約した。
- 削除した旧文書（`docs/archive/` の21件）は git 履歴にある: `git show 6faf660:docs/archive/<ファイル名>`

## 1. 製品の位置づけ

| 決定 | 理由 | 出典 |
|---|---|---|
| **「ノベルゲーム」ではなく「挿絵入りの本」** | AI 出力は事前に予測できず素材を用意できない。絵と文字が同じ画素を奪い合う VN 構成は両損 | archive/公開計画 §0 |
| **立ち絵・全面背景・表情差分・ステージ表示は復活させない**（2026-08-01 撤去） | 上と同じ。場所の絵が欲しければ挿絵へ吸収 | archive/設計_環境音ピン_実験 |
| **読者モデル**: 物語モードの入力はすべて「書き手への指示」。ユーザーは世界の住人を演じない | 「右腕を上げる」と入力しても AI の解釈が一致しない＝入力の意味論の不一致はプロンプトでは消えない | 設計_物語の簡素化 §3 |
| **`roleplay` モードは残す**（単体キャラとの会話）。ただしモードで分けるのは入力の意味論と操作系だけ、機構は共通 | 分けると二重実装になり削った複雑さが戻る | 同 §3.3 |
| **作者の仕込み（条件・数・到達目標・配役・特別イベント・固定タイムライン）は持たない** | 作り込むほど AI を使う意義から外れ、生成の流れも阻害する。作者自身が「面倒すぎる」と判断 | 同 §0・§1 |
| **ペルソナ型は持たない**。中心人物は `focusCharacterId` が指すただの参加キャラ | 全登場人物を等しく `Character` にした方が素材の再利用・カード化が単純 | 同 F3 |
| **中心人物 `null` は許さない** | 関係性が N×(N−1) に膨らむ。中心必須なら N−1 本 | 同 §2.5 |

## 2. 物語の機構

| 決定 | 理由 | 出典 |
|---|---|---|
| **状態はすべて prose**（関係性 `stance`＋次元ごとの記述・気分・時間・場所・予定） | 数値は LLM が更新を苦手とし機微を非可逆圧縮する。数の状態は F1 で全廃 | 旧 ADR-1 → 設計_物語の簡素化 §1.2 |
| **数の状態を prose の band（5段階の言葉）で残さない** | `Relation` が band を捨てて成立している。二の轍 | 同 §8 |
| **恒久フラグ（自由文字列）は持たない** | 取り消し手段が無く永久にドリフトする | FB9-C |
| **選択肢は加点・効果を持たない**。クリックはそのまま `send` | 事前にポイントが見えると面白味が半減、独自行動と同じ土俵にならない | FB7-C |
| **選択肢はオンデマンド1ボタン**（`always`/`auto` は廃止） | `always` は大半が捨てられる無駄、`auto` は判定呼び出しが要る上に外れる | 設計_物語の簡素化 §3.4 |
| **予定（`pending`）を本編プロンプトへ渡さない** | 実測 28/30 で無関係な先の予定を列挙した | 計測_時間と予定 §4.1 |
| **予定の件数上限は設けない** | 件数は精度に効かなかった | 同 §4.2 |
| **予定の消化は id でなく `what` の引用で受け、候補がちょうど1件のときだけ消す** | id は実測で壊れた。誤爆＝予定が消えて戻らない | 同 §4.3 |
| **相対表現（「来週水曜」）を予定に書かせない** | 基準日が無く 30回中2回しか発火せず両方誤り | 同 §4.4 |
| **`now` は自由文字列でコードは解釈しない** | 暦が違う世界がありうる。コードで時計を回す流派（AI Dungeon 方式）は作者コスト最大 | 設計_物語の簡素化 §2.1 |
| **時間と予定は第3のレビュー呼び出し（`t`）に分ける** | A に載せると次シーン提案が予定に引きずられ、B は負荷が偏る | 同 §2.4.2 |
| **`happened`（出来事の記録）は入れない** | 溜まる配列を本編へ入れる失敗は実証済み。漂流が起きることを測ってから | 同 §2.3.1 |
| **エンディングは世界側に定義を持たない**。AI がいつでも提案し、ユーザーが選ぶ。到達判定はしない | 条件・auto/hidden/fallback・到達記録は「作者の仕込み」そのもの | 同 §2.7 |
| **幕間は非正典**（状態へ書き戻さない。ユーザーが選んだ解釈だけ関係性へ反映） | 本編と矛盾する | 同 §2.9.4 |
| **幕間の単位はシーン丸ごと1本**。進行中シーンでは作らせない | 途中に挿すと対象範囲が生成のたびにずれる | 同 §2.9.2.1 |
| **幕間で「観察の追加」は禁じない**。禁じるのは世界設定・過去の捏造だけ | 幕間の面白さはそこにある。読み専用なので本編は汚れない | 同 §2.9.3 |
| **幕間の品質を判定 LLM で自動確認しない** | 測れなかった。人手で読む | 計測_別視点の幕間 §4 |
| **セッション内埋め込みキャラを作らない**。発見キャラはライブラリの通常キャラとして保存 | 「素材でないキャラ」が合成ビュー・カード化・全経路に波及する | FB7-E |
| **`SessionOverlay` に `characters` を足さない** | 上と同じ。足すなら `SAVE_DATA_VERSION` を上げて移行を書く | archive/設計_公開前実装 R7 |
| **完結後に出す操作は「分岐」と挿絵だけ。最後の生成文からは分岐させない** | 同じ線の続きになり、廃止した `branchToContinue` の復活と等価 | FB9-A |
| **ツリー行クリックは移動、分岐を作る操作は本文の操作行に集約** | ツリーは読む・移動する装置 | FB7-B |
| **分岐の自動削除は保護判定を通し、`recordCheckpoint` 内では剪定しない**（fail-open） | 取り漏らしをバグとして発見できるように | FB6-C |
| **`WORLD_PRESETS`（恋愛/RPG/経営）は持たない** | `newWorld()` は中立な既定（関係次元「信頼」1つ）。→ 既定コンテンツは 2026-09-13 の計画で別途入れる | G4-b |
| **キャラ別の専用モデル（`Character.model`）は持たない** | 一度も使われず、解決経路と除去処理を余分に持つだけだった | 2026-08-16 |
| **セッションカード（`aist_session`）は読み書きとも無い** | 共有はカセット・バックアップはデータ書き出し | FB3-D |

## 3. プロンプト

| 決定 | 理由 | 出典 |
|---|---|---|
| **`buildSystemPrompt` に毎ターン変わる値を足さない**（system／深さ3／深さ0 の3層） | キャッシュ粒度はメッセージ単位。system が1文字変わると全体が無効（実測ヒット率2%） | archive/詳細設計_プロンプト構造 §5 |
| **原文窓はシーン途中で動かさず、古い方へ戻さない** | 途中で畳むのが最悪の切り方。再拡張すると振動する | 同 §7.2 |
| **選択肢の文脈は `buildMessages` を使わず専用に圧縮する**（接頭辞共有＝PC2 は却下） | 接頭辞共有は期待値で負けた | 同 |
| **`cache_control` は Anthropic 系にだけ付ける**（2箇所）。Claude 系は OpenRouter 経由を推奨 | 効果は実測 2.85 倍。直叩き経路は `usage` で実効を確認できない | 同 §7.1 |
| **迎合対策の「もっと強い文面」を足さない** | 740会話の実測でどの案も対照を上回らず、強くするほど悪化した。効いているのはキャラ定義と関係性 prose | archive/計測_迎合対策文面 |
| **`startPreset.authorNote` の既定文は入れない** | 汎用の1文は効かず、非キャッシュのトークンだけ増える。入力欄の案内で「芯は人格欄へ」と伝える | 同 §4.4 |
| **プロンプトの言語は日本語で統一** | — | 設計_プロンプト構造とキャッシュ §6.3 |
| **書き手への指示（`kind:'directive'`）は本編履歴と画面だけに出し、裏方 LLM の文脈・書き出しからは落とす** | 指示は物語ではない。迷ったら落とす側 | 設計_入力の二分化 |
| **`buildMessages` の履歴からマークアップを剥がさない** | few-shot 効果で形式遵守が強化される | 構造化出力 |
| **システム側の登場文法の一文（CS3）は入れない** | 実測で効果なし | archive/設計_登場制御の見直し §5.1 |

## 4. データ・ストレージ

| 決定 | 理由 | 出典 |
|---|---|---|
| **クリーンブレイク方針は終了。`version`/`migrate` で移行する**（3系統: 入れ物／セーブ／カセット） | 公開後は前提が崩れる | R1 |
| **読めないデータは黙って落とさず、書き込みを封印して案内画面へ** | 上書きで失う方が重い | R1 |
| **`branchTrees`・`sessionImageLogs` を `Session` の中に入れない** | スナップショット深コピーで再帰肥大／復元で巻き戻る | C1・FB6-A |
| **画像の即時 `deleteImage` は書かない。参照除去＋GC のみ** | チェックポイントが imageId を参照しうる | P4 |
| **API キーは OS 資格情報ストア（Tauri）。Stronghold は使わない** | Stronghold はパスワードを要求する | R3 |
| **`isTauri()` 分岐は `platform.ts`（とストレージ実装）の外に書かない** | 環境差をコンポーネント・store へ持ち込まない | T2 |

## 7. 2026-09-13 レビューによる方針転換

第三者視点のプロダクトレビュー（本セッション）を受けた方針。**各項目の実施は [`計画_レビュー対応.md`](./計画_レビュー対応.md) の承認欄で確定する。**

| 決定（提案） | 理由 |
|---|---|
| **機能凍結。追加より削除と公開を優先する** | 10.5週・290コミットで外部ユーザー0人。作者の面白さは指標として機能していない（テーゼ転換3回・書いたコードの37%を削除） |
| **無料で公開する。制作版 ¥2,980 の二層モデルは取り下げ**（有料化は数値条件を満たしてから再検討） | 課金点「読み込み能力」は計画自身がカセット流通経路を閉じたことで空洞化。悲観ケース 14.9万円は事業として成立しない |
| **R7（ローダー除去・カセット焼き込み・ビルド分離）と署名は廃止**（凍結ではなく） | 顧客がいない段階の DRM。工数と複雑性を守るものが無い |
| **ソースを公開する**（Issue/PR は受け付けない旨を明記） | API キーを扱う未署名 exe の信用の壁を下げる。BYOK 文化圏は OSS が前提 |
| **Web 版を「開発用」から需要検証の主経路へ戻す** | SmartScreen 越しの exe 配布がファネル最大の障害。OpenRouter/Gemini はブラウザから直接叩ける |
| **最初の5分を作る**: 既定コンテンツ同梱・一行前提からの AI 起案 | 起動直後にキャラも世界も無く、AI エンジンなのに 0→1 が全て手入力 |
| **中核主張「長編でも破綻しない」を対照実験で確かめる** | 計測文化がありながら製品の中核主張だけ未計測 |
| **環境音の既定同梱・Civitai/ModelsLab・DLsite・静的カタログ・有料カセットは削る**（環境音は機能ごと撤去・Civitai/ModelsLab は削除。P1 で 2026-09-13 に実施） | 任意機能に厚く最初の5分に薄い逆三角形を正す |
| **単一 JSON 永続化と `useStore()` 全購読は作り直す** | set() ごとの全量 stringify（20セッションで 11ms/チャンク）と全再描画が「長く遊ぶ」製品と衝突する |
| **ネイティブ／Capacitor は作らない** | レスポンシブ Web＋PWA 以外は今の規模で検討する意味が無い |
