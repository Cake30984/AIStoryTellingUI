# 設計: 分岐ツリーの生成順表示と導入ロール

- 日付: 2026-07-12
- 対象: 分岐ツリーの表示順／狭幅表示／導入文の話者プレースホルダー
- 位置づけ: `設計_フィードバック反映3.md` の FB3-B2 と `設計_構造化出力.md`、`設計_開始テンプレートとゲームカセット.md` を補足する追加設計

## 実装状況（2026-07-12）

- BT1（生成順での分岐ツリー表示）と BT2（狭幅時の「いまここ」表示）は実装済み。
- **OR1〜OR3（番号スロット方式の導入ロール）は未実装のまま廃止**（2026-07-12 決定）。世界観が名前つきロールを定義する「配役システム」へ置き換えた → `設計_配役システム.md`。以下の OR 節は却下案の経緯として保存する。

## 1. 背景と要望

今回の要望は次の3点である。

1. 分岐ツリーは現在の分岐を主軸として強調しつつ、ノードの縦方向の並びは、分岐の所属にかかわらず実際に生成された順番を守る。
2. 分岐ドックの横幅が狭い場合も「▶ いまここ」を折り返さず、固定高の行からはみ出させない。
3. 導入文に `@ペルソナ`、`@キャラクター1`、`@キャラクター2` ... と書けるようにし、物語開始時にセッションで選ばれた実名へ置換する。これにより、カセットや世界観の導入テンプレート作成時に具体的な話者名が未確定でも、構造化出力の話者アイコンを正しく表示できるようにする。

## 2. 現状分析

### 2.1 分岐ツリーの順番

`BranchTreeModal.tsx` の `buildGraph` は、現在パス上の子を最初にした深さ優先の pre-order で行を作っている。そのため現在パスはレーン0の直線になりやすい一方、先に作られた別分岐のノードが、後から作られた現在分岐の子孫をすべて描いた後へ移動して見える。

`BranchTree.nodes` は `recordCheckpoint` で新規ノードを末尾へ追加しており、削除・剪定も残存ノードの相対順を維持する。したがって、この配列順がアプリ内で最も正確な「生成順」である。`createdAt` は同一ミリ秒になる可能性があるため、表示順の主キーにはしない。

### 2.2 「いまここ」の折り返し

分岐行は高さ36px固定だが、`.badge.accent` には改行禁止と縮小禁止が無い。ラベル、しおり、容量、戻る、メニューが同一の flex 行に並ぶため、狭幅では「いまここ」が内部改行し、固定行高から下へはみ出す。

### 2.3 導入文と話者アイコン

導入文 `session.story.opening` は `startStory` で AI を通さず、そのまま最初の assistant メッセージへ格納される。構造化レンダラは行頭の `@名前` を参加キャラとペルソナの実名に照合してアイコンを決めるため、導入テンプレート作成時に実名が未確定だと解決できない。

導入文は World の開始テンプレート、Session、Cassette.session の間でコピー・保持される。置換済み本文で元テンプレートを上書きすると、カセットの再利用やペルソナ変更に追従できなくなる。

## 3. 設計方針

- **並びと強調を分離する**。縦の並びは生成順に固定し、現在パスの強調は色と線で表現する。現在パスを先頭へ移動してはならない。
- **生成順の正本は `tree.nodes` の配列順**とする。表示用の sequence フィールドは追加しない。
- **導入文はテンプレートのまま永続化**し、物語開始時に作る Message の `content` だけを実名へ解決する。
- プレースホルダー解決は構造化パーサへ混ぜず、導入専用の純粋関数へ分離する。通常の AI 応答やユーザー入力に意図しない置換を行わない。
- 既存セッションは追加フィールド未設定でも現状どおり動く optional 追加とし、persist キーは据え置く。

## 4. BT1: 分岐ノードを生成順に表示する

### 4.1 表示順の不変条件

ツリータブの行順は次を満たす。

1. `tree.nodes[0]` から末尾までの配列順で並べる。
2. 現在パス上かどうか、親子の深さ、しおりの有無によって行順を変えない。
3. 削除後も残ったノードの相対順を変えない。
4. `createdAt` は表示用情報として残すが、並べ替えには使わない。
5. ★しおりタブは用途が異なるため、従来どおり新しい順でよい。

例:

```text
生成順: A(root) → B → C → D(Bから分岐) → E(Dの続き)
現在地: E

表示順も A → B → C → D → E
C を非現在分岐だからといって E の後へ移動しない。
```

### 4.2 グラフレイアウト

既存の再帰的 pre-order `visit` は廃止し、生成順の行に対してレーンと辺を割り当てる。

1. `tree.nodes` を順に走査し、`node.id → rowIndex` と `node.id → lane` を作る。
2. root はレーン0。
3. ある親の**最初に生成された子**は親のレーンを継承する。
4. 同じ親の2番目以降の子は、生成された順に新しいレーンを割り当てる。
5. 各 `parent → child` 辺について、親行の下半分で必要なら子レーンへ分岐カーブを描き、途中行では子レーンの縦線を通し、子行の上半分でドットへ接続する。
6. 木構造なので合流は描かない。レーンの再利用は初回実装では行わず、既存仕様と同程度の単純さを優先する。

これにより、親子が隣接しない場合でも、途中の行を通る縦線で関係を追える。`buildGraph` の返り値は引き続き行ごとの `topLanes`、`bottomLanes`、`branches` としてもよいが、計算元は DFS の active 状態ではなく、全辺の行区間から組み立てる。

現在パスと非現在パスで同じレーンの色が途中から変わる場合があるため、各線要素はレーン番号だけでなく、元の `parentId`／`childId` または `onCurrentPath` を保持する。描画時に行とレーンだけから色を推測しない。

### 4.3 現在パスの色

レーン番号と現在パスの色を切り離す。

- `currentPathIds` は削除保護・剪定に加えて表示色にも使う。
- 現在パス上のノードのドット、および現在パス上の親子を結ぶ辺は `--accent`（紫）で描く。
- 現在パスが途中で別レーンへ分岐していても、そのカーブ以降を紫で追えるようにする。
- 現在パス外の辺・ドットは従来の `--graph-lane-*` を使う。
- 現在ノードの「▶ いまここ」と行背景は従来どおり残す。

つまり「主軸」はレーン0や表示順の並べ替えではなく、**現在地まで連続する紫の経路**として表現する。

### 4.4 防御動作

通常データでは親が必ず子より先に `tree.nodes` に存在する。破損データで親が見つからない、または親が子より後ろにある場合は、そのノードを独立レーンへ置き、描けない辺だけを省略する。表示全体を例外で落とさない。

### 4.5 単体確認

- 同一 `createdAt` の兄弟を含めても配列順を維持する。
- 過去分岐 C の後に、B から新分岐 D、E を作っても `A,B,C,D,E` になる。
- 現在地を C と E の間で切り替えても行順は変わらず、紫の経路だけが変わる。
- subtree 削除・現在パス剪定後も残存行の相対順が変わらない。
- 親子が複数行離れていても線が子まで途切れない。

## 5. BT2: 狭幅でも「いまここ」を1行に収める

### 5.1 CSSとDOM

現在地バッジに汎用 `.badge.accent` だけでなく、用途クラス `.bg-current-badge` を付ける。ツリー行としおり行の両方で同じクラスを使う。

```css
.bg-current-badge {
  flex: 0 0 auto;
  white-space: nowrap;
  line-height: 1;
}
```

さらに次を保証する。

- `.bg-body` は単一行 flex のまま、`min-width: 0` と縦方向中央揃えを維持する。
- `.bg-label` が最初に縮み、`text-overflow: ellipsis` になる。
- しおりバッジも `white-space: nowrap` とし、狭いときは最大幅＋ellipsisで1行に留める。
- 「いまここ」と ⋯ メニューは縮めない。
- 容量表示は低優先情報とし、ドック最小幅付近では CSS container query または既存レイアウトの幅条件で非表示にしてよい。
- 固定行高36pxは変えない。横方向の情報量を調整し、縦へ逃がさない。

### 5.2 受け入れ条件

- `ui.dockWidth` の最小値300pxで「▶ いまここ」が折り返さない。
- 現在行の高さは他の行と同じ36pxで、次行へ文字が重ならない。
- 長いノード名・長いしおり名・多レーンの組み合わせでも、ラベルが省略されて現在地表示とメニューは操作できる。
- 300px／360px／560pxで目視確認する。

## 6. OR1: 導入ロールのデータモデル

### 6.1 プレースホルダー

導入文で次の予約ロールを使えるようにする。

| 記法 | 解決先 |
|---|---|
| `@ペルソナ` | `session.personaId` が指す Persona の名前 |
| `@キャラクター1` | 導入ロール設定のスロット1に割り当てた Character の名前 |
| `@キャラクター2` | 同スロット2 |
| `@キャラクターN` | 同スロットN（Nは1〜99） |

正規記法は半角 `@` とする。入力ミスを救済するため、解決時は全角 `＠` も同じ予約ロールとして受理し、出力は半角 `@実名` に正規化する。

```text
テンプレート:
@地の文「扉が開いた。」
@キャラクター1(joy)「待っていたよ」
@ペルソナ(surprise)「私を知っているの？」

解決後:
@地の文「扉が開いた。」
@美咲(joy)「待っていたよ」
@高槻悠(surprise)「私を知っているの？」
```

予約ロール以外の `@美咲` や本文中の通常文字列は変更しない。感情指定とセリフ本文はそのまま残す。

### 6.2 型

`types.ts` に次を追加する。

```ts
export interface OpeningCharacterSlot {
  /** @キャラクターN の N。1〜99 */
  slot: number
  /** session.characterIds に含まれる Character.id */
  characterId: string
}

export interface StorySetup {
  // 既存フィールド...
  /** 導入文の @キャラクターN と参加キャラの対応。未設定は空配列扱い */
  openingCharacterSlots?: OpeningCharacterSlot[]
}
```

`@ペルソナ` は既存の `session.personaId` で一意に解決できるため、重複する binding は持たない。

同じ slot が重複した不正データは、配列の後の要素を優先する。範囲外 slot、空 id、`session.characterIds` に含まれない id は無効として扱う。

### 6.3 永続化とカード

- optional 追加なので persist キー `ai-storytelling-store-v3` は据え置く。
- `newSession` は `openingCharacterSlots: []` を設定する。
- `freshSessionOf` は `story` を保持する現在の挙動により割り当ても保持する。
- System の export/import は Session を丸ごと扱うため基本的に自動追従する。
- カセット PNG は `bundle.session.story` に同梱される。`normalizeSessionBundle` で slot が整数1〜99か、characterId が文字列かを正規化する。
- カセット取込は Character.id を変更せずマージする現行方式なので、画像 id のような remap は不要。
- World.startPreset は具体的なキャラを参照しないため、導入本文の予約ロールだけを保持し、割り当ては持たない。世界観から導入をコピーした後、Session/Cassette 側で割り当てる。

## 7. OR2: 検出・検証・解決ロジック

### 7.1 専用モジュール

`src/lib/openingRoles.ts` を新設し、React・store に依存しない純粋関数を置く。

```ts
findOpeningRoles(text): {
  usesPersona: boolean
  characterSlots: number[]
}

validateOpeningRoles(text, session, characters, personas): OpeningRoleIssue[]

resolveOpeningRoles(text, session, characters, personas): {
  content: string
  issues: OpeningRoleIssue[]
}
```

`characterSlots` は本文中の登場順ではなく数値昇順で返し、重複を除く。検出・置換は単一の正規表現走査で行い、置換後の名前を再びプレースホルダーとして処理しない。

### 7.2 検証エラー

次を未解決として列挙する。

- `@ペルソナ` を使っているが `personaId` が無い、または対象 Persona が存在しない。
- `@キャラクターN` を使っているが slot N の割り当てが無い。
- 割り当て先 Character が存在しない。
- 割り当て先が `session.characterIds` に含まれない。
- 同じ Character を複数 slot に割り当てた場合は許可するが、UIに注意を表示する。同一人物が複数の劇中ポジションを兼ねるケースを禁止しない。

### 7.3 開始時の処理

`startStory` の導入あり経路を次の順にする。

1. 保存済みの `s.story.opening` を取得する。
2. `resolveOpeningRoles` で実名入り本文を作る。
3. 未解決 issue が1件でもあれば開始を中止し、`store.error` に「導入ロールを設定してください: ペルソナ、キャラクター2」のように不足を表示する。Message とチェックポイントは作らない。
4. 解決できた `content` を assistant Message に保存する。
5. 選択肢生成、`plainTextOf`、構造化レンダラ、チェックポイントは解決済み Message を使う。
6. `session.story.opening` 自体は書き換えない。

この時点で `@ペルソナ` は `@実名` になっているため、既存の `StructuredMessage` が participants＋persona から `characterId` を解決し、ペルソナの `EntityAvatar` を表示できる。構造化パーサの仕様変更は不要である。

`structuredOutput` が OFF でも置換は行う。予約ロールが文章中の名前として使われている場合にも不自然なプレースホルダーを残さないためである。

## 8. OR3: 設定UI

### 8.1 共通部品

SessionEditor と CassetteEditor で挙動を重複させないため、`OpeningRoleFields` を共通部品として切り出す。

入力:

- `opening`
- `characterIds`
- `personaId`
- `openingCharacterSlots`
- Character／Persona 一覧
- 更新 callback

表示:

1. 導入 textarea の近くに「導入ロール」説明を置く。
2. `@ペルソナ` が本文にあれば「ペルソナ → 選択中の名前／未選択」を読み取り専用で表示し、ペルソナ設定への誘導を出す。
3. 本文で検出した `@キャラクターN` ごとに select を表示し、候補は `session.characterIds` の参加キャラだけにする。
4. 未解決項目は警告色と「未設定」を表示する。
5. 「使える記法: `@ペルソナ`、`@キャラクター1` ...」と、感情を含む短い例を表示する。
6. 解決済みプレビューを折りたたみ表示できるようにする。未解決箇所は元の予約ロールを残し、警告を併記する。

本文から消えた slot の保存値は即時削除せず保持してよい。書き直して同じ slot を戻したときに再設定を省ける。ただし保存・書き出し時の正規化では1〜99と有効な Character.idだけを残す。

### 8.2 SessionEditor

- 「基本」タブにある参加キャラ／ペルソナ／導入欄の設定を参照し、割り当てUIは導入欄の直下へ置く。
- 参加キャラを外したとき、そのキャラへの slot 割り当ては解除し、導入欄に未解決警告を出す。
- セッション設定の保存自体は許可する。未完成の下書きを保持できるようにするためである。
- 「物語をはじめる」は未解決がある場合に開始せず、設定画面で直すべき項目を明示する。

### 8.3 CassetteEditor

- 「開始・進行」セクションの導入欄直下に同じ `OpeningRoleFields` を置く。
- 候補は「登場キャラ」セクションで選ばれた Character のみ。
- `@ペルソナ` は「ペルソナ」セクションの選択を参照する。
- 棚への下書き保存は未解決でも許可し、カセットカードに警告表示を付ける案は本要望の範囲外とする。
- PNG 書き出し時は未解決ロールがあれば確認ではなくエラーにする。配布後に開始不能なカセットを作らないためである。
- `▶ 遊ぶ` ではセッション複製前に検証し、未解決なら CassetteEditor を開く導線を提示する。

## 9. データ整合性

- Character 削除時は Sessions と Cassettes の `characterIds` から外す既存処理に加え、対応する `openingCharacterSlots` も除去する。
- Persona 削除時は既存どおり `personaId=null` となり、`@ペルソナ` を含む導入は未解決状態になる。
- SessionEditor/CassetteEditor で参加キャラを外した時点でも対応 slot を除去する。
- 世界観テンプレートの「空欄のみコピー／全上書き」は `opening` を更新しても既存の割り当てを勝手に上書きしない。新しい本文の検出結果に応じて警告を更新する。
- セッションからカセット下書きを作る `freshSessionOf` は割り当てを維持する。
- 予約ロール解決後の Message は通常の実名本文なので、後から Session の Persona／Character 割り当てを変えても過去メッセージは変えない。再解釈による履歴改変を避ける。

## 10. 実装フェーズ

### Phase 1: 分岐ツリー

- `buildGraph` を配列順レイアウトへ変更。
- 現在パスの辺・ドットを accent 色にする。
- 「いまここ」専用クラスと狭幅時の情報優先度をCSSへ追加。
- グラフ計算を可能なら純粋関数として分離し、順序と線区間を単体確認する。

### Phase 2: 導入ロール基盤

- `OpeningCharacterSlot` と `StorySetup.openingCharacterSlots` を追加。
- `openingRoles.ts` に検出・検証・解決を実装。
- `startStory` の導入経路へ解決と開始前検証を追加。
- Character 削除、factory、カード正規化を追従。

### Phase 3: 設定UIとカセット

- 共通 `OpeningRoleFields` を作る。
- SessionEditor／CassetteEditor へ組み込む。
- カセット書き出し／再生前検証を追加。
- 世界観開始テンプレートから導入をコピーする一巡を確認する。

各Phaseで `npx tsc --noEmit` → `npm run build` を実行する。Tauri固有層は変更しないため、通常は `npm run tauri:dev` の追加確認対象外とする。

## 11. 総合受け入れテスト

1. 直列 A→B→C を作り、Bへ戻って D→E を作る。表示は A,B,C,D,E のまま、現在パス A-B-D-E だけが紫になる。
2. Cへ戻っても行順は変わらず、紫の経路だけが A-B-C へ切り替わる。
3. ドック幅300pxで長いラベル・しおり・「いまここ」がある行を表示し、行高36pxとクリック操作を保つ。
4. 導入に `@ペルソナ(joy)` を書き、Personaを選んで開始する。最初の本文に実名とPersonaアイコンが出る。
5. `@キャラクター1` と `@キャラクター2` を別キャラへ割り当て、感情指定を保ったまま両方のアイコンが出る。
6. 未割り当ての `@キャラクター2` がある場合、開始前に不足名が表示され、Message／チェックポイントが増えない。
7. 導入テンプレート `story.opening` は開始後も予約ロールのまま保持され、Messageだけが実名になっている。
8. World.startPreset の導入をSessionへ読み込み、ロール設定→開始まで一巡する。
9. CassetteEditorで設定→棚へ保存→PNG書き出し→取込→遊ぶ、の後も割り当てが保持される。
10. 参加キャラまたはPersonaを削除すると未解決が検出され、誤って別キャラへ自動割り当てされない。

## 12. 対象外

- 通常のAI生成本文で `@キャラクター1` を動的に解決すること。
- 導入開始後にPersonaを変えた際、過去Messageの名前やアイコンを遡って変更すること。
- カセットを遊ぶ人が、カセット作成者の指定とは別のPersonaを起動時に選ぶ新フロー。
- `@敵役`、`@案内役` のような任意名称ロール。必要性が確認された場合は、番号スロットを一般化して別設計とする。
