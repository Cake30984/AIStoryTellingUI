# 設計: セーブ/ロードと分岐周回 — チェックポイント方式（C1〜C3）

2026-07-05 の設計相談で合意した「git のツリーのように物語の任意時点へ戻り、以前の分岐を残したまま新しい分岐を始められる」機能の実装計画。
**実装は C1 → C2 → C3 の順**。各フェーズごとに tsc → build → 検証 → CLAUDE.md 更新 → commit → push（既存の進め方と同じ）。
前提: Tauri 化 T0〜T3 実装済み（`platform.ts` のアダプタ層・ファイルストレージ）。T4（配布）は本機能より後。

## 背景と目的

ギャルゲ体験の核である「セーブしてから大胆な選択をする」「別ルートをやり直す」を実現する。既存の `regenerateFrom` は破壊的（それ以降を捨てる）で、状態スナップショットも分岐の並行保持もない。LLM ベースでは同じ選択でも毎回違う物語になるため、分岐の保存は既存ゲーム以上に価値が高い。

重要な設計認識: **巻き戻すのはメッセージ列ではなく Session 全体**。`state`（関係性・スタット・実績）・`overlay`（発見ロア・成長）・`timeline`・`usedEventIds`・`scenes`・`spriteEmotions` が本文と一緒に巻き戻らないと、「イベント消化済みで二度と発火しない」「未来の関係値が残る」という壊れ方をする。さらに選択肢クリックの加点（`applyChoiceEffects`）と実績解除はシーン中に起きるため、小ポイントも状態フリーではない。→ セッション全体の深コピーを取るチェックポイント方式で一括解決する。

## 決定事項（2026-07-05 合意）

| 論点 | 決定 | 理由 |
|---|---|---|
| データ表現 | **チェックポイント方式**: 各物語操作の完了時にセッション全体の深コピーを gzip 圧縮して大容量ストア（CheckpointStore）へ保存。木のメタデータ（親リンク・ラベル）だけを zustand persist に持つ | メッセージツリー内蔵方式は `s.messages` を読む全コードの大手術になる。チェックポイントなら既存コードにほぼ触れない。scenes・state など「メッセージ以外も fork する」問題も丸ごと解決 |
| fork の契機 | **全操作が自動 fork**（明示 fork 操作なし）。復元後に操作すればその地点の子が積まれ、既存の子と自然に兄弟分岐になる | fork という概念をユーザーに意識させない。「どの時点にも戻れて、戻っても何も失われない」が体験のすべて |
| 大ポイント | **レビュー確定（`confirmSceneReview`）の単位**（kind: `scene`）。レビューやり直しは大ポイントの**親**（＝レビュー直前の小ポイント）へ戻る。レビュー直前ポイントは表示を変える（導出表示） | シーン区切りが物語の章に相当する。ディレクター抽選を引き直したい需要にも「レビュー前に戻る」で応える |
| 小ポイント | 物語操作1回（送信〜応答完了）ごと（kind: `action`）。ラベルは**作成時に確定**して保存: 直近ユーザー発言の冒頭（選択肢クリックは send(choiceText) なので自然に選択肢テキストになる）→ 無ければ assistant 本文冒頭。マーカー疑似メッセージは「⏩ 続き」「🎬 シーン導入」等に置換 | 後からの導出はメッセージ編集・削除で崩れる。選択肢テキストがそのままラベルになるのがギャルゲ的に最も分かりやすい |
| 記録方式 | **全自動記録＋しおり（★・任意名・サムネイル）のハイブリッド** | 「あの時点に戻りたい」は事後に発生するので全記録が必須。意図した地点はしおりで目立たせる |
| 画像の削除 | **即時 `deleteImage` を全廃し GC 一本化**。チェックポイント内の imageId も使用中扱い | 分岐 A で挿絵を消すと分岐 B のスナップショットが壊れる。削除は「参照除去」だけにし、実体の回収は `gcUnusedImages` に集約 |
| 素材昇格・素材編集 | **ツリー外の共有資産と割り切る**（昇格・素材編集は巻き戻らない・全分岐に波及する）。UI に注釈を明示 | 素材はセッション横断の再利用資産。チェックポイントに含めると「どのセッションのどの分岐の素材が正か」が破綻する |
| 復元と設定の関係 | スナップショットは Session 全体を保存するが、復元時に**プレイ用ノブだけ現在値を維持**（passthrough）: `title` / `model` / `reviewModel` / `choicesModel` / `temperature` / `maxTokens` / `spritesEnabled`。それ以外（characterIds・world・persona・authorNote・story・narrativeStyle・choiceMode・director 含む）はスナップショットから復元 | ゲームのロードで「使用モデルや音量設定」が巻き戻るのは期待に反する。一方 characterIds や narrativeStyle は本文と結合しており、現在値を残すと不整合になる。**passthrough リストは最小・明示**とし、迷ったらスナップショット側に倒す |
| エクスポートとの関係 | `exportBundle`（画像込み含む）・セッションカードに**ツリー・チェックポイントは含めない**（現在の物語のみ）。インポートされたセッションはツリー空から開始 | バンドル肥大を避ける。デスクトップ版のフルバックアップは `data/` フォルダコピー（checkpoints/ を含む）で既に完結している |
| persist スキーマ | トップレベルに `branchTrees` を**追加**（optional 追加のため persist キーは v3 のまま・クリーンブレイク不要） | 既存データはツリー空として扱えばよく、破壊的変更ではない |

### 既知の制約（報告時に説明すること）

- チェックポイントは「物語操作」単位。設定・状態の手動編集（SessionEditor / StatusPanel / DiscoveryPanel / SceneEditor）は単独では記録されず、次の物語操作のスナップショットに相乗りする。
- `spriteEmotions` は fire-and-forget の表情判定がチェックポイント後に届くことがあり、復元直後の表情が 1 応答ぶん古い場合がある（次の応答で再判定される・表示のみの影響）。
- Web 版のチェックポイントは IndexedDB に入るため、ブラウザのサイトデータ削除で消える（デスクトップ版が正式版という T 系の整理どおり）。

## データモデル

### 木のメタデータ（zustand persist・軽量）

```ts
/** 分岐ツリーの1ノード。チェックポイント実体は CheckpointStore に nodeId で保存 */
export interface BranchNode {
  id: string
  /** null = ルート（このセッションで最初に記録された時点） */
  parentId: string | null
  /** action = 小ポイント（物語操作1回） / scene = 大ポイント（レビュー確定） */
  kind: 'action' | 'scene'
  /** 作成時に確定するラベル（選択肢テキスト・入力冒頭・シーンタイトル等） */
  label: string
  /** シーン見出し用（大ポイントのみ: timeLabel） */
  timeLabel?: string
  createdAt: number
  /** スナップショットが参照する画像 id（GC 用。チェックポイントを展開せず集計するため保存時に抽出） */
  imageIds: string[]
  /** 圧縮後バイト数（剪定 UI のサイズ表示用） */
  bytes: number
  /** しおり（C3） */
  star?: { name: string; thumbImageId?: string }
}

export interface BranchTree {
  /** 現在地。次のチェックポイントはこのノードの子として積まれる */
  currentId: string | null
  nodes: BranchNode[]
}

// AppState に追加（partialize に含める・Session の中には入れない）
branchTrees: Record<string /* sessionId */, BranchTree>
```

**`branchTrees` を Session の外に置くのは必須**。Session 内に置くとスナップショット（Session の深コピー）が木自身を含んで再帰的に肥大する。

### チェックポイント実体（CheckpointStore・大容量）

- 内容: `{ v: 1, session: Session }` を `JSON.stringify` → gzip（`CompressionStream('gzip')`）した `Uint8Array`。
- Session は**全フィールド**を保存する（passthrough の適用は復元時に行う。保存時に削るとリスト変更時に旧チェックポイントが読めなくなる）。
- 深コピーは `structuredClone(session)`（Session は plain JSON なのでそのまま通る）。

```ts
/** platform.ts に追加する interface（stateStorage / BlobStore と同じ流儀で Web/Tauri 実装を切替） */
export interface CheckpointStore {
  put(sessionId: string, nodeId: string, data: Uint8Array): Promise<void>
  get(sessionId: string, nodeId: string): Promise<Uint8Array | undefined>
  delete(sessionId: string, nodeId: string): Promise<void>
  /** セッション削除時にまとめて破棄 */
  deleteSession(sessionId: string): Promise<void>
  /** 整合性チェック（木に無い孤児の掃除）用 */
  listNodeIds(sessionId: string): Promise<string[]>
}
```

- **Web 実装**: IndexedDB（新 DB `aist-checkpoints`・key は `${sessionId}/${nodeId}`）。
- **Tauri 実装**: `%APPDATA%/…/data/checkpoints/<sessionId>/<nodeId>.bin`（T3 で予約済みのディレクトリ。gzip 済みバイナリをそのまま書く）。
- gzip/gunzip ヘルパは `platform.ts` か新設 `lib/checkpoint.ts` に置く（`CompressionStream` は Chromium/WebView2 とも利用可。実装時に動作確認）。

### 容量の目安

500 メッセージ級の長大セッションで JSON ~500KB → gzip ~50〜100KB/個。小ポイント 500 個でも合計 25〜50MB 程度で、ファイル/IndexedDB とも実用域。dedupe（下記）と剪定で実際はさらに小さくなる。

## チェックポイントの契機

**実装は store.ts 内のヘルパ `recordCheckpoint(sessionId, kind, label)` に集約**し、以下から呼ぶ:

| 契機 | kind | 備考 |
|---|---|---|
| `runCompletion` 正常完了後（選択肢生成の await 後） | action | send / continueStory / regenerate / startStory / beginScene 導入 / continueLast / regenerateFrom がすべてここに合流するため**フックは1箇所**。中断（Abort）・エラー終了時は積まない |
| `editMessage` / `deleteMessage` 直後 | action | ラベルは「✏ 編集: 冒頭…」「🗑 削除」 |
| `confirmSceneReview` 直後 | scene | ラベルは新シーンの title・timeLabel。直後の導入生成完了でさらに action が積まれる |

- **選択肢クリック**は `applyChoiceEffects` → `send(choiceText)` の流れなので独立した契機にしない（直後の送信完了チェックポイントに加点込みで含まれ、ラベルも選択肢テキストになる）。
- **ルートの遅延生成（既存セッションの移行を兼ねる）**: 上記契機の**操作開始時**に対象セッションの木が空なら、まず操作前の現在状態をルートノード（label「開始時点」）として積んでから操作に入る。`regenerateFrom` や `deleteMessage` のような破壊的操作が機能導入後の最初の操作でも、直前の状態が必ず救われる。
- **dedupe**: 直前ノード（currentId）のスナップショットと JSON 文字列が完全一致するなら積まない（実質無変化の操作）。
- チェックポイント作成は fire-and-forget（メインスレッドをブロックしない）。`imageIds` は保存時に `sessionImageIds(session)`（下記 GC 節）で抽出してノードに記録する。

## 復元（ロード）と分岐の発生

```
restoreCheckpoint(sessionId, nodeId):
  1. ガード: isStreaming / isGeneratingChoices / isReviewing 中は不可（UI 側でも disable）
  2. CheckpointStore.get → gunzip → { session: snapshot }
  3. 復元値 = { ...snapshot, ...現在セッションの passthrough フィールド }
  4. セッションを全置換し、sceneReview（ランタイム）は破棄
  5. branchTrees[sessionId].currentId = nodeId
```

- 復元は**何も削除しない**。次の物語操作で `nodeId` の子が積まれ、既存の子がいれば自然に兄弟分岐になる（明示 fork なし）。
- 復元前の現在地は直近操作完了時に必ずチェックポイント済みなので、失われるものはない（passthrough 対象の設定変更は復元後もそのまま生きる）。
- UI の確認ダイアログ: 「この地点に戻りますか？ 現在の物語はそのまま残り、ここから新しい分岐が始まります。」
- 実行中の画像生成ジョブは復元を妨げない。ただし復元でジョブの対象シーンが存在しなくなった場合、`applyImageJobResult` は「対象シーンが見つかりません」でジョブを error にする（C1 で挙動を確認して調整）。

## GC 一本化（即時 deleteImage の全廃）

現在 store.ts に4箇所ある即時削除を**すべて参照除去のみに変更**する:

1. `setCharacterSprite`（旧 imageId の削除）
2. `removeIllustration`
3. `applyImageJobResult` の立ち絵置換
4. `applyImageJobResult` の背景置換

回収は `gcUnusedImages`（設定画面の「未使用画像を整理」）に一本化し、使用中集合を次の和集合に拡張する:

```
使用中 = collectUsedImageIds(characters, personas, sessions)   ← ライブデータ（既存）
       ∪ branchTrees 全ノードの imageIds                       ← チェックポイント参照
       ∪ branchTrees 全ノードの star.thumbImageId              ← しおりサムネイル
```

- **収集漏れを構造的に防ぐため**、`collectUsedImageIds` からセッション1件分の抽出を `sessionImageIds(session)` として切り出し、①ライブ収集 ②チェックポイント保存時の `imageIds` 抽出 の両方で同じ関数を使う（規約「画像 id を増やしたらここに追加」の対象がこの1関数になる）。
- `deleteSession` を拡張: セッション削除時に `branchTrees` から木を除去し `CheckpointStore.deleteSession` を呼ぶ（画像実体は GC に任せる）。
- エクスポート用の画像収集（T0）は従来どおりライブデータのみ（チェックポイントは含めない設計のため変更なし）。

## ツリー UI（C2: `BranchTreeModal`）

- 入口: ChatPanel トップバーに「🕘」（🖼 の隣）。
- **シーン（大ポイント）を見出しにした縦リスト**を基本形にする（git グラフ風の 2D 描画はしない。実プレイの木は「長い直線＋まれな股裂き」なので、リスト＋分岐展開のほうが読める):
  - scene ノード見出し: 「📖 {title}（{timeLabel}）」＋「↩ レビュー前に戻る」（＝親ノードへ restore。ディレクター抽選の引き直しに相当）
  - 配下に action ノード行: ラベル・時刻・★・（小さく）サイズ・「⏪ ここに戻る」・「🗑」
  - 子が複数あるノードの下に「⑂ 別の分岐 (n)」トグル → 兄弟サブツリーをインデント表示。既定では**現在パスだけを展開**
  - 現在地ノードに「▶ いまここ」バッジ。子に scene を持つ action ノードに「🔀 レビュー直前」バッジ（導出表示）
- **剪定**:
  - 「🗑」= そのノード以下のサブツリーを削除（チェックポイント実体も削除・回収サイズを表示・confirm あり）。**現在パス上のノードは削除不可**
  - 「✂ この分岐だけ残す」= 現在パスに含まれないノードを一括削除（confirm あり）
  - フッターに合計ノード数・合計サイズ
- **共有資産の注釈**（合意事項）: DiscoveryPanel の昇格 confirm と CharacterEditor / WorldEditor / PersonaEditor に一文を追加——「素材の編集・昇格はすべてのセッション・すべての分岐に共有されます（分岐を戻しても巻き戻りません）」。

## しおり（C3）

- ノード行の「★」→ 名前入力（既定は現在ラベル）。`star: { name, thumbImageId }` に保存。
- サムネイルはそのノードの `imageIds` から 背景 → 挿絵 の優先で自動選択（無ければ色バッジ）。
- モーダル上部に「★ しおり」フィルタ（しおりだけの一覧＝ギャルゲのセーブスロット一覧に相当）。

## フェーズ分割

### C1: チェックポイント基盤（UI なし・store と platform のみ）

- `BranchNode`/`BranchTree` 型（types.ts）・`branchTrees` 初期値と partialize 追加
- `CheckpointStore` interface＋Web（IndexedDB）/Tauri（`data/checkpoints/`）実装、gzip/gunzip ヘルパ
- `sessionImageIds(session)` の切り出しと `collectUsedImageIds` の再編
- `recordCheckpoint` ヘルパ＋3契機への組み込み（ルート遅延生成・dedupe 込み）
- `restoreCheckpoint` アクション（passthrough 適用・ガード）
- GC 一本化: 即時 `deleteImage` 4箇所の除去・使用中集合の拡張・`deleteSession` の掃除
- **検証**: Preview MCP の `preview_eval` で store 直叩き——操作→ノード増加、`restoreCheckpoint` で本文・state・timeline・usedEventIds が戻る、復元→操作で兄弟分岐、GC がチェックポイント参照画像を残す、セッション削除でチェックポイント消滅。Tauri チェックリストに「`data/checkpoints/` にファイルが生えて再起動後も復元できる」を追加

### C2: ツリー UI と復元導線

- `BranchTreeModal`（シーングルーピング・分岐展開・現在地・⏪戻る confirm・🗑サブツリー削除・↩レビュー前に戻る・✂この分岐だけ残す）
- ChatPanel トップバー 🕘・復元/削除中のガード（isStreaming 等で disable）
- 素材昇格・素材エディタへの共有資産注釈
- **検証**: Preview MCP で一連の UI 操作（分岐作成→切替→剪定）・エラー 0 件

### C3: しおり・仕上げ

- ★しおり（名前・サムネイル・フィルタ表示）
- 孤児チェックポイントの起動時掃除（`listNodeIds` と木の突き合わせ。GC 実行時でも可）
- サイズ表示の調整・（検討メモ）自動間引き（「fork 後にユーザー発言が無い葉」の自動整理）は使用感を見てから
- **検証**: しおり付与→フィルタ→復元、GC がしおりサムネを保護すること

## リスク・落とし穴（実装時の規約）

1. **`branchTrees` を Session の中に入れない**（スナップショットの再帰肥大）。同様にスナップショットへ「木の情報」を混ぜない。
2. **即時 `deleteImage` を新規に書かない**。画像の削除は常に「参照除去＋GC」（既存規約の強化）。
3. **画像 id を持つフィールドを増やしたら `sessionImageIds` に追加**（GC・チェックポイント両方に効く。従来の「gcUnusedImages に追加」規約はこの関数に一本化）。
4. **passthrough リストの変更は慎重に**。「物語と結合しているか」で判定（結合例: narrativeStyle は本文のパース方式・characterIds は登場人物。非結合例: model・temperature）。迷ったらスナップショット側。
5. スナップショットは Session 全フィールドを保存し、削るのは復元時（passthrough）。保存時に削ると旧チェックポイントの互換が壊れる。
6. `regenerateFrom` 等の既存操作の挙動は変えない（「破壊的」のままでよい——直前状態はチェックポイントが持っている）。
7. 復元ガード（isStreaming / isGeneratingChoices / isReviewing）。sceneReview はランタイムなので復元時に破棄。
8. Session のスキーマ変更（既存フィールドの型変更）を行う場合、旧チェックポイントの読み出し互換に注意。ペイロードに `v: 1` を持たせてあるので、非互換変更時は読み出し時変換 or 「古い記録は復元不可」表示を選ぶ（クリーンブレイク方針はライブデータの話であり、ユーザーの「セーブデータ」は気軽に捨てない）。
9. チェックポイント書き込みは fire-and-forget だが、**連続操作での順序逆転**（前の書き込み完了前に次が始まる）に注意。sessionId ごとに直列化する（単純な Promise チェーンで足りる）。
