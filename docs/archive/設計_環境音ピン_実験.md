# 設計 — 環境音ピン（スクロール連動サウンドスケープ・実験機能）

> 2026-07-26 合意。**実験機能**として最小構成で入れ、「そもそも面白いか」だけをまず検証する。
> 本書は新セッションで設計・実装を始めるための要望まとめ。§1〜§5 が確定方針、§6 に却下案を理由つきで残す。
> 実装前に既存の挿絵（`SceneIllustration`）の仕組みを読むこと。この機能は**挿絵の音声版**であり、位置アンカーの仕組みを流用する。

## 0. この機能に至る製品方針の文脈（新セッション向け前提）

長い議論の末に固まった、視覚・聴覚まわりの製品方針。この機能はこの文脈の上に乗る。

- **本製品はビジュアルノベルではない。文章がメイン。** ターゲットは VN 層ではなく **ラノベ／TRPG 層**。「美しく組版された挿絵入りの本」に寄せる。
- **立ち絵は廃止。** 地の文が感情を書く媒体では立ち絵は冗長。同一ピクセルに2つの注意対象を置くと両損になる。
- **全面背景・背景の独立機能は作らない。** 「場所の絵」が欲しければ挿絵（オンデマンド生成）1枚で足りる。事前資産ライブラリ方式（素材リストをAIに選ばせる）は、VN の事前キュレーション制作モデルへの逆走なので採らない。
- **BGM（音楽）は作らない。** 音楽は世界観固有＝同梱できず、必ずユーザーに準備を強いる。レビュー時にAIへ選ばせる案は、スクロール／分岐で過去に戻ると鳴っている音がズレる「同期問題」を持ち、これは実装で潰しても別の顔で出る（音楽が状態を過剰主張するため）。
- **残す視覚/聴覚要素の判定軸＝「pull型・準備ゼロ・位置固定できるもの」だけ。** 挿絵はこれを満たす唯一の視覚要素。本機能（環境音ピン）は、聴覚要素でこれを満たす唯一の形として設計する。

## 1. 決定サマリ

| 項目 | 決定 |
|---|---|
| 何を作るか | 本文スクロール領域の任意位置に、ユーザーが**環境音ファイルをピン留め**する。スクロールがピンに近づくと音量が上がり、離れると下がる。 |
| 音の種類 | **環境音のみ**（雨・波・風・焚き火・蝉・雑踏など）。音楽は対象外。 |
| 音源 | **アプリ内蔵の環境音ライブラリからのピック**。ユーザー生成・世界観ごとの準備はさせない。 |
| トリガー | **完全手動 pull**。ユーザーが「ここに音を置く」と決めた時だけ。LLM による自動配置は v1 では作らない。 |
| 位置アンカー | **メッセージより細かい"本文フロー上の一点"に固定**（下記§5参照）。挿絵はメッセージ単位ブロックでよいが、音のピンはピーク位置＝本文中の狙った一点に来る必要があるためメッセージ単位では粗すぎる。スクロール・分岐で戻れば同じ音が鳴る点は挿絵と同じ。 |
| 音量カーブ | v1 は**デフォルトカーブ固定**。ユーザーがカーブを描く機能は作らない。調整子はせいぜい「到達半径」1つ。 |
| 位置付け | あくまで**実験機能**。当たってから拡張（カーブ編集・LLM自動提案・共有）を検討。 |

## 2. なぜこの設計が成立するか（判断の根拠・再議論しない）

1. **同期問題が消える。** 音が「今のシーンの状態」ではなく「本文のこの位置」の属性になるため、スクロールで戻れば戻る、分岐で過去ノードに行けばそのノードのピンが鳴る。挿絵の位置固定アーキテクチャにそのまま乗る。
2. **シーン内移動の問題が縮退する。** 「このシーン全体は雨」と状態を過剰主張せず、「この段落あたりに雨がある」点＋減衰半径として表現。読み進めればフェードして消えるので状態を持ちすぎない。読者はサウンドスケープの中を動くプレイヘッドになる。
3. **準備負債が出ない。** pull 型で、欲しい時に置くだけ。世界観作成時に音ライブラリを仕込む工程が要らない。
4. **環境音が音楽より構造的に正しい理由（3つ）:**
   - **チャンネル非競合。** 環境音は目を奪わない。本製品で唯一、本文と同じ感覚チャンネルを取り合わない非テキスト要素。旋律・歌詞は読書の内なる声と競合するが、情報量ゼロの環境音は干渉しない。
   - **ループ耐性。** 定常テクスチャなので任意音量・任意ループでも破綻しない。音楽は構造と進行があるため中途半端な音量・ループが気持ち悪い。
   - **有界で普遍。** 環境音は全世界観で使い回せる普遍セット（20〜30個）。内蔵ライブラリとして配れる。音楽は世界観固有なので同梱できない。

## 3. v1 スコープ

### 3.1 やること

- 内蔵環境音ライブラリ（20〜30音程度、ループ可能な素材）。
- 本文中のメッセージ位置へ環境音ピンを1つ以上留める UI（挿絵の追加導線に倣う）。
- スクロール位置に応じた音量制御。各ピンの音量 = 現在のスクロール中心とピン位置の距離の関数（デフォルトカーブ）。近いほど大、遠いほど 0。
- 複数ピンが近接する場合は**距離関数によって自然にクロスフェード**（＝空間的ミックス。雨＋遠雷のような重なりは許容）。
- ピンの削除。
- ピン情報の永続化（チェックポイント／分岐でも保持されること）。

### 3.2 やらないこと（v1 非スコープ）

- **ユーザーによる音量カーブ描画**（課金相当の knob。当たってから）。
- **LLM による自動ピン配置**（push＋構造化追従の信頼性リスクへ逆戻り。完全手動 pull のみ）。
- **音楽トラックのピン**（環境音のみ）。
- **ユーザーによる音源アップロード／生成**（内蔵ライブラリのみ）。
- **共有・書き出し**（「採譜された一節」を人に聴かせる方向は将来の上振れ余地として認識のみ）。

## 4. 実装上の注意（詰めておくこと）

1. **スクロールは滑らかなプレイヘッドではない。** 読書中はスクロールを止めて数分パークし、そこからジャンプする。生のスクロール位置に音量を直結すると、微小な指の動きで音量がヒクヒクする。**ヒステリシス／スムージング（時間方向のイージング）を必ず入れる。** 目標音量へ一定速度で追従させる等。
2. この機能が一番効くのは**能動的にスクロールして読み進めている瞬間**。パークして読んでいる間はフェードが起きない前提で調整する。
3. **音源はユーザー生成にしない。** 挿絵はオンデマンド生成でよいが、環境音は内蔵ライブラリからのピック。ここでユーザーに音を用意させると pull・準備ゼロが崩れる。
4. **ループ再生**（環境音は定常テクスチャ）。継ぎ目のない素材を用意するか、クロスフェードループにする。
5. **音量 0 のピンは実際に停止/一時停止**してリソース・電池を無駄にしない（画面外の遠いピンを鳴らし続けない）。
6. ブラウザ／Tauri のオーディオ再生ポリシー（初回ユーザー操作までの自動再生ブロック）に留意。
7. **既存の画像 GC 規約に倣う。** 挿絵は「即時 delete を書かず参照除去＋GC」方針。音源ピンも同様に、削除は参照除去のみとし内蔵ライブラリ実体は消さない（そもそも内蔵なので GC 対象外だが、ピンの永続化・分岐チェックポイント参照の整合は挿絵に合わせる）。

## 5. データモデル案（挿絵に"倣うが同じではない"・実装時に確定）

### 5.1 アンカー粒度 — ここが挿絵との決定的な違い

音量は本質的に **`音量 = f(スクロール中心のY − ピンのY)`** であり、ピンの**画面上の縦位置(Y)**がピークを決める。

- **挿絵はメッセージ単位アンカーでよい**。挿絵は「メッセージ直下に置かれるブロック」で、messageId → ブロックのY で足りるため。
- **音のピンはメッセージ単位では粗すぎる**。messageId だけだとピークが**メッセージ末尾（生成単位の切れ目）に固定**され、本文の途中で盛り上げたい狙いとズレる。**メッセージより一段細かい"本文フロー上の一点"にアンカーし、描画時に DOM Range 経由でその一点のYへ解決する**必要がある。

**⚠ レンダリング上の"行"（折り返し行）をアンカーにしてはいけない。** 折り返しはウィンドウ幅・フォント・ズームで変わり、永続化した位置が壊れる。「行単位で置きたい」という要望は**内容上の安定位置**で実装する:

- 候補A: **文字オフセット** `{messageId, charOffset}` — メッセージ本文（ソーステキスト）先頭からの文字数。最も細かく狙える。
- 候補B: **段落インデックス** `{messageId, paragraphIndex}` — 地の文の段落単位。粗いが安定しUIも作りやすい。
- 精度がどれだけ効くかは**到達半径と釣り合う**。半径が広ければ段落単位でも体感差は小さい（過剰実装）。実験初手は **段落インデックス＋やや広めの半径**で始め、細かい配置要望が出たら文字オフセットへ、が現実的。両論併記で実装時に選ぶ。

### 5.2 型（第一候補・実装時確定）

```
AmbientPin — {id, soundId, messageId?, anchor, createdAt, radius?}
  soundId: 内蔵ライブラリの環境音 id
  messageId: アンカー先メッセージ（消失時はシーン末尾フォールバック＝挿絵と同規約）
  anchor:   メッセージ内の位置。charOffset か paragraphIndex のいずれか（§5.1 で確定）
  radius?:  到達半径（省略時デフォルト）
Scene — {..., illustrations?, ambientPins?, ...}  // 読む側は ambientPins ?? []
```

参考・挿絵の現行型:
```
SceneIllustration — {id, imageId, prompt, negative?, messageId?, createdAt}
Scene — {..., illustrations?, backgroundImageId?, ...}  // 読む側は illustrations ?? []
```

### 5.3 その他

- **描画時の解決:** anchor → DOM Range → `getBoundingClientRect().y` で一点のYを得て、スクロール中心との距離で音量を算出。
- **編集耐性:** 本文編集・やり直しで anchor が範囲外になったらクランプ（末尾へ丸め）。メッセージ消失時はシーン末尾フォールバック。
- **マーカーは本文へ差し込まない。** ピンはメタデータ。解決したYの位置に**左ガター/余白の小マーカー**を出す（`@`アイコンのように本文へ埋め込まない＝本文を汚さない）。
- 分岐チェックポイント／`sessionImageLogs` 相当の整合は挿絵の実装を参照して合わせる。
- 永続化はクリーンブレイク方針（既存データ移行不要）。既存 Scene に `ambientPins` が無いケースは `?? []` で吸収。
- `AGENTS.md` のデータモデル節・実装済み機能節を同一コミットで更新。

## 6. 音源データの管理（内蔵アセット。JSONにもカセットにもblobストアにも入れない）

「内蔵ライブラリのみ」（§3.2）の帰結として、**環境音は世界観データではない**。データ管理の重い部分（blobストア・GC・エクスポート・カセット同梱・移行）が丸ごと不要になる。

### 6.1 画像と同じ扱いにしない理由

画像（`imageStore.ts`）がblobストア（Web=IndexedDB / Tauri=`%APPDATA%/data/images/<id>.<ext>`）を要するのは、**ユーザー生成・無限・不透明id（`uid()`）**だから。環境音は真逆で、道具立てを共有しない。

| | 画像 | 環境音 |
|---|---|---|
| 出所 | ユーザー生成 | アプリ内蔵（固定カタログ） |
| 数 | 無限 | 有界（20〜30） |
| id | 不透明 `uid()` | **意味のある安定キー**（例 `"rain-soft"`） |
| 実体の置き場 | blobストア（IndexedDB/ファイル） | **アプリ同梱の静的アセット** |
| JSONに載るもの | `imageId`（参照） | `soundId`（参照） |
| GC / エクスポート / カセット同梱 / 移行 | 必要 | **全部不要** |

### 6.2 保存方針

- **JSONに載るのは `soundId`（短い安定キー文字列）だけ。** `AmbientPin.soundId` が持つのはこれ。音声バイトは state.json にも世界観にも入らない。
- **音源** = アプリ同梱の静的ファイル（ループ可能な `.ogg`/`.opus`、モノラル圧縮。1本数百KB、20〜30本で計5〜10MB目安）。まず Vite の `import`/`public/` 参照が Web/Tauri 共通で最短。サイズが問題になれば Tauri `resources`＋asset protocol へ移す。
- **カタログ（マニフェスト）** = コード側の定数（`soundId → {ファイル, 表示名, ループ情報, ライセンス/帰属}`）。アプリの一部でありデータではない。
- **id は `uid()` にしない。** カタログはアプリと共にバージョン管理される作り込み資産なので、`"rain-soft"` のような**安定・可読キー**にする（移植性とフォールバックのため）。

### 6.3 カセット共有・フォールバック

- 環境音ピンを使った世界観を共有しても、**カセットには `soundId` 文字列が入るだけ**。音声バイトは同梱されない（受け取り側の内蔵ライブラリで解決）。スプライトのような base64 同梱は不要。
- アプリのバージョン差でカタログに無い `soundId` を参照した場合は **黙ってスキップ**（そのピンは鳴らないだけ）。安定キーなので通常は解決する。実験機能としてはこの寛容フォールバックで十分。

### 6.4 将来（スコープ外）

万一ユーザー持ち込み音源を許すなら、そのとき初めて画像と同じ道具立て（blobストアの音声版＋カセットへの base64 同梱＝スプライト方式）を再利用する。**v1ではやらない**。built-in に絞ることでこの重い部分を回避しているのが本設計の要。

## 7. 却下・保留にした案（理由つき・蒸し返さない）

| 案 | 却下/保留理由 |
|---|---|
| レビュー時に AI が BGM/背景を素材リストから選ぶ | スクロール・分岐で過去に戻ると同期がズレる。音楽が状態を過剰主張し、シーン内移動で破綻。事前資産モデルへの逆走。 |
| BGM（音楽）のピン | 音楽は構造・進行を持つため任意音量/ループが不自然。読書の内なる声と競合。世界観固有で同梱不可。→ 環境音に限定。 |
| ユーザーによる音量カーブ描画 | knob はユーザーへの課税。実験段階の検証（面白いか）に不要。当たってからデフォルトカーブの外へ開く。 |
| LLM による自動ピン配置 | push＋構造化追従の信頼性リスク。安いモデルでは失敗が可視化される責任を持たせない方針。v1 は手動 pull のみ。 |
| ユーザー音源アップロード/生成 | 準備負債が生まれ pull・準備ゼロが崩れる。内蔵ライブラリのみ。 |
| 立ち絵・全面背景・独立した背景機能 | §0 の製品方針により廃止/不採用。 |
