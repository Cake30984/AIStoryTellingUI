## 2. FB9-A — 完結後は分岐だけ

### 2.1 現状と問題

`isSessionFinalized`（[store.ts:1566](../src/store.ts)）が真のとき、ChatPanel は本文中の「分岐」ボタンごと生成系の操作を全部隠し（[ChatPanel.tsx:436](../src/components/ChatPanel.tsx)）、代わりにコンポーザーへ「ここから分岐して続ける」（`branchToContinue`）を出す。この導線は**完結（`endedAt`）だけを解除して同じ線の続きを書かせる**ため、「終わった物語」がその場で終わらなくなる。

### 2.2 決定

1. **`branchToContinue` は廃止**（アクション・ボタン・型定義とも削除）。
2. 完結後も**本文中の各メッセージの「分岐」を表示する**。分岐＝その地点まで巻き戻して新しい世界線を作る操作であり、完結した線は名前つきブランチとして保護されて残る。
3. **`session.messages` の末尾1件からは分岐させない**。そこからの分岐は「完結した線の続きを同じ線で書く」ことと等価であり、廃止した `branchToContinue` の復活になるため。
4. 完結中に許可する操作は **分岐と、挿絵・背景の生成のみ**。編集・削除・やり直す・続きを生成・選択肢を生成・シーン編集・入力欄は出さない。挿絵・背景を許すのは本文を書き換えないため（完結した物語に後から絵を足せる）。
5. 分岐でエピローグより前へ巻き戻ったら **`ending` を解除**して普通に続きを書ける状態に戻す。エピローグ内へ巻き戻った場合は `ending` を保ったまま**完結（`endedAt`）だけ解除**する（エピローグ継続中＝「物語を完結する」で再び締められる）。

### 2.3 型

追加・変更なし。削除のみ。

```ts
// store.ts の AppState から削除
branchToContinue: () => Promise<void>   // 1300 行付近の宣言と 3519-3547 の実装
```

### 2.4 実装

**`src/store.ts`**

1. `branchToContinue` の宣言（1299-1300）と実装（3519-3547）を削除。
2. 巻き戻し後の結末整理を行う純関数を追加（`rewindScenesFor`（1548）の直後に置く）。

```ts
/**
 * 巻き戻し後の scenes を見て ending / 完結を整理する（FB9-A）。
 * - エピローグシーンごと消えた → ending を解除（普通の物語に戻る）
 * - エピローグシーンが残った   → ending は保ち endedAt だけ解除（エピローグ継続中）
 * ending が無ければ何もしない（未完結の通常巻き戻しでも安全に通せる）。
 */
export function rewindEndingFor(
  s: Pick<Session, 'ending'>,
  scenes: Scene[],
): { ending?: Session['ending']; scenes: Scene[] } {
  if (!s.ending) return { scenes }
  const epId = s.ending.epilogueSceneId
  if (!scenes.some((sc) => sc.id === epId)) return { ending: undefined, scenes }
  return {
    ending: s.ending,
    scenes: scenes.map((sc) => (sc.id === epId ? { ...sc, endedAt: undefined } : sc)),
  }
}
```

### 2.5 受け入れ基準

- 完結したセッションで、末尾以外のすべてのメッセージに「分岐」が出る。末尾のメッセージには出ない。
- 完結中に 編集・ここから・削除・続ける・やり直す・続きを生成・選択肢を生成・シーン編集・入力欄 が一切出ない。挿絵・背景ボタンは出る。
- 完結前のシーンのメッセージから分岐すると、`session.ending` が消え、`.finalized-lock` が入力欄に戻り、続きを書ける。
- エピローグ内（末尾以外）のメッセージから分岐すると、`ending` は残り「物語を完結する」ボタンが出る状態に戻る。
- どちらの場合も分岐ツリーに元の完結線が ⑂ 名前つきで残り、🏁 ノードも消えていない。
- 分岐ツリーの「⑂ ここから分岐して再開」は従来どおり動く（本バッチで触らない）。

### 2.6 落とし穴

- `regenerateFrom` に `opts` を足すと、既存の呼び出し（`branchFromMessage` 以外）は引数省略で完結ガードが効いたままになる。これが正しい挙動。**ガード自体を消してはいけない。**
- `rewindEndingFor` を `patchActive` のスプレッド順で `rewindScenesFor` の**後**に置くこと。順序が逆だと `scenes` が上書きされて `endedAt` の解除が消える。
- `editMessage` / `deleteMessage` は store 側に完結ガードが無い（UI で隠しているだけ）。本バッチでは現状維持。コマンドパレット等から到達する経路を将来足す場合はガードを追加すること。

## 3. FB9-B — 到達エンディング記録のセッション化

### 3.1 現状と問題

`EndingRecord` は `{worldId, endingDefId, sessionId, reachedAt, parties?}`（[types.ts:938](../src/types.ts) の `endingRecords`）。`sessionId` を持っているのに、表示側が `worldId` だけで絞っているため、**同じ世界観の別セッションで到達した結末が、今のセッションでも到達済みに見える**（[StatusView.tsx:164](../src/components/StatusView.tsx)）。

世界観に紐づけるのが誤りである理由: 世界観は再利用される素材で、1つの世界観から複数のカセット（別々の物語）を作れる。カセット配布時には受け手のライブラリへ世界観がマージされる。プレイ履歴を素材側に持たせると、混ざるか配布物に他人の記録が乗るかのどちらかになる。「素材は不変・プレイの結果はセッション側」という既存原則（`SessionOverlay` と同じ）から外れる。

### 3.2 決定

記録の**主キーはセッション、集計軸はカセット**の二段構えにする。

| 表示場所 | 集計単位 | 文言 |
|---|---|---|
| ステータス（プレイ中） | `sessionId === session.id` | 「エンディング（このセッションで到達 n/m）」 |
| カセット棚 | `cassetteId === cas.id` | 「到達エンディング n/m」（tooltip に「通算」） |

- セッション単位でも n/m に意味がある。FB9-A により**1セッション内で分岐して複数のエンディングを回収できる**ため。
- 記録テーブル自体は残す（セッションを削除してもコレクションが消えないため）。
- 「見た結末」という表記は全廃し「到達エンディング」に統一する。
- 世界観単位の集計は廃止。`EndingRecord.worldId` は World 削除時の掃除（[store.ts:2534](../src/store.ts)）に使うため残す。
- カセット由来でないセッション（ライブラリから直接組んだもの）は棚に出ない。セッション内表示のみで足りる。

### 3.3 型

```ts
// types.ts — Session
/** このセッションの出自カセット（FB9-B。到達エンディングをカセット単位で集計するため） */
originCassetteId?: string

// types.ts — EndingRecord
/** 出自カセット（FB9-B。棚のコレクション表示の集計キー） */
cassetteId?: string
```

### 3.4 実装

1. **`store.ts` `playCassette`（4237）** — クローンしたセッションに `originCassetteId: cas.id` を注入する。
2. **`lib/cards.ts` `freshSessionOf`（392 付近）** — `ending` を初期化しているのと同じ場所で `originCassetteId` を落とす。カセット下書きの種にセッションを使ったとき、出自が引き継がれると誤集計になるため。
3. **`store.ts` エピローグ突入時の追記（3407-3418）** — レコードに `...(s.originCassetteId ? { cassetteId: s.originCassetteId } : {})` を足す。

7. **`AGENTS.md`** — データモデル節の `EndingRecord`・`Session` の説明を更新（「周回横断」→「セッション単位＋カセット通算」）。

### 3.5 受け入れ基準

- 世界観 W のセッション S1 でエンディング E に到達したあと、同じ世界観の新規セッション S2 のステータスで E が未到達（`hidden` なら ？？？）に見える。
- S1 内で分岐して別のエンディング F に到達すると、S1 のステータスが 2/m になる。
- カセット C から S1・S2 を始めた場合、棚の C の表示は S1・S2 の到達を合算した distinct 件数になる。
- カセット由来でないセッションの到達は、どのカセットの棚表示も増やさない。

### 3.6 落とし穴

- 既存の `EndingRecord` は `cassetteId` を持たないため、**棚の表示は 0 から始まる**。クリーンブレイク方針として許容する（ユーザーに一言伝える）。
- `exportBundle`/`importBundle` の `mergeEndingRecords` は同値 dedupe。`cassetteId` が増えるとキーが変わるので、dedupe 条件が id 全体の比較になっているか確認すること。

## 4. FB9-C — 関係フラグの撤去と「フラグ」の再定義

### 4.1 現状と問題

`Relation.flags: string[]` は**レビューが自由文字列で立てる**（[prompts.ts:438](../src/lib/prompts.ts)）。条件側は `flags.includes(clause.flag)` の完全一致（[store.ts:224](../src/store.ts)）。世界観の作者は、AI がどんな文字列を生成するか事前に知り得ないため、**狙ったフラグを条件にできない**。

経緯（`設計_ステータスエンジン.md` §2.2）: フラグは条件のために作られたのではなく、**stance/aspects が毎レビューで全文置換されるため、消えては困る不可逆な事実の退避先**として P1 で生まれた。P4 の条件エンジンで `Clause` に接続された際、`stats`/`counters`/`achievements` には World 側の定義（Def）があるのに **flags だけ定義を持たないまま条件変数に昇格した**。これが非対称の起点。

前提はすでに崩れている:

- 長期記憶は `Scene.summary` の全シーン注入（`priorSummaries`）が担っている。
- レビュープロンプトが「今シーンで変化していない機微（好悪・約束）は失わず維持して書く」と明示するようになった（[prompts.ts:437](../src/lib/prompts.ts)）。
- そもそも `buildStateInfo`（[store.ts:1623](../src/store.ts)）はフラグを読んでいない＝**本編プロンプトに届いていない**。退避先として機能していない。
- 和集合でしか増えず、**UI に削除手段が一つも無い**（`StatusPanel` は 🚩 の読み取り専用表示、レビューは `flagsAdd` の追加のみ）。一度立つと状況が変わっても永久にレビュープロンプトへ載り続け、文脈からずれた解釈を誘発する。

### 4.2 決定

**関係フラグを撤去する。置き換えの新しい型は作らない。**

当初は「世界観で定義するフラグ」（`FlagDef`／`Clause.flag`）を新設する計画だったが、2026-07-26 の再検討で**新設しないこと**に決めた。理由:

1. **表現力の増加がゼロ**。「一度きりの不可逆な出来事」はキャラ別カウンター `>= 1` で完全に表現できる。カウンターは単調増加で取り消されず、世界観で名前を定義済み＝閉じたリストとしてレビューに渡っており、条件として狙って当てられる。
2. **プレイヤーは条件式を見ない**。画面に出るのは実績の解除・エンディングの到達・イベントの発火の3つだけ。条件の語彙はプレイヤー体験ではなく作者の道具であり、増やしても没入や周回動機は上がらない。
3. **`>= 1` がユーザーに露出するという前提が誤りだった**。条件エディタは FB8-E3 で既に文章形（`OP_LABELS`）になっており、「告白した が 1 以上」と表示される。単位「回」を足せば「告白した が 1回 以上」で一般ユーザーにも自然に読める。
4. **作者の実際のボトルネックは語彙ではなく予測可能性**。「どういう場面で計上されるか」を AI に伝える手段が無いことが問題で、それは `CounterDef.note` で解ける。フラグ型の追加はこれに何も足さない。

したがって本バッチは **(a) 害のあるものの除去** と **(b) 予測可能性を上げる最小の追加** の2点だけを行う。

- **除去**: `Relation.flags` / `RelationUpdate.flagsAdd` / `Clause`・`GroupSubClause` の `relationFlag` 節と、それらの評価・プロンプト・表示・編集 UI 一式。
- **追加**: `CounterDef.note`（どんな時に計上するか）をレビュープロンプトへ渡す。条件エディタのカウンター行に単位「回」を付ける。

将来、実際にカセットを作る中で「回数として書くのが不自然な条件が多い」と分かった時点で `CounterDef.kind` を足せばよい。**語彙を先回りして増やさず、必要が実証されてから足す。**

### 4.5 既存データの正規化

既存 World の条件式に `relationFlag` 節が残っていると、union から消えた `kind` が評価器の `default: return false` に落ち、実績・エンディングが恒久的に達成不能になる。**読み込み時に一度だけ落とす。**

- `store.ts` に純関数 `stripLegacyFlagClauses(world: World): World` を置き、persist の `merge`（`normalizeUiPrefs` を呼んでいる箇所）で全 `worlds` に適用する。
- 対象は `achievements[].condition` / `endings[].condition` / `scheduledEvents[].condition` の `all`/`any` 配列と、`group` 節の `clauses` 配列。`kind === 'relationFlag'` の要素を除去するだけ。
- 節が空になった条件は `matchGroups` が `ok:false` を返す（[store.ts:386](../src/store.ts)）ため追加対応は不要。`WorldEditor` では条件が空の定義として現れるので、ユーザーが自分で書き直せる。
- `Relation.flags` は型から消えるだけで、`state.json` に残っていても読み捨てられる。移行コードは書かない。

### 4.6 受け入れ基準

- `rg "flagsAdd|relationFlag|🚩"` が 0 件（設計ドキュメントを除く）。
- 世界観エディタのカウンター定義に説明欄があり、書いた内容がレビュープロンプトの `counterEvents` 指針に現れる（`reviewSystem` の戻り値を直接確認すれば足りる）。
- 条件エディタでカウンター条件が「〔告白した〕が〔1〕回〔以上〕」と読める。ステータス条件には「回」が付かない。

- `relationFlag` 節を含む既存 World を読み込んでも型エラー・実行時エラーが出ず、当該節が消えている。空になった条件の実績が勝手に解除されない。

## 6. 却下案

> フラグ関連は検討の過程で結論が2度動いている（定義済みフラグを新設する → 内部はカウンター共有 → 新設しない）。**最終決定は §4.2**。以下は経緯として残す。

- **`CounterDef.kind:'count'|'flag'` で内部を共有し UI だけ分ける** — 一度は採用したが撤回（2026-07-26）。`world.counters` を読む21箇所のうち**約14箇所が `kind` の絞り込みを必要とし、絞り忘れがすべて型エラーにならず静かに壊れる**（レビュー用リストにフラグが混ざる・本編に数値で出る・パネルが数値入力になる等）。判定式が `(d.kind ?? 'count')` と旧データ対応を含むため、`d.kind === 'count'` と書くと旧カウンターが全部こぼれる罠も残る。
- **`FlagDef`/`FlagValue` を独立した型として新設** — 上の共有案より型安全（追加コストは `SessionState` の3リテラルで、いずれも型エラーとして検出される）だが、そもそも**カウンターに対する表現力の増加がゼロ**であることが決め手で不採用。型・値・条件節・レビュー契約・エディタ節・表示を各1つずつ増やす対価が、UI 上の語彙の差だけに見合わない。
- **自由フラグのまま条件側を部分一致にする** — 「意図した時に立つ／立たない」の不確実性が残り、作者が結果を検証できない。
- **フラグを本編プロンプトに注入して残す（撤去しない）** — 和集合で永久に増え、取り消し手段が無い設計のままでは、文脈からずれた古い事実が生成を歪め続ける。
- **用語を「できごと」「経験」「節目」へ変更** — 新しい型を作らない決定により論点ごと消滅（カウンターの語彙で足りる）。
- **到達記録を世界観に紐づけたまま `sessionId` で表示だけ絞る** — セッション内表示の問題は解けるが、素材にプレイ履歴が貼りつく構造（カセット配布時の混入）が残る。
