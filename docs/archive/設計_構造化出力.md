# 設計: 構造化出力（セリフ・地の文・話者・感情の機械可読化）

> **⚠ 感情タグは撤去済み（2026-08-01）**: 本書の**感情（`(感情)` トークン・`EmotionId`・`resolveEmotionToken`・
> ストリーミング表情切替・方式A フォールバック）に関する記述はすべて実装から削除**されました。
> 唯一の消費先だった立ち絵を廃止したためです（`AGENTS.md` の「立ち絵・背景の撤去」／`docs/公開計画_マネタイズと配布.md` の製品方針＝「挿絵入りの本」）。
> **現在の出力形式は `@名前「セリフ」`**（話者名＝行頭 `@` から最初の `「` まで）。**後方互換は持ちません**——
> 旧メッセージに残る `@美咲(joy)「…」` は話者チップに `(joy)` が出ますが、名前の前方一致でアイコンは正しく
> 解決されます。`@地の文(感情)「…」` はラベル非表示の救済が効かず話者行として描かれます。
> セリフ・地の文・話者の機械可読化（D-1〜D-6・graceful degradation・レンダラ分岐）は**現役**です。

ロードマップ項目 4 の詳細設計。本編出力を「どの行がセリフで、誰の発言で、どの感情か」が機械可読な
行フォーマットにし、次の3つを実現する:

1. **立ち絵の表情切替をストリーミング中に行単位で行う**（毎応答後に裏方 LLM が判定する現行の方式A を、
   本編出力自体に埋め込まれた感情タグで置き換える。ただし方式A は削除せず**フォールバックとして残す**）
2. **将来の読み上げ（TTS）の下準備**（セリフ＝キャラ声／地の文＝ナレーター声の振り分けに必要な
   「話者つきセリフ行」構造をパーサ出力として確立する。TTS 自体は本設計の範囲外）
3. **チャット画面はマークアップを隠して綺麗に表示**（novel＝小説風の流し込み、chat＝話者ごとの吹き出し。
   既存の平文メッセージと混在しても壊れない）

実装フェーズは **ST1（基盤・表示）→ ST2（生成・立ち絵連動）→ ST3（周辺の整流）** の3段階。
各フェーズごとに tsc → build → Preview 検証 → CLAUDE.md 更新 → commit → push（既存の進め方と同じ）。
**ST1 の時点では生成プロンプトを一切変えない**ため、各フェーズが独立に検証可能。

## 必須仕様: graceful degradation（弱モデル耐性・途中切れ耐性）

この機能の成否は「フォーマットが守られなかった時に何も壊れないこと」で決まる。以下を**全フェーズの不変条件**とする:

| # | 状況 | 挙動 |
|---|---|---|
| D-1 | 行頭に `@` が無い行 | すべて**地の文（narration）**として扱う。→ 既存の平文メッセージ（旧データ・構造化OFFセッション）は全行 narration となり、表示・挙動が現状と完全一致する |
| D-2 | `@` 行だが名前が参加キャラに解決できない | **セリフとして表示は行う**（名前をそのまま表示。モブ・脇役の発言をサポート）。characterId 無しなので立ち絵切替はしない |
| D-3 | 感情が6値に解決できない・無い | セリフとして扱い、感情だけ無視（立ち絵は現在の表情を維持） |
| D-4 | ストリーミング途中・`max_tokens` 途中切れ | 末尾の「改行で終わっていない行」は**未確定行**として生テキストのまま表示。感情の反映は**確定行（改行済み）のみ**。「⤵ 続きを生成」の追記で行が完成すれば再パースで正しく表示される |
| D-5 | モデルがフォーマットを完全に無視 | 全行 narration → 現状の表示と同じ。この場合は**方式A（classifyEmotions）へ自動フォールバック**し、立ち絵切替も現状どおり動く |
| D-6 | 本文がフォーマットを部分的にしか守らない | 守られた行だけ構造化の恩恵を受け、残りは narration。テキストが失われることは決してない |

**原則: パースに失敗した行は必ず「そのままのテキストの narration」に落ちる。テキストの欠落・改変は一切しない。**

## フォーマットの決定（ADR）

### 採用: 行単位軽量タグ

```
夕日が教室をオレンジ色に染めていた。彼女は窓際で振り返る。
@美咲(shy)「……ねえ、ちょっとだけ時間いい？」
@美咲(joy)「やった。じゃあ、屋上ね」
返事を待たずに駆け出していく。その背中を追いかけた。
@店員(neutral)「いらっしゃいませー」
```

文法（1行＝1ユニット）:

```
dialogue-line = "@" 名前 [ "(" 感情 ")" ] セリフ本文
narration-line = 上記以外のすべての行
```

- **名前**: `@` の直後から、最初の `(`／`（`／`「` までの文字列（trim）。参加キャラ名と完全一致 →
  前方一致で解決（既存 `resolveEmotionUpdates` と同じ規則）。解決できなくてもセリフ扱いは維持（D-2）。
- **感情**: `neutral / joy / anger / sadness / shy / surprise`（`EmotionId`）。括弧は ASCII `()` と
  全角 `（）` の両方を受理。日本語ラベル（`ふつう/喜び/怒り/悲しみ/照れ/驚き`＝`EMOTIONS[].label`）も
  id に解決する（弱モデルが日本語で書いてしまうケースの救済）。
- **セリフ本文**: 感情括弧（無ければ名前）以降の残り全部。通常は鉤括弧「」込みで書かれる。
  1発話＝1行（プロンプトで指示）。

### 却下した代替案

- **XML（`<say name="美咲" emotion="joy">…</say>`）**: ①途中切れで閉じタグが欠けるとパース不能になり
  D-4 を満たせない、②弱モデルが属性の引用符・ネスト・エスケープを崩しやすい、③開閉タグぶんトークンを
  食う、④ストリーミング表示にインクリメンタル XML パーサが必要になる。行タグは「行が増えるだけ」で
  途中切れ＝最後の1行が未確定になるだけなので、graceful degradation の要件に構造的に合うのは行タグ。
- **JSON（`{"lines":[...]}`）**: ストリーミング逐次表示がほぼ不可能（完了までパースできない）、
  途中切れが致命傷。裏方系（選択肢・レビュー）と違い、本編は逐次表示が生命線なので不採用。
- **現行の自然慣習（`名前「セリフ」`）をそのままパースする案**: マークが無いため地の文中の引用
  （`彼は「はい」と言った`）と区別できず、誤検出でセリフでない行が吹き出しになる。「タグが無い行は
  必ず narration」という安全側の規則が成立しない。`@` プレフィックスは「書き手（LLM）が明示的に
  宣言した行だけ構造化する」ための必須マーカー。

### 保存形式の決定: マークアップ付きの生テキストを `Message.content` にそのまま保存

パース結果（構造体）は**保存しない**。`Message` スキーマ・persist キー（v3）・チェックポイント・
セッションカード・エクスポートは**一切変更しない**。

| 論点 | 決定 | 理由 |
|---|---|---|
| 保存 | 生テキスト（`@` 行込み）を `content` に保存。パースは表示時・ストリーミング監視時に都度行う純粋関数 | スキーマ不変＝分岐チェックポイント・カード・旧データとの互換が**無条件で成立**。「既存平文との共存」は D-1 により自動的に解決（レンダラ二刀流ではなく「単一レンダラ＋全行 narration という縮退」） |
| API 履歴 | `buildMessages` の履歴は**生テキストのまま送る**（マークアップを剥がさない） | モデルが自分の過去出力の形式を見ることで形式遵守が強化される（few-shot 効果）。剥がすと毎ターン形式を忘れる方向に働く |
| 編集 UI | 生テキストを編集（マークアップが見える） | 編集は上級操作。マークアップを隠す編集 UI は複雑化に見合わない。✎ を押せば形式が学べる副次効果もある |
| 裏方文脈（レビュー・挿絵起案・表情判定） | `plainTextOf` で `@名前(感情)「…」` → `名前「…」` に変換して渡す（ST3） | 裏方 LLM に独自形式の学習コストを払わせない。話者情報は自然な `名前「…」` 形式で保持される |
| トークン目安（`estimateTokens`） | 生テキストのまま（変更しない） | 実際に API へ送るのは生テキストなので、目安として正しいのはこちら |

### セッション設定: `structuredOutput?: boolean`

- `Session` に optional 追加（persist v3 のまま）。**新規セッションは `true`**（`newSession` factory で設定。
  本機能を新しい標準にするため）。**既存セッションは undefined＝OFF**（`?? false` で判定。進行中の物語の
  途中でモデルへの指示が変わるのを避ける。有効にしたい場合は SessionEditor のトグルで ON にする）。
- ON/OFF はいつ切り替えてもよい（メッセージ単位でパースするため、履歴に平文と構造化が混在しても
  D-1 でそれぞれ正しく表示される）。
- `restoreCheckpoint` の passthrough には**入れない**（＝スナップショット側から復元）。本文の形式と
  結合した設定であり、`narrativeStyle` と同じ扱い（CLAUDE.md の判定規則「本文・進行と結合しているか」）。
- 選択肢・レビュー・表情判定（フォールバック）・画像起案など**裏方の JSON 出力は本設計の対象外**
  （現行のまま）。構造化するのは**本編（runCompletion）の出力のみ**。

### ST1-2. パーサ（新規 `src/lib/structured.ts`）

すべて純粋関数。store・React に依存しない（`types.ts` のみ import）。

```ts
import { EMOTIONS, type EmotionId } from '../types'

/** 構造化本文の1行。dialogue 以外はすべて narration（graceful degradation の要） */
export type StructuredLine =
  | { kind: 'narration'; text: string }
  | {
      kind: 'dialogue'
      /** 行頭 @ の直後に書かれた名前（未解決でもそのまま保持＝モブ対応） */
      name: string
      /** 参加キャラに解決できた場合のみ */
      characterId?: string
      /** 6値に解決できた場合のみ */
      emotion?: EmotionId
      /** セリフ本文（通常「」込み） */
      text: string
      /** 元の行全文（編集・フォールバック表示用） */
      raw: string
    }

export interface ParseCharacter {
  id: string
  name: string
}

/** キャラ名解決: 完全一致 → 前方一致（双方向 startsWith）。resolveEmotionUpdates と同一規則 */
export function matchCharacterByName(name: string, characters: ParseCharacter[]): string | undefined {
  const hit =
    characters.find((c) => c.name === name) ??
    characters.find((c) => c.name && (name.startsWith(c.name) || c.name.startsWith(name)))
  return hit?.id
}

/** 感情トークンを EmotionId に解決（id の大小文字ゆれ・日本語ラベルも受理）。不明は undefined */
export function resolveEmotionToken(token: string): EmotionId | undefined {
  const t = token.trim().toLowerCase()
  const byId = EMOTIONS.find((e) => e.id === t)
  if (byId) return byId.id
  const byLabel = EMOTIONS.find((e) => e.label === token.trim())
  return byLabel?.id
}

/** 1行をパースする。@ 行でなければ narration */
export function parseLine(line: string, characters: ParseCharacter[]): StructuredLine {
  if (!line.startsWith('@')) return { kind: 'narration', text: line }
  const body = line.slice(1)
  // 名前 = 最初の ( / （ / 「 まで。どれも無い行・名前が空/長すぎる行は narration に落とす（D-1 の原則）
  const m = body.match(/^([^(（「]{1,24})([(（]([^)）]{0,12})[)）])?/)
  const name = m?.[1]?.trim() ?? ''
  if (!name) return { kind: 'narration', text: line }
  const emotionToken = m?.[3]
  const rest = body.slice((m?.[0] ?? '').length).trim()
  // セリフ本文が空（@名前 だけの行）は情報が無いので narration 扱い
  if (!rest) return { kind: 'narration', text: line }
  return {
    kind: 'dialogue',
    name,
    characterId: matchCharacterByName(name, characters),
    emotion: emotionToken ? resolveEmotionToken(emotionToken) : undefined,
    text: rest,
    raw: line,
  }
}

/** 本文全体をパースする。空行は narration（text=''）としてそのまま保持（段落区切りをレンダラが使う） */
export function parseStructured(content: string, characters: ParseCharacter[]): StructuredLine[] {
  return content.split('\n').map((line) => parseLine(line, characters))
}

/** dialogue 行を1行でも含むか（レンダラのレガシー・フォールバック判定用） */
export function hasStructuredLines(content: string, characters: ParseCharacter[]): boolean {
  return parseStructured(content, characters).some((l) => l.kind === 'dialogue')
}

/**
 * マークアップを自然な日本語表記に落とす（裏方 LLM の文脈・チェックポイントラベル用。ST3 で使用）。
 * @美咲(joy)「やった」 → 美咲「やった」。narration はそのまま。
 */
export function plainTextOf(content: string): string {
  return content
    .split('\n')
    .map((line) => {
      const parsed = parseLine(line, [])
      return parsed.kind === 'dialogue' ? `${parsed.name}${parsed.text}` : line
    })
    .join('\n')
}

/**
 * 確定行（＝末尾の未完行を除いた行）から立ち絵の感情更新を抽出する（ST2 のストリーミング監視用）。
 * 同一キャラが複数回発言していれば後勝ち。characterId と emotion の両方が解決できた行のみ。
 */
export function emotionUpdatesOf(
  completedLines: string[],
  characters: ParseCharacter[],
): { characterId: string; emotion: EmotionId }[] {
  const map = new Map<string, EmotionId>()
  for (const line of completedLines) {
    const p = parseLine(line, characters)
    if (p.kind === 'dialogue' && p.characterId && p.emotion) map.set(p.characterId, p.emotion)
  }
  return [...map.entries()].map(([characterId, emotion]) => ({ characterId, emotion }))
}
```

注意:
- `matchCharacterByName` を新設したので、`store.ts` の `resolveEmotionUpdates` 内の同一ロジック
  （完全一致→前方一致）を**この関数を import して置き換える**（重複実装を残さない。挙動は不変）。
- `plainTextOf` は characters 無しでパースする（characterId 解決は不要。名前文字列があれば十分）。

### ST1-3. 構造化レンダラ（ChatPanel.tsx）

方針: **メッセージ単位のフォールバック**。`hasStructuredLines(m.content, participants)` が false なら
既存の `renderNovelMessage`/`renderMessage`（吹き出し）を**そのまま**使う（＝旧データ・構造化OFF・
モデルがフォーマット無視、のすべてで現状表示）。true のときだけ構造化レンダラに切り替える。

新コンポーネント `StructuredContent`（ChatPanel 内 or 小ファイル分離はどちらでも可）:

```tsx
function StructuredContent({ m, participants, novel, pending }: {
  m: Message
  participants: Character[]
  novel: boolean
  pending: boolean
}) {
  const lines = useMemo(() => parseStructured(m.content, participants), [m.content, participants])
  // ストリーミング中は最後の「改行で終わっていない行」を未確定として生表示する（D-4）
  const endsWithNewline = m.content.endsWith('\n')
  const settled = pending && !endsWithNewline ? lines.slice(0, -1) : lines
  const tail = pending && !endsWithNewline ? lines[lines.length - 1] : undefined
  ...
}
```

表示ルール:
- **novel（小説形式）**: narration 行は現行 `renderProse` と同じ装飾（「」spans）で段落表示。
  dialogue 行は `.st-dialogue` 行として表示——先頭に小さな話者チップ（`EntityAvatar` の色 or 名前。
  `characterId` 解決済みなら参加キャラの色を使い、未解決名はグレー）＋セリフ本文（`.dialogue` と同じ強調色）。
  感情は表示しない（立ち絵側の演出。ただし `title={emotion}` 程度の tooltip は可）。
- **chat（会話劇）**: 連続する同一話者の dialogue 行を1つの吹き出しにまとめ（`EntityAvatar`＋名前＋各行）、
  narration 行は吹き出し間の `.st-narration` ブロック（中央寄せ・淡色。マーカー表示 `.continue` と
  同系の控えめさ）として挟む。メッセージ全体の外枠・`msgActions`（✎/↻/🗑）は**メッセージ単位のまま**
  （行単位の編集はしない）。
- 未確定行（`tail`）: 生テキストのまま淡色表示＋ストリーミングカーソル。`@美咲(jo` のような書きかけが
  そのまま見えるが、確定した瞬間（次の改行）に正しい表示に変わる。
- 編集モード（`editingId === m.id`）は既存どおり `editBox()`（生テキストの textarea）。

CSS（styles.css）: `.st-dialogue`（話者チップ＋セリフの行）・`.st-speaker`（チップ）・`.st-narration`
（chat 用の地の文ブロック）を追加。既存の `.dialogue`/`.bubble`/`.msg` の見た目に馴染ませる。

```ts
    `【セリフの出力形式（厳守）】\n` +

      `  例: @美咲(joy)「ほんとに？　ありがとう！」\n` +
      `- 感情は neutral / joy / anger / sadness / shy / surprise の6語のみ（括弧内は英語小文字のまま）。\n` +
      `- 地の文（情景・心情・行動の描写）は行頭に @ を付けず、普通の文章として書いてください。\n` +
      `- セリフ行に地の文を混ぜない。地の文に鉤括弧のセリフを埋め込まない（発話は必ず @ 行に分ける）。\n` +
      `- 名前は【登場人物】の表記を正確に使ってください。名前の無い脇役は「@店員(neutral)「…」」のように役割名で構いません。`,
  )
}
```

併せて、構造化 ON のとき**矛盾する既存指示を条件分岐で無効化**する（ここが実装の要注意点）:

1. **novel の執筆ルール**の1行 `「誰の発言か紛らわしい場合のみ、「名前「セリフ」」の形で…」` は
   構造化 ON では出さない（@ 行形式が常に話者を持つため）。該当バレットのみ三項演算子で切り替える。
2. **グループ会話のおまかせ指示**（`「応答は必ず「キャラ名: 」で始めてください。」`）は構造化 ON では
   `「セリフはすべて @名前(感情) 行で書くため、応答の先頭に「キャラ名: 」は付けないでください。」` に
   差し替える。
3. **`buildMessages` の multi プレフィックス**（chat 群像で assistant 履歴に `名前: ` を前置する処理）は
   `session.structuredOutput` が真なら**スキップ**する（@ 行が話者を運ぶため。二重に付けると
   `美咲: @美咲(joy)「…」` という汚れた履歴でモデルを混乱させる）。

### ST2-2. ストリーミング監視と表情反映（store.ts `runCompletion`）

方式: ローカル累積文字列を持ち、**チャンクに改行が含まれた時だけ**確定行を差分パースして
`session.spriteEmotions` を upsert する（1行ごと・軽量。生成中に立ち絵が切り替わる）。

```ts
// runCompletion 冒頭（refs 確定後）に追加:
const structuredOn = !!s.structuredOutput
const watchEmotions =
  structuredOn &&
  !!s.spritesEnabled &&
  refs.characters.some((c) => (c.sprites?.length ?? 0) > 0)
// 追記（appendToId）の場合は既存本文から開始する
let acc = appendToId ? (s.messages.find((m) => m.id === appendToId)?.content ?? '') : ''
let processedLineCount = acc.split('\n').length - 1 // 確定済み（改行で閉じた）行数
let emotionApplied = false

const applyLineEmotions = (completedLines: string[]) => {
  const updates = emotionUpdatesOf(completedLines, refs.characters)
  if (updates.length === 0) return
  emotionApplied = true
  const cur = target()
  if (!cur) return
  const next = [...(cur.spriteEmotions ?? [])]
  for (const u of updates) {
    const idx = next.findIndex((e) => e.characterId === u.characterId)
    if (idx >= 0) next[idx] = u
    else next.push(u)
  }
  patchTarget({ spriteEmotions: next })
}

// writeDelta を拡張:
const writeDelta = (chunk: string) => {
  ...既存の content 追記...
  acc += chunk
  if (watchEmotions && chunk.includes('\n')) {
    const lines = acc.split('\n')
    const completed = lines.slice(0, -1) // 最後の要素は未確定行
    if (completed.length > processedLineCount) {
      applyLineEmotions(completed.slice(processedLineCount))
      processedLineCount = completed.length
    }
  }
}

// ストリーム完了後（finishReason 確定後・choices 生成の前）に最終行ぶんを処理:
if (watchEmotions) {
  const lines = acc.split('\n')
  applyLineEmotions(lines.slice(processedLineCount)) // 末尾行も確定扱いで反映
}
```

**方式A（classifyEmotions）との接続**: 末尾の fire-and-forget 呼び出しを次に変える:

```ts
// 表情判定のフォールバック（方式A）。構造化で1件でも感情が取れた応答ではスキップ
if (finalMsg && finalMsg.content.trim() && !emotionApplied) {
  get().classifyEmotions(sessionId)
}
```

`classifyEmotions` 自体は**無変更で残す**（構造化 OFF セッション・フォーマット無視モデル（D-5）・
感情括弧を書かないモデル（D-3）のための現役フォールバック）。

### ST2-3. chat おまかせの話者確定（store.ts `runCompletion` 完了後処理）

既存の「先頭の `名前:` を剥がして characterId を判定する」処理（`!novel && !characterId &&
refs.characters.length > 1` のブロック）を、構造化 ON のとき次に差し替える:

- `parseStructured(content, refs.characters)` して**最初の dialogue 行の characterId** を採用する
  （全 dialogue 行が同一話者ならその話者、複数話者が混在するなら**先頭話者**をメッセージの
  characterId にする。レンダラは行単位で話者を出すため、characterId はアバター・裏方用の代表値）。
- `名前:` プレフィックスの剥がし（`content.slice(match[0].length)`）は構造化 ON では**行わない**
  （@ 行を壊さないため。ST2-1-2 の指示によりそもそも出なくなる想定だが、出ても剥がさず D-1 で無害）。

構造化 OFF のときは既存処理のまま。

## ST5: `@地の文` ラベル非表示（実装済み）

実運用でモデルが**地の文の行にまで** `@地の文(感情)「…」` とラベルを付けて出力し、`@地の文` の文字列が
そのまま画面に表示される問題が判明した。話者名「地の文」（＝ナレーション自体）を予約語として narration
に落とし、ラベルを描画しない表示整流を行う。**パーサ／レンダラ経路のみの表示整流**にとどめ、生テキスト保存・
graceful degradation（D-1〜D-6）は不変。

`src/lib/structured.ts` の変更（純粋関数のみ・store/React 非依存は維持）:

- `StructuredLine` の narration 変種に `fromTag?: boolean` を追加（`@地の文` ラベルを剥がして地の文に
  落とした行の目印。レンダラ分岐用）。
- `NARRATION_NAMES = new Set(['地の文','地文','ナレーション','ナレーター','narration','narrator'])`
  （ASCII 名の大小文字ゆれ吸収のため小文字保持・照合も `toLowerCase`）。
- `parseLine`: 名前解決後、`NARRATION_NAMES.has(name.toLowerCase())` の行は
  `{ kind:'narration', text: rest, fromTag: true }` を返す（`rest`＝`@地の文(感情)` ラベルを除いた本文。
  本文が空でも `text:''` で落とす＝孤立した `@地の文` ラベルも表示しない）。
- `hasStructuredLines`: `dialogue` 行 **または** `fromTag` の narration 行を含めば真。
  → `@地の文` だけで実キャラのセリフが無いメッセージも構造化レンダラ（ラベル非表示）に載る
  （dialogue 行だけを見ると false になりレガシーレンダラが生テキストを出してしまうため）。
- `plainTextOf`: narration 行は元の行ではなく `parsed.text` を返す。通常の地の文は `text === 元の行`で
  不変、`@地の文` 由来の行はラベルが剥がれる。→ ST3 の裏方文脈5箇所（レビュー transcript・
  チェックポイントラベル・挿絵/背景起案・表情判定フォールバック）から自動的に `@地の文` が消える。

レンダラ（`StructuredMessage.tsx`）・`ChatPanel` は**変更不要**（narration 行の `text` を描画するだけの
既存経路がラベル除去後の本文をそのまま表示する）。

**注意点**:
- 名前は行内の最初の `(`／`（`／`「` までで区切る既存規則のため、実ケースの `@地の文（感情）「…」`・
  `@地の文「…」` は「地の文」が確実に切り出される。区切りの無い `@地の文 本文`（半角/全角スペース区切り・
  括弧なし）は名前が行全体を取り込むため対象外だが、`@名前(感情)「セリフ」` テンプレートに沿った
  実出力は必ず括弧か鉤括弧の区切りを伴うため実害はない。
- 「地の文」を実在のキャラ名にはしない前提（予約語）。
- ストリーミング中の未確定行（tail）も同経路でラベルが剥がれるため、生成中に `@地の文` がちらつかない。

検証: `tsc`/`build` 通過。`preview_eval` で全パターン（日本語括弧・全角括弧・ラベルのみ・英語予約語・
全 narration メッセージ・`plainTextOf`・`hasStructuredLines`）を単体確認、novel/chat 両文体の実 UI で
DOM に `@地の文` が現れないこと・実キャラのセリフは話者チップ/吹き出しで正しく表示されることを確認、
console error 0件。

## 落とし穴・注意（実装者向けまとめ）

- **`Message` スキーマ・persist キーを変えない**。構造はすべて表示時パースで得る。`parts` のような
  パース結果フィールドを保存したくなっても追加しない（生テキストとの二重管理は必ずズレる）。
- **`resolveEmotionUpdates` の名前解決を `matchCharacterByName` に一本化**する（ST1-2）。
  コピーを残すと将来の解決規則変更が片側だけに効く。
- **レンダラのフォールバック判定はメッセージ単位**（`hasStructuredLines`）。セッション単位のトグルで
  レンダラを切り替えると、ON セッション内の旧平文メッセージ・フォーマット無視応答で表示が崩れる。
- **未確定行に感情を反映しない**（D-4）。`@美咲(anger` の書きかけを `anger` と誤読して立ち絵を
  切り替えない——確定は改行のみで判定する。
- **`emotionApplied` は「characterId と emotion の両方が解決できた行があったか」**。名前だけの @ 行
  （感情なし）しか無い応答では方式A フォールバックを走らせる（表情情報ゼロのまま放置しない）。
- **chat 群像の `名前:` 剥がし・前置は構造化 ON で無効化**（ST2-1-3・ST2-3）。有効なままだと
  `@` 行の破壊・履歴の二重話者表記が起きる。
- ST3 の `plainTextOf` 適用は表の5箇所**のみ**。`buildMessages`・`estimateTokens`・編集・エクスポートに
  適用すると形式強化・トークン目安・データ忠実性がそれぞれ壊れる。
- 立ち絵まわりの既存ガード（`spritesEnabled`・sprites 保有チェック・シーン確定時の `spriteEmotions: []`
  リセット）は**そのまま流用**する。ストリーミング監視はこのガードを `watchEmotions` として生成開始時に
  1回評価すれば十分（生成中のトグル切替までは追わない）。
